# T7.1 — Normalize attachment kinds and backfill existing files

## Goal

Stop trusting the upstream `attachments[].kind` field as the final media type.
Derive one normalized kind from the mime type, filename, variants and duration,
persist it, and reclassify existing archives without refetching anything.

## Why

Upstream uses `kind='gif'` for both real GIFs and short silent MP4s. In the
reference archive three attachments are `kind='gif'`, `mimeType='image/gif'`,
but resolve to `original.mp4` with `durationMs` set (see T7.0). Every
downstream consumer (`_gallery_where`, `_decorate_files`, `loadAttachment`)
therefore treats a video as a still image. The same weakness would mislabel any
future `image`/`video`/`file` mismatch.

## Scope

**Classifier (pure function, testable)**

- [ ] Add `classify_media_kind(*, raw_kind, mime_type, original_filename,
      variants, duration_ms) -> str` next to `extract/post.py` (or in
      `cumst/media.py` if it needs URL helpers). It must return one of
      `image`, `gif`, `video`, `audio`, `file`.
- [ ] Precedence:
      1. `video/*` mime, or a media variant/filename ending in
         `.mp4/.webm/.mov/.m4v`, or `duration_ms > 0` with no still-image
         extension → `video`.
      2. `gif` only when the mime is `image/gif` **and** the payload is a GIF
         (`.gif` filename/variant, no MP4/MOV variant).
      3. `image/*` mime or a still extension (`.jpg/.jpeg/.png/.webp/.avif`) →
         `image`.
      4. `audio/*` mime, or `.mp3/.m4a/.ogg/.wav/.opus` → `audio`.
      5. otherwise `file`.
- [ ] Keep the raw upstream value for provenance. Do not silently destroy the
      only record of what cum.st said.

**Schema**

- [ ] Migration `V5`: `ALTER TABLE files ADD COLUMN raw_kind TEXT`, then
      `UPDATE files SET raw_kind = kind WHERE raw_kind IS NULL`.
- [ ] Keep `files.kind` as the normalized value so existing indexes and queries
      keep working. `SCHEMA_VERSION` becomes 5.
- [ ] New rows: `extract_files()` stores the raw value in `raw_kind` and the
      classifier result in `kind`.
- [ ] Existing rows: a reclassify routine updates `kind` from
      `(raw_kind, mime_type, original_filename, variants_json, duration_ms)`.
      No API call, no raw_json parse required.
- [ ] Expose it as `monoke db reclassify` with `--dry-run` support. Print a
      per-transition table (`gif -> video: 3`, etc.) and only write when not a
      dry run. It must be idempotent.
- [ ] Add `CREATE INDEX IF NOT EXISTS files_kind_post` only if the existing
      `files_kind (kind, post_id)` index is insufficient; do not duplicate it
      blindly.

**Tests**

- [ ] Unit table tests for the classifier: real GIF, MP4-backed `gif`, `image`
      with `.mp4` filename, `video` with `video/mp4`, `audio/m4a`, unknown.
- [ ] Extraction test: a payload shaped like the onlyfans rows above produces
      `kind='video'` and `raw_kind='gif'`.
- [ ] Migration/backfill test: insert v4-style rows, run reclassify, assert
      only the MP4-backed gif changes and the real GIFs stay `gif`.
- [ ] Dry run writes nothing.
- [ ] Existing extraction/gallery/media tests stay green after fixtures are
      updated to include `raw_kind`.

## Acceptance criteria

- [ ] On a copy of the reference database, `monoke db reclassify --dry-run`
      reports exactly 3 `gif -> video` changes for creator 2 and 0 changes for
      creator 1.
- [ ] After the real run, this query returns 0 rows:

      ```sql
      SELECT * FROM files
      WHERE kind = 'gif'
        AND (variants_json LIKE '%original.mp4%'
             OR original_filename LIKE '%.mp4'
             OR mime_type LIKE 'video/%');
      ```

- [ ] Real GIFs (`original.gif`, no duration) remain `kind='gif'`.
- [ ] `files.raw_kind` is populated for every row and never NULL after V5.
- [ ] Re-running the command twice produces no further changes.
- [ ] No media bytes are downloaded and no cum.st request is made.

## Out of scope

- Rendering changes (T7.2–T7.4).
- Recomputing `files.url` or variants; raw data is already correct.
- Changing the crawler's API models beyond passing through the existing fields.

## Notes

- `extract_files()` already builds the variant list before inserting the row, so
  the classifier can use it directly. `_write_files()` must also persist
  `raw_kind`; update the INSERT column list and the `save_post_bundle` path.
- `db.GALLERY_KINDS` becomes the single source of truth for gallery-eligible
  kinds in T7.2; do not keep a second hard-coded tuple.
- The three reference posts are 85478926, 74724441 and 65498265.
