# T8.13 — Make viewer preload predictive and decode-ready

## Goal

Make fast viewer swipes as reliable as slow swipes. The viewer is intended to
preload three images ahead and three behind the current item, but the current
implementation often starts fetching only while the user is already swiping.
That leaves a fast gesture waiting on the network or image decode; the incoming
layer appears late, the layout corrects after the gesture starts, and the
viewer can appear to hang before settling.

The preload window must be warm **before** the next swipe begins, and warming
must include decode readiness where the browser supports it. Navigation must
not depend on a new request or a late layout correction in the common case.

## Reported behaviour

- Slow swipes usually work because the gesture gives the browser time to fetch
  and decode the destination.
- Fast swipes can begin before the destination has been fetched, so the
  preview is empty or arrives late.
- The viewer may pause or hang during a fast swipe, then fix the layout after
  the image finishes loading.
- The requirement is specifically **3 images ahead and 3 images behind**, not
  merely scheduling a best-effort request after an idle callback.

## Current implementation and likely causes

- `viewer.js` has `PRELOAD_RADIUS = 3`, but `schedulePreload()` waits for the
  current media to report `load`/`error`, then waits for
  `requestIdleCallback` (up to 1.5 seconds) or a 200 ms fallback.
- A new navigation cancels the pending preload callback and schedules a new
  window. Rapid navigation can therefore repeatedly cancel warming before the
  six-image window is requested.
- `new Image()` warms the HTTP cache, but the later viewer layer is still a
  different element and may need its own decode before it can paint.
- The drag preview currently creates a fresh layer on demand. If that layer is
  not already decoded, the preview can appear after the finger has moved.
- Cross-post payload prefetch and edge-image preload are also idle work, so a
  fast post-boundary swipe can race both the payload request and the image
  request.

## Scope

### A. Warm the full rolling window before input

- [ ] Keep the exact `PRELOAD_RADIUS = 3` contract: up to three eligible image
      URLs before and three after the current item, excluding the current item.
- [ ] Start the first preload as soon as the current media has established its
      first usable state; do not require a long idle wait before issuing the
      six image requests.
- [ ] Keep the current media request highest priority. Preloads must begin
      after the current request is committed, but should not be deferred until
      the browser has a long idle period.
- [ ] When the current index changes, immediately maintain the new rolling
      window. Do not cancel already-started useful loads merely because the
      pointer moved; cancel only stale queued work that has not started.
- [ ] Use a small bounded queue if needed so all eligible items in the
      three-ahead/three-behind window are dispatched promptly without creating
      unbounded work.
- [ ] Preserve the existing data-saver, 2G, reduced-data, hidden-tab and
      image-only exclusions.

### B. Make preloading decode-ready

- [ ] Retain preload image elements until their request and decode settle.
- [ ] Call `decode()` where available and record whether each URL is
      `requested`, `loaded`, `decoded`, or `failed`.
- [ ] Reuse a decoded preload entry when creating the incoming viewer layer,
      or otherwise guarantee that the new layer paints from the already
      decoded browser resource without a second visible wait.
- [ ] Do not append hidden preload elements to the viewer media host; the host
      must continue to contain at most the active layer, transition layer and
      temporary drag preview as defined by T8.12.
- [ ] A preload failure must not block navigation. It may fall back to the
      existing on-demand load path and must not retry continuously.
- [ ] Keep image dimensions available before the preview is painted so the
      shared media step cannot change after the gesture begins.

### C. Fast-swipe and post-boundary behaviour

- [ ] A fast horizontal swipe to an eligible in-post image reveals a
      request-complete, decode-ready neighbour from the first painted drag
      frame.
- [ ] A fast vertical or horizontal post-boundary move must prefetch the
      required neighbouring payload and its edge image early enough that a
      cached boundary move does not begin fetching only after release.
- [ ] Do not fetch arbitrary post payloads or images solely because the user
      touched the stage. Only the bounded adjacent-post plan may be warmed.
- [ ] If the neighbouring post is not available under the data-saving or
      archive-boundary rules, preserve the current T8.12 behaviour and keep
      the drag responsive.
- [ ] The commit path must not restart from a centred incoming layer or wait
      for a second request when a preloaded entry exists.

### D. Memory, lifecycle and priority

- [ ] Keep the hard bound at six in-post preload entries, plus only the
      explicitly bounded adjacent-post edge plan already covered by T8.8.
- [ ] Do not retain duplicate entries for the same URL across the preload map,
      post-boundary cache and incoming layer; define the ownership handoff.
- [ ] Drop entries outside the active rolling window after their request has
      settled, while allowing already-started browser requests to finish.
- [ ] Clear preload state on viewer cleanup and post changes without leaving
      decode promises, timers, listeners or detached media references behind.
- [ ] Use `fetchPriority = "low"` or equivalent only for background work; do
      not lower the priority of the active or committed incoming media.

## Tests

- [ ] Unit/static coverage proves that an index in the middle produces the
      exact three-before/three-after eligible image window and that edges clamp
      correctly.
- [ ] Test the preload state machine for queued, requested, loaded, decoded and
      failed entries, including a decode rejection followed by navigation.
- [ ] Test that moving from index `i` to `i + 1` does not cancel already-started
      loads that are still useful to the new window.
- [ ] Test that an existing decoded preload is reused or promoted without a
      duplicate visible fetch/decode path.
- [ ] Test that at most six in-post preload entries are retained and that
      cleanup clears their references and handlers.
- [ ] Keep the T8.12 gesture harness green, including no first-frame layout
      jump, no black band and no horizontal movement for vertical drags.
- [ ] Browser acceptance in Chromium/Firefox desktop and Android Chrome touch:
      - land on a middle image and verify all eligible URLs from three ahead
        and three behind start before any swipe;
      - use a fast flick immediately after landing and verify that the incoming
        image is already request-complete and paints without a blank frame;
      - repeat fast flicks through at least 10 images and confirm the rolling
        window advances without repeatedly fetching the same URL;
      - verify `performance.getEntriesByType("resource")` shows no
        destination request beginning only after the swipe for warmed images;
      - cross a post boundary quickly and verify the payload/edge-image path
        does not block the transition when it was prefetch-eligible;
      - verify network throttling still degrades safely, with no broken layout
        or permanent hang when a preload is slow or fails;
      - verify data saver, 2G/reduced-data and hidden-tab modes do not start
        background image work;
      - verify memory and live preload references remain bounded after repeated
        forward/backward swipes.

## Acceptance criteria

- [ ] Before a swipe begins, the viewer has proactively requested the eligible
      three images ahead and three images behind the current item.
- [ ] In normal network conditions, a fast swipe to a warmed image has no
      fetch-start stall, blank preview, decode hitch or post-gesture layout
      correction.
- [ ] The incoming media dimensions and position are stable from the first
      painted drag frame.
- [ ] Repeated fast swipes keep the rolling window warm without duplicate
      requests, unbounded memory, or more than the allowed viewer layers.
- [ ] Slow networks and preload failures degrade to the existing safe viewer
      behaviour rather than hanging or corrupting the layout.
- [ ] Data-saving and visibility protections remain intact.
- [ ] No new dependency, no service worker, no disk cache, and no change to the
      viewer payload contract.

## Out of scope

- Preloading videos, GIFs or audio.
- Downloading the entire post or archive.
- Service workers, persistent offline storage or custom HTTP cache policy.
- Predictive preloading based on swipe velocity beyond the fixed three-ahead /
  three-behind window.
- Replacing the T8.12 two-layer transition model or changing direction
  semantics.

## Notes

- “Requested” is not sufficient for this ticket: a browser may have started
  the transfer while the image is still unavailable to paint. The important
  fast-swipe invariant is request plus decode readiness before the gesture.
- `requestIdleCallback` is useful for optional background work but cannot be
  the only trigger for the six-image window; a fast user can swipe before idle
  work runs.
- The implementation should preserve the current media's priority and avoid
  turning six background loads into a connection flood. Measure the trade-off
  in the browser acceptance pass rather than relying on timer tuning.
