# T7.5 — Explain (and de-emphasise) empty tags for upstream creators

## Goal

When a creator has no tags upstream, the UI should say so instead of showing an
empty Tag dropdown that looks like a bug. No derived or invented tags.

## Why

`onlyfans/39058172` has 0 tag rows. Investigation (T7.0) confirmed this is
faithful: the live profile returns `"hasTags": false`, and every stored post
payload has `"tags": []`. The page still renders a Tag select with only "Any",
which reads as "tagging is broken". The post page correctly hides its tag chips,
so only the creator filter form needs a clear empty state.

## Scope

- [ ] `_facet_context()` already receives `tag_facets`. When the list is empty
      and no `tag` filter is active, hide the Tag select and render a muted
      note: "No tags provided by cum.st for this creator." Keep the control
      visible when a tag filter is active (so the user can clear it).
- [ ] Do the same on the gallery filter form (`gallery.html`) when there are no
      tag facets. Do not add a dead empty select.
- [ ] Do not show the note when tags exist but the current filters hide them;
      in that case the select stays and shows the matching tags.
- [ ] Optional: if the profile's `hasTags` flag is persisted, use it to
      distinguish "upstream has no tags" from "tags exist upstream but were not
      ingested". Do not add a migration just for this; a count-based message is
      enough for now.
- [ ] Add a short line to the creator/gallery empty-tag note explaining that
      tags come from cum.st and are not derived from captions.

**Tests**

- [ ] Creator page with zero tags: no `<select ... name="tag">`, note present,
      all other filters unchanged.
- [ ] Creator page with tags: select renders and the note is absent.
- [ ] Active `?tag=foo` with zero facets still renders a way to clear it.
- [ ] Gallery page with zero tags follows the same rule.
- [ ] Existing facet/creator/gallery tests stay green.

## Acceptance criteria

- [ ] `/c/2` no longer shows an empty Tag dropdown; it shows the explanatory
      note.
- [ ] `/c/1` (creator with tags) is unchanged.
- [ ] Filtering, htmx partial updates and pagination URLs are unaffected.
- [ ] No tags are invented from captions or filenames.

## Out of scope

- Deriving tags from caption hashtags (only 5 posts on the reference archive,
  all `#FINISHED`; not worth a feature).
- Backfilling tags from another source.
- Any crawler change.

## Notes

- The user-visible complaint was "tagging is incorrect". The data is correct;
  this ticket fixes the misleading empty control and records the upstream
  limitation.
- Related: T7.0 documents the exact `hasTags`/`tags` evidence.
