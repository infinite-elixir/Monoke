# T8.9 — Fluid transitions between viewer media

## Goal

Replace the hard cut in the fullscreen viewer with a short, directional
transition. Moving between images should feel like moving through a strip:
the outgoing image leaves in the gesture direction while the incoming image
arrives from the opposite side, with no blank stage, layout shift or flash of
the counter.

The transition must never make slow navigation slower: the current image stays
visible until the destination is ready, and reduced-motion users get the
current instant swap.

## Current behaviour

- `viewer.js` `render(index)` calls `unloadMedia()` before building the next
  `<img>`/`<video>`. The old element is removed immediately, so the stage is
  blank until the new element loads.
- `.viewer-media-el` has only `max-width`/`max-height`; no enter/leave classes
  or transition state. `.viewer-media` has a 120 ms opacity transition used for
  `aria-busy`, not navigation.
- Preloaded neighbours from T8.7/T8.8 are in the HTTP cache, but the DOM still
  hard-swaps.
- `go(action)` knows the semantic direction (`next-image`, `prev-image`,
  `next-post`, `prev-post`), so the desired motion is already available.
- `?quiet=1` and `prefers-reduced-motion: reduce` currently make the hint
  instant; navigation is instant for everyone.
- Rapid arrow presses, wheel bursts and boundary post jumps can overlap; any
  transition must keep exactly one visible item and must not leak layers or
  fetches.

## Scope

**Transition intent**

- [ ] Add a small pure helper (Node-testable, in a `BEGIN/END transition-plan`
      block) that maps an action to a direction:
      - `next-image` → `{x: 1, y: 0}` (incoming from the right),
      - `prev-image` → `{x: -1, y: 0}`,
      - `next-post` → `{x: 0, y: 1}` (incoming from below),
      - `prev-post` → `{x: 0, y: -1}`.
      Boundary crossings keep the same action, so right-at-the-edge still
      slides horizontally into the next post.
- [ ] `go()` passes that intent to `render(index, updateUrl, intent)`. Direct
      first paint, URL restoration and error recovery have no intent and do not
      animate.

**Two-layer renderer**

- [ ] Keep the outgoing media element alive while the incoming element is
      prepared off-screen. Build the incoming element with the same
      `<img>`/`<video>` rules as today (poster, controls, alt, error fallback).
- [ ] For an image, commit when it is decoded: use `img.decode()` where
      available, otherwise `load`/`error` (and `complete` immediately). The
      outgoing image remains visible in the meantime.
- [ ] Do not wait indefinitely to update the UI. If decoding has not completed
      after a short safety window (suggest 400–600 ms), reveal the incoming
      element at its starting transform and let its own load event drive the
      rest; keep the outgoing layer behind it rather than blanking the stage.
- [ ] The host may contain at most **two** `.viewer-media-el` layers during a
      transition. Remove the outgoing layer after `transitionend` or a bounded
      timeout, and always remove it on error, close, post jump or reduced-motion
      path.
- [ ] If the incoming item errors, keep the existing `Media unavailable`
      fallback and make sure the outgoing layer is removed. Do not leave two
      interactive videos alive.
- [ ] Videos/GIFs: crossfade opacity only, without translating the video's
      native controls. Do not restart a video that is already the current item;
      pause and unload the outgoing video only after it has left the screen.
- [ ] Images may translate + fade. Use `transform: translate3d(...)` and
      `opacity` only; never animate width, height, top/left or layout.
- [ ] The counter, URL, announcer and `aria-busy` update once, when the new
      item is committed. Do not announce both layers.
- [ ] `history.replaceState` still runs exactly once per move and keeps the
      existing `?post=&i=` contract.
- [ ] A post jump still uses the T8.8 cached payload/fetch path. The transition
      starts after the target payload is known; a failed jump leaves the
      current media, counter and URL untouched and shows the existing flash.

**Motion design**

- [ ] Duration 180–240 ms, easing close to
      `cubic-bezier(0.22, 1, 0.36, 1)`.
- [ ] Incoming horizontal offset ~8% of the stage width; vertical ~8% of its
      height. Outgoing offset ~4% opposite, with opacity fade. This is a hint of
      direction, not a full-screen carousel that exposes neighbouring pixels.
- [ ] Both layers are centred and sized exactly like the current media, so
      there is no layout shift and no counter jump.
- [ ] First paint, direct URL load, `?quiet=1` and
      `prefers-reduced-motion: reduce` bypass the enter animation and behave
      like today. The global reduced-motion CSS remains the final guard.
- [ ] Rapid navigation: a new move supersedes the in-flight transition, snaps
      the current incoming layer to its final transform, removes any older
      layer, then starts the newest transition. At no point may three layers be
      present.
- [ ] A transition never hides the current image before the incoming image is
      available. A slow network shows the old image until the new one is ready,
      not a black stage.
- [ ] Do not preload or fetch outside T8.7/T8.8. The transition reuses the same
      URL and relies on the browser cache/decoded images.
- [ ] Do not introduce timers on idle, observers, animation libraries or a
      requestAnimationFrame loop. CSS transitions plus `transitionend` are
      enough.

**Styling**

- [ ] Add viewer transition classes in `style.css`, scoped to
      `.viewer-media`/`.viewer-media-el`, with a z-index/stacking rule that
      keeps the incoming layer above the outgoing one.
- [ ] The outgoing layer must not intercept clicks/taps after it starts
      leaving (`pointer-events: none`).
- [ ] No transition on `.viewer-media` for `aria-busy`; keep that feedback
      independent.
- [ ] `prefers-reduced-motion: reduce` removes transform/opacity transitions
      and the old layer is removed synchronously.
- [ ] No persistent controls, captions or chrome are added.

**Tests**

- [ ] Node test for the extracted `transition-plan` helper: all four actions,
      edge-crossing actions and unknown/no intent.
- [ ] Static tests that `render()` accepts an intent, reduced motion bypasses
      the transition, and the two-layer limit is documented/enforced.
- [ ] Markup/CSS tests for the transition classes and reduced-motion block.
- [ ] Server/viewer contract tests remain green; no payload or route changes
      are expected.
- [ ] Browser acceptance in Chromium and Firefox, with CPU/network throttling:
      - left/right/up/down animate in the correct direction;
      - a post-edge crossing slides horizontally and never blanks;
      - ten rapid `ArrowRight` presses leave one media element and the correct
        final counter/URL;
      - slow 3G keeps the old image visible until the new one decodes;
      - `?quiet=1` and emulated reduced motion swap instantly;
      - no more than two media elements exist during a transition and none
        remain after it;
      - video controls stay usable and the video is not restarted by a
        transition;
      - T9.2 bookmark keys and T8.8 fullscreen still work during/after a move.

## Acceptance criteria

- [ ] Moving between any two viewer items is a short directional transition
      instead of an immediate blank/unload.
- [ ] The outgoing item stays visible until the incoming item is ready; slow
      loads never produce a blank stage.
- [ ] Post-boundary moves animate in the same direction as in-post moves.
- [ ] Reduced-motion and quiet mode remain instant and correct.
- [ ] Rapid navigation is bounded, the final item/URL/counter are correct, and
      there is no DOM or image-layer growth.
- [ ] No new dependency, no idle timers, no layout shift, no changed input
      semantics, and all existing viewer/bookmark tests stay green.

## Out of scope

- Finger-following drag/rubber-band gestures (T8.10).
- Zoom, pan, pinch, rotation, slideshow/autoplay.
- A filmstrip, thumbnails, captions or persistent navigation chrome.
- Transitioning the T4.7 gallery lightbox.
- Animated GIF frame control or video seeking.

## Notes

- The T8.8 cache already makes the incoming image usually decode immediately;
  the transition should observe readiness rather than add delay.
- Preloaded `Image` objects are owned by `preloadMap`. Do not move them into the
  DOM; create a normal `<img>` with the same URL so the browser can reuse the
  cached response/decoded data.
- Keep the existing error/fallback and bookmark paths intact. The transition is
  a DOM shell around the same media lifecycle, not a second renderer.
- Use `transitionend` with a guarded timeout. `transitionend` alone is not
  reliable when the tab is hidden or the transition is cancelled.
