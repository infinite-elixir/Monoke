# T3.3 — Shortener resolution

## Goal
See through `bit.ly`/`t.co` so a "MEGA" link is actually filed under MEGA.

## Scope

- [ ] Resolve only categories in `{shortener}`.
- [ ] Method: `HEAD` first, fall back to `GET` with `follow_redirects=True`, max 5 hops,
      `timeout=8s`, browser-ish UA (not the Monoke API UA; these are third parties).
- [ ] Cache every attempt in `link_resolutions(url, final_url, resolved_at)`; never retry a
      resolved or recently failed URL within 30 days.
- [ ] Concurrency 2, global; total budget per run: 100 resolutions (configurable), then defer.
- [ ] On success: set `links.resolved_url`, re-run `classify(final_url)`, update `category`.
- [ ] On failure/timeout/loop: leave the row as `shortener`, set `final_url = NULL`, continue.
- [ ] Flag `--no-resolve` on the CLI and a toggle in the UI for a fast, offline crawl.

## Acceptance criteria

- [ ] `http://bit.ly/49A802v` resolves to a `mega.nz` URL and its category becomes `mega`.
- [ ] The original URL stays in `links.url`; `links.resolved_url` holds the target.
- [ ] A second crawl performs zero new resolution requests (cache hit).
- [ ] A dead shortener (404) does not fail the post or the run.
- [ ] RespX tests cover: direct 301, 2-hop chain, redirect loop, timeout.

## Notes
- This is the only place Monoke talks to a non-Kemono host. Keep it optional and cheap.
- Never resolve shorteners found in `post.caption` more than once globally, even across creators.
