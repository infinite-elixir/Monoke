# T8.14 — Make boundary payloads eager and preload priorities predictive

## Goal

Remove the remaining fast-swipe hitch when the destination is in another post.
The viewer must warm the adjacent post payload early enough for a boundary
gesture to have a destination before release, while keeping the immediate
in-post images ahead of deeper background work.

## Findings

- The viewer currently starts adjacent post JSON warming only after the active
  media is considered ready.
- A prefetched payload is cached, but its returned media is not explicitly
  promoted into the image preload path until the post is entered.
- Every image created by the preload path is assigned `fetchPriority = "low"`.
  This protects the active image, but can unnecessarily delay the next and
  previous in-post destinations.
- `fetch()` supports an optional low-priority request hint in browsers that
  implement it; unsupported hints must remain harmless.

## Scope

### A. Eager adjacent payload warming

- [x] Start the bounded previous/next payload plan as soon as the current
      viewer state is known, without waiting for the current image's load event.
- [x] Start the same bounded plan immediately after a neighbouring payload is
      applied, before waiting for the incoming image transition.
- [x] Keep bookmark mode, archive boundaries, hidden-tab, data-saver, 2G and
      reduced-data protections unchanged.
- [x] Keep payload requests deduplicated and bounded to the two adjacent posts.

### B. Promote payload media into image warming

- [x] When an adjacent payload arrives, warm only its eligible edge image(s)
      and the already-bounded current rolling image window.
- [x] Reuse the existing URL map and failure state; do not create duplicate
      requests for URLs already warming or decoded.
- [x] Do not retain arbitrary post payloads or full post media beyond the
      existing payload cache bound.

### C. Priority policy

- [x] Keep the active committed media at browser-default/high priority.
- [x] Use browser-default priority for the nearest previous and next eligible
      in-post image so an immediate swipe is not artificially delayed.
- [x] Keep deeper in-post entries and adjacent-post edge work low priority.
- [x] Use a low-priority fetch hint for background JSON where supported, without
      requiring that option in browsers that ignore it.

## Tests

- [x] Static coverage proves payload prefetch is invoked from initial state and
      immediately after applying a neighbouring payload.
- [x] Static/Node coverage proves nearest in-post images are not assigned low
      priority while deeper and adjacent work remains low priority.
- [x] Verify payload responses do not cause duplicate image requests.
- [x] Keep the T8.13 preload state tests and T8.12 gesture harness green.
- [x] Run the full offline test suite.

## Acceptance criteria

- [ ] On landing, previous and next post payload requests begin without waiting
      for the first image's load event.
- [ ] A fast boundary swipe uses a cached payload and a warmed edge image when
      both were eligible; it does not begin JSON and image discovery only after
      release.
- [ ] Immediate in-post swipes are not delayed by forcing their image requests
      to low priority.
- [ ] Background work remains bounded, deduplicated and disabled by existing
      data-saving and visibility protections.
- [ ] Slow or failed payload/image warming still falls back to the existing
      safe navigation path.

## Out of scope

- Fetching the entire archive or more than the two adjacent post payloads.
- Preloading video, GIF or audio media.
- Service workers, persistent storage or custom HTTP cache policy.
- Velocity-based or machine-learned prediction.

## References

- `HTMLImageElement.fetchPriority`: the browser hint is advisory, not a
  correctness mechanism.
- `HTMLImageElement.decode()`: decode readiness is separate from request
  completion.
- `link rel=preload` guidance: dynamically discovered image resources can
  otherwise start after script execution and should be prioritized selectively.
