# T8.17 — Fix viewer media that never paints: videos and stuck black images

## Goal

Make every media item the viewer commits render on the first presentation.
Videos must show a poster (or a deliberate placeholder) with working native
controls and play when activated. Images must never remain a black rectangle
that only recovers after swiping past it and coming back.

The viewer may show an unavailable state for a genuinely broken URL, but
"black and stuck" is never an acceptable terminal state.

## Reported behaviour

- Opening the fullscreen viewer from the gallery shows images but not videos,
  even though the same videos appear as tiles in the gallery.
- Some images render as a black box. Swiping forward past the image and then
  swiping back makes the image appear.
- The problem is not limited to a single creator or a single post.
- The same session can show the image normally after the away-and-back
  gesture, so the URL is not necessarily dead.
- The separate complaint about a black area appearing *during* a swipe is
  covered by T8.18. This ticket is about media that never paints at all.

## Current implementation and likely causes

### Videos

- `viewer_media()` and `VIEWER_KINDS` do include `video`, and route tests prove
  a video payload and a `<video>` element are produced. The failure is therefore
  in rendering/normalization, not in the media query alone.
- The first item is server-rendered by `viewer.html`; later items are created by
  `createMediaElement()` in `viewer.js`. Only the JS-created element receives the
  `error` listener in `createMediaElement()`. A server-rendered first video that
  fails stays as a black `<video>` instead of becoming `viewer-unavailable`.
- `.viewer-media-el` sets `background: #000`. A video with no poster, no decoded
  first frame, or a failed source is indistinguishable from a black image.
- Videos are created without `width`/`height` attributes, unlike images. If the
  browser cannot determine an intrinsic size before metadata loads, the element
  can occupy an unexpectedly small or zero box.
- `kind` is normalized by ingestion, but stored rows can still be stale or
  mixed (`video/mp4` or an `.mp4` URL under an image kind, or an MP4-backed
  "gif"). Such a row is rendered as `<img>` and appears black. The viewer should
  not depend on a single historical `kind` value when MIME/extension disagree.
- Video poster URLs are upstream thumbnails and can fail independently of the
  video URL. A failed poster should not leave a black element.
- Video playback is deliberately not autoplayed (`preload="metadata"`), so the
  poster and native controls are the only affordances before the user presses
  play. Both must be visible and reachable.

### Black images

- Images can arrive through two paths: the server-rendered first `<img>`, or a
  JS-created layer that may reuse an entry from `takeDecodedPreload()`.
- A detached preload image can be decode-complete without having painted. When
  it is promoted directly into a visible layer, the element may composite as
  its black CSS background for one or more frames.
- `removeLayerNow()` clears `src` on removed layers. If a preload/layer
  reference is promoted or reused after that cleanup, the committed element has
  no source and shows black.
- `warmPreloadWindow()`, `prunePreloadMap()` and the decode callbacks do not
  share a generation token. A late callback can mutate an entry after the
  viewer has moved on.
- `whenReady()` resolves on a 500 ms safety timer with `ready=false`. The
  commit path still makes the incoming layer fully opaque. If the incoming
  element has no bitmap, the stage shows black until a later load event.
- `onMediaError()` treats a removed/leaving layer as expected, but a failed
  promotion that is already active can end up in the unavailable path only
  after the UI has already shown black.
- The server-rendered first image is not created through `createMediaElement()`,
  so it does not get the same `__viewerItem`/error/attribute setup as later
  layers until the script attaches it.

## Scope

### A. One rendering path for server and client

- [ ] Make the server-rendered first media element and every JS-created element
      share the same setup: kind, `src`, dimensions, alt/aria label, poster,
      controls, error handling, item metadata and render generation.
- [ ] Keep the no-JavaScript server-rendered fallback working.
- [ ] Do not duplicate listener attachment when the script adopts the
      server-rendered element.

### B. Videos must be visibly video

- [ ] Render `kind == "video"` as `<video controls playsinline
      preload="metadata">` with a poster when `thumb_url` exists.
- [ ] Never autoplay.
- [ ] Give the video an explicit aspect box (intrinsic `width`/`height` when
      known, otherwise the configured media box) so `object-fit: contain`
      applies and controls are not clipped.
- [ ] If the poster is missing or fails, show a neutral media placeholder with
      a play affordance, not a black rectangle.
- [ ] Bind `error` on the server-rendered video as well as JS-created videos.
      A failed video source becomes the existing `viewer-unavailable` state.
- [ ] Keep the native controls interactive: tapping/dragging on a video's
      controls must not start a viewer swipe or trigger a left/right tap zone.
- [ ] Pause, clear `src` and release the previous video when leaving it, so
      audio cannot continue behind the next item.
- [ ] Normalize kind at viewer read time using MIME type and URL extension as a
      fallback when stored `kind` is missing or contradictory. Do not rewrite
      the database in this ticket.
- [ ] A gallery video tile must deep-link to that exact video; the viewer must
      not land on a different index or on an image.

### C. Images must paint or fail explicitly

- [ ] Promote only an element that is known to have a valid, loaded source.
- [ ] Track a render generation/token for every layer. Late `load`, `decode`,
      `error`, prune and cleanup callbacks from an older generation must not
      change the current layer.
- [ ] Never remove or clear the source of an element that is active, incoming
      or the hand-off preview.
- [ ] On promotion, reset all transient classes and inline `transform`,
      `opacity`, `willChange`, `pointerEvents` and stale `src` values.
- [ ] Do not leave an `<img>` with a black CSS background as the visible layer.
      Either paint a known thumbnail/placeholder behind it or make the image
      layer transparent until its first frame is ready.
- [ ] If the safety window expires before the image is ready, keep the outgoing
      layer visible (or a placeholder) rather than revealing a black incoming
      layer.
- [ ] On `error`, try the post thumbnail once where available, then show
      `viewer-unavailable`. Never retry forever.
- [ ] Only commit a new index once the destination is either painted or has a
      deliberate placeholder; the counter and URL must not claim an item that
      is still an empty black element.

### D. Diagnostics

- [ ] In debug mode, record per render: item kind, index, URL, whether it came
      from the server/preload/fresh element, `complete`, `naturalWidth`,
      `naturalHeight`, decode state and the final layer state.
- [ ] Expose the current render generation and preload entry status to the
      Node/browser test harness.
- [ ] A failed render must leave a useful log line and an unavailable card,
      not a silent black layer.

## Tests

- [ ] Route test: a mixed post renders a `<video>` with poster, controls,
      playsinline, metadata preload and no autoplay when the video is the first
      item.
- [ ] Route test: the same post renders a video at a later index when opened
      with that index.
- [ ] Node/DOM test: the server-rendered element receives exactly the same
      setup/error handling as a JS-created element.
- [ ] Node test: a stale generation callback cannot commit, clear `src`, or
      change the active layer.
- [ ] Node test: a failed image source falls back to the thumbnail once and then
      to unavailable; it never remains a black active layer.
- [ ] Node test: a promoted preload whose `src` was cleared is rejected and a
      fresh element is created instead.
- [ ] Keep the T8.2, T8.5, T8.12 and T8.16 viewer tests green.
- [ ] Browser acceptance in Chromium/Firefox desktop and Android Chrome touch:
      - open a mixed post and step through every item; every video shows its
        poster, controls and plays;
      - deliberately break one video URL and one poster URL and verify a useful
        fallback rather than a black box;
      - reproduce the stuck-black image with network throttling; verify it
        either paints or shows a placeholder/unavailable state without needing
        an away-and-back swipe;
      - leave a playing video by swiping and verify audio stops;
      - open videos from the gallery's Videos tab and verify the exact item is
        shown.

## Acceptance criteria

- [ ] A video in the viewer is visibly a video before play: poster or
      placeholder, native controls, correct box.
- [ ] Pressing play starts the video; leaving it stops and unloads playback.
- [ ] A failed video or poster shows a clear fallback, never a silent black box.
- [ ] An image committed by the viewer paints on first presentation; the
      away-and-back gesture is no longer required.
- [ ] When an image cannot be painted before the safety window, the viewer keeps
      a valid previous frame or placeholder until it can.
- [ ] Server-rendered and JS-created media behave identically.
- [ ] No regression to swipe gestures, fullscreen, controls, bookmarking or the
      T8.12 layer model.

## Out of scope

- Preloading video bytes, transcoding, proxying or fixing upstream CDN URLs.
- Rewriting historical `files.kind` rows (T7.1 already owns normalization).
- Changing the viewer payload contract for navigation (T8.1 owns it).
- The swipe-frame preload overhaul (T8.18).
- Gallery filter context in the viewer (T8.19).

## Notes

- A `decode()` promise proves the browser has a decoded bitmap, not that the
  element has been painted in its final box. Do not treat decode success alone
  as "ready to show".
- A poster is an image resource: it must be allowed to fail independently of
  the video source.
- The black CSS background is useful behind a video, but it actively hides the
  difference between "loading" and "broken" for images. Prefer a deliberate
  placeholder for images and keep black only for the letterbox around video.
