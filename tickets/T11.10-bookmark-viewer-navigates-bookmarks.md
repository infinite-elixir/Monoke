# T11.10 — The viewer opened from Bookmarks navigates bookmarks, not post media

## Goal

When the merged lightbox/viewer is opened from `/bookmarks`, prev/next must walk
the **media bookmarks you are browsing**, not every attachment of the underlying
post. Today the overlay always hydrates a post playlist through
`/c/{creator}/viewer/data?post={service_id}`, so a media bookmark opens inside
its post and the arrows immediately wander into unbookmarked attachments and
then into neighbouring posts.

The gallery entry point keeps its current post-scoped playlist. Only the
Bookmarks entry point changes context.

## Why this is a change of a locked decision

T11.3 deliberately chose "all media of the underlying post, no bookmark-only
playlist". That decision is what causes the reported behaviour and is
**superseded for the Bookmarks entry point** by this ticket. T11.3's data hooks,
no-JS tile links and overlay reuse stay; only the playlist source and the
up/down behaviour change.

## Current behaviour

- `bookmarks.html` media tiles carry `data-lightbox-open`,
  `data-post-service-id` and `data-sha256`, but no source/context hook.
- `lightbox.js` `openFromTile()` always fetches
  `/c/{creator}/viewer/data?post={service_id}` and selects the tile's sha
  inside `payload.media`.
- `canStep()`, the arrows, wheel and swipe all operate on
  `payload.media[].index` and fall back to `payload.previous_post` /
  `payload.next_post` at the edges. The announcer and counter read
  "N of M in this post".
- Result: opening bookmark 3 of 83 shows "1 of 5 in this post", prev/next walks
  the post's other four media, then crosses into a different post. The
  bookmarks page's own order and filter are lost.
- The gallery has no such problem: its playlist genuinely is the post, and
  cross-post navigation is wanted there.

## Locked decisions (2026-10-23)

| Question | Decision |
|---|---|
| Playlist source | The media bookmarks of the current Bookmarks view, in the library's own `created_at DESC, id DESC` order. |
| Scope when filtered | Creator-filtered view: that creator's media bookmarks, across all pages. |
| Scope on the grouped overview | The creator section the tile was clicked in, so navigation stays inside that section. |
| Left/right | Previous/next bookmark in that playlist, crossing pages. |
| Up/down and vertical swipe | Disabled in this context. There is no post chain to cross; do not silently leave the bookmark set. |
| Start item | The clicked `sha256`. If it is no longer in the payload, keep the overlay on the unavailable state and let the arrows recover. |
| Missing media | Stays in the playlist and is navigable, exactly as in the library. |
| Counter/copy | "3 of 83 bookmarks", not "in this post"; post title and **Go to post** stay. |
| Unbookmarking the current item | Remove it from the in-memory playlist and counter; keep the current medium on screen until the next navigation, which then lands on the neighbouring surviving bookmark. |
| Gallery | Unchanged: post playlist, left/right within post, up/down across posts. |
| No new HTML route | JSON-only data endpoint; no `/bookmarks/viewer` page. |

## Scope

**Data and endpoint**

- [ ] Add a read-only JSON endpoint for the bookmarks context, e.g.
      `GET /bookmarks/viewer/data?view=media&creator={id}&sha={sha256}`,
      `include_in_schema=False`.
- [ ] It accepts the same `BookmarkFilters` fields the page uses (`view`,
      `creator`) and the clicked `sha256`, and returns the playlist needed by
      the controller:
      - `context: "bookmarks"`
      - `media[]` in library order with `sha256`, `kind`, `url`, `thumb_url`,
        `title`/filename, `creator_id`, `creator_name`, `post_service_id`,
        `post_title`, `post_url`, `missing`, dimensions and duration
      - `index` of the clicked sha
      - `total`
- [ ] The playlist covers the **whole filtered set**, not just the current
      page. Add or reuse a repository helper that returns every media bookmark
      for the filter without the page limit (guard with a sane hard cap so the
      payload cannot grow unbounded, and document the cap).
- [ ] Reuse `_decorate_library_media()` so viewer rows match the tiles.
- [ ] Unknown creator or an empty set returns `404` with a JSON error, mirroring
      the existing viewer endpoint.
- [ ] Do not change `/c/{creator_id}/viewer/data`; the gallery and its tests
      keep using it.

**Markup and context**

- [ ] Mark bookmarks media tiles with a viewer source, e.g.
      `data-viewer-context="bookmarks"`, a `data-creator-id`, and the existing
      `data-post-service-id`/`data-sha256`. Keep the tile's post `href` and all
      T11.3 hooks.
- [ ] On the grouped overview, include the section's creator id on the tile so
      the controller can request a creator-scoped playlist even though the page
      has no creator filter.
- [ ] Keep the overlay root and `lightbox.js` include unchanged; no second
      overlay or controller.
- [ ] Post bookmark cards still navigate to the post page, not the overlay.

**Controller (`lightbox.js`)**

- [ ] Record the entry context from the tile when opening. Gallery tiles keep
      the existing post-scoped path; bookmark tiles fetch the new endpoint and
      never request `/c/{creator}/viewer/data`.
- [ ] Treat a bookmarks payload as the active playlist: `canStep()`,
      left/right, wheel left/right, horizontal swipe and the nav buttons index
      `payload.media`; there is no `previous_post`/`next_post` fallback.
- [ ] Disable/hide post navigation in this context: up/down keys, wheel
      up/down, vertical swipe, and the post prev/next controls. They must not
      fetch, announce or navigate anywhere.
- [ ] Announce and counter use the bookmark wording and total; keep the media
      kind and post title. The post bar link remains **Go to post**.
- [ ] Reuse the existing prefetch window over the bookmark playlist and skip
      cross-post payload prefetching when `context === "bookmarks"`.
- [ ] The top media bookmark control and `b` shortcut still target the current
      sha. After a successful toggle, splice the item out of the playlist when
      it was removed, clamp `currentIndex`, refresh the counter/arrow state and
      leave the current medium visible.
- [ ] Opening another tile after closing rebuilds the playlist from the current
      library state; do not cache a stale bookmark playlist across overlay
      sessions.
- [ ] Closing still restores focus to the originating tile and leaves the page
      URL, filters and page untouched.

**Copy and accessibility**

- [ ] The announcer says, for example, "Image 3 of 83 bookmarks · NyL".
- [ ] Disabled vertical navigation is not exposed as a dead control: give
      post buttons a disabled state and update the overlay's keyboard help.
- [ ] The first-run hint removal is T11.9; do not reintroduce hint copy here.

**Tests**

- [ ] Endpoint: creator-filtered request returns only that creator's media
      bookmarks, in library order, across all pages, with the clicked sha's
      index; overview request without a creator returns the whole set.
- [ ] Template: bookmark media tiles expose the bookmarks context and creator
      id; gallery tiles do not.
- [ ] JS source/behaviour: opening a bookmark tile requests the bookmarks
      endpoint and not the post endpoint; left/right moves to the next bookmark
      across page boundaries; up/down and vertical swipe do nothing.
- [ ] JS behaviour: the counter reflects the number of bookmarks, not post
      media, and unbookmarking updates the playlist without ejecting the
      overlay.
- [ ] Regression: opening the same media from a gallery still uses the post
      playlist and still crosses posts up/down.
- [ ] Missing media remains navigable from the bookmarks playlist.
- [ ] `node --check src/monoke/web/static/lightbox.js` and `uv run pytest` pass.

## Acceptance criteria

- [ ] Opening a media bookmark shows "N of M bookmarks" and starts on the
      clicked item.
- [ ] Left/right, wheel-left/right and horizontal swipe move to the previous/
      next bookmark, including across library pages.
- [ ] Up/down fades or disables; it never leaves the bookmarks set or loads a
      different post.
- [ ] It is impossible to reach an unbookmarked attachment by navigating from
      the Bookmarks viewer.
- [ ] The same overlay opened from a gallery still walks the post's media and
      crosses posts.
- [ ] Unbookmarking from the overlay removes the item from the sequence without
      closing the overlay or resetting the library.
- [ ] Closing returns to the same bookmarks page, filter, tab and page number.

## Out of scope

- Changing the gallery's post playlist or its cross-post navigation.
- A bookmark-only HTML viewer route.
- Reordering the library itself (it remains newest-bookmarked first).
- Cross-creator navigation from the grouped overview beyond the clicked
  section.
- Post bookmarks in the viewer (T11.9 keeps them out).
- Media caching, preload tuning or fullscreen behaviour beyond reusing them.

## Notes

- The bug is a context mismatch, not a repository bug: the library already
  knows the exact ordered set. Prefer passing that set to the controller over
  inferring it from ranked posts.
- `viewer_state()` is post-shaped and should stay that way; do not teach it
  bookmark filters.
- The hard cap on the playlist is a payload guard, not a product limit; if a
  user has more bookmarks than the cap, navigation covers the capped prefix and
  the counter says so.
- Update the viewer section of `docs/INSTALL_AND_USAGE.md` (currently states
  that bookmark entry inherits post navigation) after implementation.
