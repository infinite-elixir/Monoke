# T2.3 — Run records, progress events, CLI

## Goal
Every crawl is observable, recordable, and reproducible from the terminal.

## Scope

- [ ] `runs` row created at start (`status=running`), finished with counts, duration, error.
- [ ] `crawler/events.py`: an in-process pub/sub keyed by `run_id`.
      ```python
      bus.publish(run_id, {"phase": "posts", "page": 3, "pages": 16,
                           "done": 120, "total": 782, "links": 41})
      bus.subscribe(run_id)  # async iterator for SSE
      ```
- [ ] Event types: `started`, `page`, `progress`, `post_failed`, `warning`, `done`, `error`.
- [ ] CLI:
      ```bash
      uv run monoke sync <url> [--full] [--limit N] [--concurrency 4] [--no-cache] [--json]
      ```
- [ ] Human report on success:
      ```
      782/782 posts · 812 links · 912 files · 14.2s (16 pages, 0 errors)
      ```
- [ ] `--json` prints the `RunResult` as JSON on stdout, logs on stderr.
- [ ] Exit codes: `0` ok, `1` run failed, `2` usage/parse error, `3` API blocked.
- [ ] `monoke db stats` prints row counts per table and DB size.

## Acceptance criteria

- [ ] A run row exists for every CLI invocation, including failures.
- [ ] `--json` output parses with `jq` and contains all `RunResult` fields.
- [ ] Ctrl-C finishes the run as `cancelled` (not `failed`) and keeps written posts.
- [ ] Report numbers match `SELECT count(*) FROM posts WHERE creator_id=?`.
- [ ] `monoke db stats` works on an empty DB without crashing.

## Notes
- The event bus is per-process; if the app later runs multiple workers, this becomes a DB
  cursor or Redis. Not now.
