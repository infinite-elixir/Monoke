# T8.18 — Overhaul viewer image preloading into a paint-ready pipeline

## Goal

Replace the current best-effort image warming with a real preload pipeline:
the destination must be fetched, decoded, sized and **paint-ready** before the
gesture begins, so the first drag frame already contains the destination
pixels. A swipe must never reveal a black rectangle, a black band, or a blank
layer that only fills in after release.

The current three-ahead/three-behind window is the minimum contract, not the
ceiling. The overhaul may widen or adapt the window, but it must stay bounded,
deduplicated and safe on slow or metered connections.

A second invariant is part of the overhaul: at rest on media `i`, the exact
`i - 1` and `i + 1` elements must already be mounted, laid out at their real
destination box and painted — not merely decoded. Dragging must reveal a
pre-painted neighbour; it must not create, fetch, decode or paint one.

## Reported behaviour

- Preloading is faster than before, but swiping still shows "a black thing
  emerging" before the destination image appears.
- The effect is most visible on the first fast swipe after landing and on
  repeated flicks.
- The destination eventually appears, so this is a readiness/paint problem,
  not a broken URL.
- The expectation is that a preloaded image is already there under the finger,
  not merely downloaded by the time the finger lifts.

## Current implementation and findings

- `PRELOAD_RADIUS = 3` and `PRELOAD_MAX = 6` define the in-post window;
  `PRELOAD_TOTAL_MAX = 12` adds bounded adjacent-post edge images.
- `warmPreloadWindow()` creates detached `new Image()` loaders, sets `src`,
  waits for `load`, then calls `decode()`. Detached images can be decode-ready
  without having been painted, and `createMediaElement()` later promotes the
  element with `opacity: 1`.
- `beginSwipePreview()` creates the preview layer and immediately sets
  `opacity: 1`, then appends it. If the element has not painted, the black
  `.viewer-media-el` background shows as a black rectangle emerging under the
  finger.
- The preview path can fall back to a fresh element when no decoded entry
  exists. That starts a network request during the gesture, which is exactly
  what preloading is supposed to prevent.
- The preload map, payload cache and post-boundary edge plan are separate
  structures. The same URL can be requested more than once and ownership of a
  promoted element is implicit.
- `preloadEpoch` is incremented but never checked by the async preload
  callbacks. There is no effective generation or cancellation for detached
  image work.
- `prunePreloadMap()` marks entries stale but leaves callbacks, decode promises
  and element references alive until they settle.
- The plan order is "all in-post, then adjacent edges". It is not a true
  urgency order, so a boundary destination can be queued behind deeper in-post
  work.
- `mediaReady` delays the first window until the current media has loaded.
  That protects the visible request, but it can also leave the first swipe cold.
- Only still images are warmed. Video posters are not, so a mixed post still
  produces a cold black frame when crossing into a video.
- `PRELOAD_TOTAL_MAX` bounds count, but not the number of live DOM/compositing
  layers, listeners, timers or decode promises.

## Scope

### A. Make "preloaded" mean paint-ready

- [ ] Define a preload entry state machine at minimum:
      `queued → requested → loaded → decoded → painted → promoted`, with
      `failed` and `cancelled` terminal states.
- [ ] A destination counts as preloaded only when its element has:
      - a valid source,
      - completed load,
      - completed decode where supported,
      - its final intrinsic/aspect box known,
      - been laid out at the destination size,
      - and produced at least one painted frame (for example by keeping the
        exact element in a hidden, rendered warm bench until promotion, or by
        an equivalent verified paint step).
- [ ] Keep the exact warmed element and promote it by moving it into the media
      host. Do not create a second element for the same URL on the commit path.
- [ ] If a browser cannot prove paint readiness, degrade deliberately: show a
      thumbnail/poster or a neutral placeholder, never a black layer.
- [ ] Set the destination's visible width/height before it is shown. No layout
      correction is allowed to move the image after the gesture starts.

### B. One bounded preload service

- [ ] Replace the separate detached-image map, adjacent-post edge list and
      payload media with one URL-keyed cache that records:
      element, item, source (`in-post`, `adjacent-previous`, `adjacent-next`),
      state, priority, owning post, generation and failure.
- [ ] Deduplicate by URL. One URL has one element, one request and one decode
      path at a time.
- [ ] Promote, demote and release through explicit ownership rules. A promoted
      entry must not be cleared or pruned by a later window update.
- [ ] Bound both entry count and live-node count. The hard floor is the
      three-before/three-after in-post window; the overall bound must not grow
      without limit.
- [ ] Include video posters as still-image preload entries so mixed posts do
      not open on a black video frame. Do not preload video bytes.

### C. Predictive but bounded scheduling

- [ ] Keep the active/committed media at browser-default or high priority.
- [ ] Warm the immediate previous and next destinations before deeper entries.
- [ ] Use a priority queue with a clear order:
      1. current media;
      2. immediate next/previous;
      3. remaining in-post window in the direction of travel;
      4. adjacent-post edge images in the direction of travel;
      5. the opposite direction and deeper background work.
- [ ] Start the rolling window as soon as the viewer state is installed, not
      only after the current media's `load`. Protect the active request through
      priority rather than serialising all preload behind it.
- [ ] Maintain the new window immediately after every commit, without waiting
      for the incoming image's load event.
- [ ] Do not cancel already-started useful loads when the index moves. Cancel
      only queued work that is no longer useful.
- [ ] Optionally widen the window adaptively after observed fast swipes, up to
      a hard cap (recommended cap: five before/five after, or a documented
      equivalent). Adapt to swipe pace, not to arbitrary timers.
- [ ] Keep the current data-saver, 2G, reduced-data, hidden-tab and
      non-image exclusions. Add poster requests to the same policy.
- [ ] A failed preload must not block navigation or retry continuously. Fall
      back once to the on-demand path.

### D. Gesture integration

- [ ] The drag preview must use a paint-ready preloaded entry whenever the
      destination is eligible.
- [ ] The preview must not become opaque before it has its first painted frame.
      If the entry is not paint-ready, use the placeholder/thumbnail path, not
      a black element.
- [ ] Keep the T8.12 layer contract: at most one active layer, one incoming
      layer and one temporary preview; hidden warm layers must not live in the
      media host.
- [ ] Commit must promote the same element without restarting from a centred
      layer, re-fetching or re-decoding.
- [ ] Preserve axis lock, rubber-banding, tap zones, transition geometry and
      reduced-motion behaviour.

### E. Lifecycle and observability

- [ ] Add a generation/epoch check to every async preload callback, decode
      promise and paint check. Stale work must not mutate the current map.
- [ ] Clear timers, listeners, decode promises and node references on viewer
      cleanup and on post changes. Do not leak detached media or warm DOM.
- [ ] Keep memory bounded under repeated forward/backward swipes and mixed
      posts (coordinate with T6.5).
- [ ] In debug mode, expose counts for: warm entries by state, live warm nodes,
      cache hits/misses, duplicate requests, promotions, failures, paint
      readiness and window width.
- [ ] Add `performance.mark`/`measure` integration or equivalent debug timing
      so the browser acceptance pass can prove that a destination request
      started before the gesture and was not repeated on commit.

### F. Paint-warm the direct neighbours (triple-buffer)

The direct neighbours are the ones a drag can reveal first, so they get a
stronger guarantee than the rest of the preload window: they are not just
warm entries, they are a mounted three-image ring.

- [ ] Maintain a three-slot ring: `active`, `previous (i - 1)` and
      `next (i + 1)` from the current filtered playlist.
- [ ] Both neighbour slots must be created from the same URL-keyed cache entry
      that will be promoted later. One node per URL, no duplicate copies.
- [ ] Neighbours must be laid out at the exact media box and neighbour offset
      the drag geometry will use, with intrinsic `width`/`height` applied. No
      late size or position correction is allowed when the gesture begins.
- [ ] Neighbours must be genuinely painted before input. `decode()` alone is
      not enough. Do not use `display: none` or `content-visibility: hidden` if
      that causes the browser to skip rasterisation; verify with a first-frame
      screenshot.
- [ ] Keep the paint buffer inert: no pointer input, no focus, no accessibility
      exposure, no playback, no tap zones. It must not interfere with the active
      layer or the T8.12 swipe state machine.
- [ ] Keep the paint buffer outside `[data-viewer-media]` so the media host
      still contains only the active, incoming and temporary preview layers
      from T8.12. If a different container is proposed, update T8.12 explicitly
      and prove that swipes cannot stick.
- [ ] On drag axis lock, the first painted frame must use the already-painted
      neighbour node. Promotion/commit must move or re-role that same node
      without clearing `src`, refetching, re-decoding, or resetting its visual
      box.
- [ ] After commit, shift the ring by one: the old active becomes the new
      previous where still useful, the old next becomes the active, and a new
      next is warmed. Do not rebuild all three nodes on every swipe.
- [ ] The ring must cross a post boundary when the filtered playlist does:
      `i - 1` may be the last matching item of the previous post and `i + 1`
      the first matching item of the next. Use the T8.19 context so the ring
      never contains filtered-out media.
- [ ] For a video neighbour, paint its poster (T8.17) in the ring; do not
      preload video bytes. For a GIF, paint the first frame/poster rather than
      starting animation in the buffer.
- [ ] Bound the stronger guarantee to these two neighbours only. Deeper window
      entries remain fetch/decode-warm or thumbnail-prepared; do not mount the
      whole window.
- [ ] Guard memory: only two full adjacent images may be mounted at once. On
      low-memory, data-saver, very large-image or capped-network conditions,
      paint a correctly sized thumbnail/placeholder in the ring and upgrade to
      the full image before it becomes active if policy allows. No black slot.
- [ ] If a neighbour is not paint-warm when the gesture starts, degrade to the
      existing placeholder/thumbnail path and keep the swipe responsive. Never
      block the gesture waiting for the ring.
- [ ] A ring slot must be replaced or released when the current item changes,
      the filter context changes, the viewer closes, or a jump aborts. Stale
      ring nodes must not survive into the new playlist.

## Tests

- [ ] Pure Node tests for the window planner: three-before/three-after floor,
      edge clamping, direction weighting, adaptive widening and hard cap.
- [ ] Pure Node tests for the priority queue: immediate neighbours beat deeper
      in-post entries, which beat adjacent-post edges.
- [ ] State-machine tests: queued, requested, loaded, decoded, painted,
      promoted, failed and cancelled transitions, including stale generations.
- [ ] Test that a promoted entry is never pruned/cleared by a later window
      update.
- [ ] Test that moving from `i` to `i + 1` keeps already-started entries that
      are still useful and cancels only queued stale work.
- [ ] Test that a failed or decode-rejected entry falls back once and does not
      enter a retry loop.
- [ ] Test that a video poster can be warmed and used as a placeholder without
      requesting video bytes.
- [ ] Static/DOM test: the preview layer is not made opaque with a black
      background before it is paint-ready.
- [ ] Static test: warm elements live outside the media host and the host still
      contains at most the active, incoming and preview layers.
- [ ] Ring test: on index `i` the paint buffer contains exactly `i - 1` and
      `i + 1` from the filtered playlist, with clamping at the post/archive
      edges and cross-post neighbours at a boundary.
- [ ] Ring test: committing `i + 1` promotes the exact existing next node and
      shifts `previous/active/next` without creating a second node or clearing
      `src`.
- [ ] Ring test: the buffer slots are inert (`aria-hidden`/`inert`,
      `pointer-events: none`, no autoplay) and are not inside the media host.
- [ ] Ring test: filtered-out media never enters the ring; changing context
      releases the old ring nodes.
- [ ] Ring test: an unavailable/failed neighbour cannot leave a black paint
      slot; it falls back to the thumbnail/placeholder path.
- [ ] Keep T8.12's drag harness green: no first-frame layout jump, no black
      band and no horizontal movement for vertical drags.
- [ ] Browser acceptance in Chromium/Firefox desktop and Android Chrome touch:
      - land on a middle image and verify the eligible window is requested and
        decoded before any swipe;
      - verify at rest that the exact `i - 1` and `i + 1` elements are already
        mounted, sized and painted (screenshot/inspect, not just `decode()`);
      - perform a fast flick immediately after landing and verify the first
        painted drag frame contains destination pixels, not black, and that no
        new request or decode starts for the direct neighbour;
      - repeat at least 20 fast flicks and verify the ring shifts rather than
        rebuilding, no destination request starts after the gesture for warmed
        items, no duplicate requests and no re-decode on commit;
      - cross a post boundary in both directions and verify the ring already
        holds the matching edge item/poster from the adjacent post;
      - swipe into a video and verify its poster is already present; swipe into
        a GIF and verify it is not animating in the paint buffer;
      - switch from Images to Videos context and verify the ring is rebuilt from
        the new filtered playlist;
      - throttle to slow 3G, verify safe placeholder behaviour, no permanent
        hang and no broken layout;
      - verify data saver, 2G/reduced-data and hidden-tab modes start no
        background image/poster work;
      - after repeated swipes, verify warm nodes, listeners and memory stay
        bounded.

## Acceptance criteria

- [ ] "Preloaded" means fetch-complete, decoded, correctly sized and
      paint-ready, not merely requested.
- [ ] A fast swipe to a warmed image shows the destination from the first
      painted drag frame. No black rectangle or black band emerges.
- [ ] The image box does not move or resize after the gesture starts.
- [ ] The immediate next/previous destinations are warmed before deeper work,
      including across a post boundary.
- [ ] At rest on item `i`, the exact `i - 1` and `i + 1` elements are already
      mounted, sized and painted — not merely downloaded or decoded.
- [ ] The first drag frame uses the pre-painted neighbour: no new request, no
      decode, no blank frame and no black buffer slot.
- [ ] Committing a swipe promotes the same painted node and shifts the ring by
      one; repeated swipes do not rebuild all three slots.
- [ ] The paint buffer stays exactly two neighbours, inert and outside the
      media host, and is rebuilt from the filtered playlist (T8.19).
- [ ] The paint buffer does not increase unbounded memory or break the T8.12
      swipe/layer contract.
- [ ] Repeated swipes keep the window warm with no duplicate requests, no
      duplicate decodes and bounded memory.
- [ ] Video posters are warmed where policy allows; video bytes are not.
- [ ] Slow networks and failures degrade to a deliberate placeholder or the
      existing safe on-demand path, never a black permanent layer.
- [ ] Existing swipe, transition, fullscreen, bookmark, filter and accessibility
      behaviour is unchanged.
- [ ] No service worker, disk cache, new dependency or custom HTTP cache policy.

## Out of scope

- Downloading video bytes or preloading full playback.
- Service workers, persistent storage or offline mode.
- Machine-learned or velocity-perfect prediction; adaptive widening must stay
  simple and bounded.
- Replacing the T8.12 two-layer transition geometry.
- Viewer filter context (T8.19) and terminal video/black-image rendering bugs
  (T8.17), except where the new pipeline must not regress them.

## Notes

- A detached `Image` can be `decode()`-complete without ever having been
  painted. The overhaul exists specifically to close that gap.
- Preload cost is connection-bound: warming six images is not free. The
  priority queue and adaptive cap are the trade-off controls, not a reason to
  keep detached loaders.
- The black `.viewer-media-el` background is useful behind video letterboxing
  but makes an unpainted `<img>` look like a rendering bug. Placeholders should
  be explicit.
- Measure readiness in the browser. Timer tuning alone cannot prove that the
  first painted drag frame is correct.
- The three-image ring is a triple buffer, not a full carousel. Only `i - 1`
  and `i + 1` get the stronger painted guarantee because they are the only
  destinations a single gesture can reveal. Deeper entries stay bounded and
  decode-warm.
- "Painted" is the hard part. `decode()` can resolve while the element is still
  outside the render tree, and `display: none`/`content-visibility: hidden` can
  make the browser skip rasterisation entirely. The acceptance pass must prove
  the first drag frame visually, not just inspect state.
- Moving a painted node between containers can still trigger a repaint. The
  implementation must either promote the node without clearing `src`/box and
  verify no blank frame, or keep the ring as the permanent render surface.
- Two extra full-size decoded images are a real memory cost on mobile. The ring
  is the place to use a correctly sized thumbnail as the painted fallback for
  oversized images or constrained devices; the invariant is "never black", not
  "always full resolution".
