# T8.11 — Smooth finger-following swipes and remove click zones

## Goal

Make the viewer's touch navigation feel continuous in both axes. Today the
drag preview jumps, leaves a black gap beside the finger, and vertical swipes
can lock onto the horizontal axis. The result is not the Instagram/X-style
paging the gesture is supposed to imitate.

This ticket also removes the four invisible click regions (`prev-image`,
`next-image`, `prev-post`, `next-post`). Navigation stays on swipe, arrow keys,
mouse wheel, and the viewer's explicit controls.

Vertical swipe direction is fixed: **swiping down goes to the older post, and
swiping up goes to the newer post**. This matches the existing ArrowDown/ArrowUp
semantics and must not be inverted by the new gesture work.

The fix is not a small threshold tweak: it needs a short implementation study
of how Instagram carousels/X media paging and Reels vertical paging keep the
current and incoming media glued together while the finger moves.

## Reported symptoms

- Starting a horizontal swipe turns the visible image into a strip that follows
  the finger while the rest of the stage is black. The adjacent image is not
  attached to the edge of the current image.
- The preview jumps on touch/drag start instead of appearing already at the
  correct edge.
- Vertical swipes have the same black-gap/jump problem.
- A vertical drag can lock to the horizontal axis and slide sideways, even
  though the destination post should arrive from above/below.
- The invisible left/right/up/down click regions still navigate on tap. These
  regions should be deleted rather than fixed.

## Current behaviour (root causes to verify)

- `viewer.js` `beginSwipePreview()` appends the preview layer before any
  transform is applied. The first `requestAnimationFrame` positions it, so for
  one frame the preview is centred on top of the current media and then snaps
  to the edge.
- Drag offsets use `stageSize()` (the whole viewport) rather than the current
  media element's rendered box. When an image is letterboxed, translating the
  preview by a full stage width leaves a large black gap between the current
  image's edge and the incoming image.
- Both layers are independently centred in the flex host and moved with
  `translate3d`. There is no shared track/pager geometry, so "adjacent" is only
  correct when the media happens to fill the stage exactly.
- Axis lock happens at 9 px using the raw delta at that instant. Diagonal or
  slightly jittery vertical gestures can lock `x` before the vertical motion
  dominates. The axis then never changes for the rest of the gesture.
- Horizontal and vertical previews share one positioning path; the vertical
  case is not verified to keep the incoming layer above/below the current
  media box.
- The four `.viewer-zone` buttons, their click handler, their CSS, and the
  bottom-zone video adjustment still exist from T8.3.

## Research before coding

Spend a short, time-boxed pass documenting how the reference experiences behave,
then write the findings into this ticket before implementing:

- Instagram carousel/media viewer: horizontal paging within a post, edge
  resistance at the first/last item, how the next page is pinned to the current
  page, snap/velocity behaviour, and how letterboxed media is handled.
- X media viewer: horizontal image paging, how the viewer avoids diagonal axis
  ambiguity, and what happens at the first/last image.
- Instagram Reels / X-style vertical paging: one full-screen page per post,
  vertical-only snapping, direction of travel, and how a slight diagonal
  gesture is kept on the intended axis.
- Identify whether the reference uses a single translated track with page-sized
  children, CSS scroll-snap, or two independently translated layers. Note the
  trade-offs for this viewer (no new dependency, at most two live media
  elements, existing T8.9 transition hand-off).

Record concrete conclusions and any measurements (slop, commit distance,
velocity, spring duration) in the Notes section of this ticket. The goal is a
deliberate gesture model, not copied magic numbers.

### Research findings (reference behaviour, time-boxed pass)

**Instagram carousel / X media viewer (horizontal paging)**

- Both are **one pager with page-sized neighbours**, not two independently
  centred layers. The incoming page is the direct neighbour of the outgoing
  page in the pager's own coordinate system, so it is always attached to the
  outgoing page's edge: the page is revealed by the drag, never re-positioned
  after the drag starts. That is the mechanism behind the "glued together"
  look, and it is exactly what the reported black gap loses.
- The pager is clipped to the viewport and the page advances by one **page**,
  not by the size of the photo. Letterboxed photos are fitted *inside* their
  page (`contain`) and the page background continues behind them, so the black
  band belongs to the page and never appears *between* two pages.
- At the first/last item the pager **resists** (rubber band) and does not
  wrap; X's media viewer and Instagram's carousel both stop with resistance.
- A release either completes the page or springs back. Velocity is sampled
  over the last ~100 ms, so a slow start followed by a flick still commits
  and a pause before lifting kills the flick.
- X's media viewer is horizontal only; the ambiguity between the two axes is
  removed by a direction lock, not by a bigger threshold.

**Reels / X-style vertical paging**

- One full-screen **page per post**, vertical-only snapping, one page per
  gesture, no inertia through several pages. The dragged page follows the
  finger 1:1 and the next page is its neighbour on the same axis.
- A slightly diagonal gesture stays on the intended axis. The iOS reference
  (`UIScrollView.isDirectionalLockEnabled`) locks the axis once the drag
  commits to a general direction, and a *truly* diagonal drag is **not**
  locked until the intent is clear — the smaller axis stays live in the
  meantime instead of being guessed from the first few pixels.
- The feed's own direction mapping is a product choice, not a mechanic: this
  viewer keeps **down = older post, up = newer post** to match ArrowDown and
  ArrowUp.

**Model chosen for this viewer**

- Keep the **two-layer hand-off** (no dependency, at most two media elements,
  T8.9's commit hand-off intact) but express it as a pager: both layers stay
  centred in the flex host, so the centre-to-centre distance for a flush
  join is `(currentWidth + incomingWidth) / 2` horizontally and the same with
  heights vertically. That half-sum is the "page step" of a track pager,
  measured in **media pixels** instead of stage pixels.
- A single CSS scroll-snap track was rejected: it would need the host to
  become a scroll container with page-sized children, which breaks the
  two-layer cap, the post-boundary fetch hand-off and the video/GIF
  cross-fade path for no visible gain.
- **Alignment rule (documented):** the two visible media boxes are joined
  edge to edge along the drag axis; each keeps its own aspect ratio, nothing
  is stretched or overlapped, and the shared black stage background stays
  continuous. If the two media have different rendered sizes, the step is
  still the half-sum, so the join stays flush.

### Gesture constants (final)

| Constant | Value | Meaning |
|---|---|---|
| `SWIPE_SLOP` | 9 px | movement before an axis may be chosen |
| `SWIPE_AXIS_DOMINANCE` | 1.2 | the leading axis must be 20% longer than the other |
| `SWIPE_AXIS_FALLBACK` | 24 px | a still-ambiguous diagonal locks here, to the larger delta |
| `SWIPE_TERMINAL_RATIO` | 0.18 | commit distance as a share of the **media** dimension |
| `SWIPE_TERMINAL_MAX` | 96 px | absolute commit distance cap (unchanged from T8.10) |
| `SWIPE_VELOCITY` | 0.45 px/ms | flick threshold (unchanged from T8.10) |
| `SWIPE_RUBBER_BAND` | 0.25 | edge resistance (unchanged from T8.10) |

The commit policy itself is unchanged from T8.10; only the **dimension** it
measures against changed, from the stage to the visible media box.

### Implementation notes

- The active layer is measured **once per gesture** (`getBoundingClientRect()`
  at `pointerdown`) and that box drives the drag offsets, the preview
  placement and the commit threshold. The stage size is only a fallback for a
  stage without a media layer.
- The preview is positioned **before it joins the host**, in the same task
  that locks the axis, so the first painted frame is already flush. Its
  visible box comes from the payload's `width`/`height` through the same fit
  the stylesheet applies (`contain` inside the host box); a late decode that
  reports a different size corrects the shared step once, with no timer.
- Bug found while doing this: the **server-rendered first layer had no
  `__viewerItem`**, so the first image of a post never moved with the finger
  and never produced a preview. The layer now adopts the current item on
  start-up.
- The preview is still only created for **image** destinations (T8.10
  behaviour): videos and GIFs keep their native controls and cross-fade.

### Other notes

- The likely minimal fix is still a two-layer hand-off, but both layers must be
  positioned from the **measured media box**, not the stage. If the research
  shows a track/pager is materially smoother, a single track with page-sized
  children may replace the two-layer drag path while keeping T8.9's commit
  hand-off and layer cap.
- Do not mix stage-sized translations with media-sized previews: that mismatch
  is the most likely source of the reported black gap.
- Check the very first pointer frame: the preview must be positioned before it
  is painted, not on the next rAF.
- Keep the existing post fetch and T8.8 payload cache untouched; the gesture
  still must not fetch merely to preview.
- Direction invariant for this viewer: **down = older post, up = newer post**.
  Reference apps may use a different feed orientation; copy their mechanics,
  not their direction mapping. Add an explicit assertion/test so a future
  refactor cannot silently invert it.
  **Superseded by T8.12:** the vertical axis now follows the finger, so
  **up = older post** and **down = newer post** for the swipe, the arrow keys
  and the wheel. The T8.11 invariant above is kept only as the record of what
  this ticket shipped.
- The Chromium/Firefox/phone pass in the Tests section is still manual; the
  automated coverage is the pure-helper Node tests plus a fake-DOM harness
  (`tests/fixtures/viewer_drag_harness.js`) that drives the real `viewer.js`
  through a horizontal drag, a vertical drag, a diagonal drag, jitter and an
