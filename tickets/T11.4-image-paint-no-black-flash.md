# T11.4 — Remove the first-forward black flash when an image appears

## Goal

Eliminate the black frame shown the **first time** the viewer moves forward to
an image. Going back to an already-seen image is clean today, which points at
the swap/paint path rather than network caching alone. The fix must paint the
next image before the current one is removed, using decode-aware preloading and
a double-buffered stage.

## Locked decisions (2026-10-22)

| Question | Decision |
|---|---|
| Implementation target | `static/lightbox.js` after T11.1. Do not modify the old `viewer.js`; T11.1 deletes it. |
| Browser caching depth | HTTP cache + retained/decoded `HTMLImageElement`s only. No service worker, no Cache API, no IndexedDB blobs, no media archive. |
| Decoded bitmap budget | At most 3: current, next, previous. Deeper neighbours stay HTTP-cache-warm but are not `decode()`d. Drop to 2 when `navigator.deviceMemory <= 4` is available and low. |
| Slow/failed load | The outgoing image stays fully visible until the incoming image is decoded. No dim, spinner or thumbnail placeholder. |
| Transition | Instant layer swap. No crossfade; T8.9 owns viewer transitions. |

The browser's normal HTTP cache and in-memory decoded bitmaps are expected and
in scope. "Downloading or caching media to disk" in Out of scope means Monoke
must not build a persistent media store; it does not forbid preloading.

## Observed behaviour

- Surface: merged lightbox-viewer in fullscreen (old viewer path reproduced it
  too).
- Trigger: first forward navigation to an image. The stage goes black, then the
  image appears.
- Returning to that image (or navigating back) shows it immediately with no
  flash.
- Browser/OS: Chromium and Firefox on Linux; confirm the same on the target
  mobile browser.
- Videos are not part of the reported bug, but must not regress.

## Why it happens (working hypothesis)

The current controller calls `unloadMedia()` before building the next element:

1. `unloadMedia()` clears `src`, calls `load()` and `replaceChildren()`, so the
   stage has no painted content.
2. A fresh `<img>` is created with `decoding="async"` and `src`, then appended.
3. The browser paints the empty stage while that new element decodes.
4. The preload `Image` object in `preloadMap` is never explicitly decoded or
   reused as the painted element, so the new DOM element still has to
   decode/paint.
5. On a return visit, the browser has already decoded and cached the bitmap for
   that URL, so the new element paints in its first frame.

Preloading alone is therefore not enough: the swap is not gated on the visible
element being ready to paint.

## Scope

**Paint-ready navigation**

- [ ] Introduce a double-buffered stage: the outgoing media layer stays visible
      while the incoming layer loads and decodes; only then swap layers and
      remove the outgoing one.
- [ ] For images/GIFs, wait for `img.decode()` when available (fallback:
      `load` + `requestAnimationFrame`), then swap on a second animation frame.
      Never expose a blank stage between items.
- [ ] Never insert an undecoded `<img>`: wait for its `decode()` before it
      becomes visible, then use `decoding="sync"` (or omit `async`) on the
      final visible element. `decoding="sync"` is a hint, not a substitute for
      `decode()`. Keep `loading="eager"` for the visible item; never lazy-load
      it.
- [ ] Keep at most three decoded bitmaps alive (current, next, previous).
      Deeper neighbours stay HTTP-cache-warm only and are not `decode()`d.
      Drop to two when `navigator.deviceMemory <= 4` is available and low.
- [ ] Reuse the exact preloaded `HTMLImageElement` as the incoming layer, not
      just its URL. Store `{ image, decoded }` in the preload map, rewire its
      handlers and viewer attributes on promotion, and keep the reference alive
      until the swap. If a second element is unavoidable, `decode()` it before
      the swap.
- [ ] Warm the **first forward neighbour** immediately when the overlay opens,
      not only after `load` of the current media. Start its low-priority fetch
      and `decode()` at boot, before the first idle callback; queue it
      alongside the current image request while still yielding to the visible
      item if the connection is constrained.
- [ ] Keep the reduced-data / save-data / 2G guard: when preloading is disabled,
      navigation still works and never blanks the stage; it simply waits for the
      incoming image to decode before swapping.
- [ ] On decode/load failure, fall back to the existing unavailable state or
      paint the next item without leaving the stage permanently black.
- [ ] Videos keep native `preload="metadata"`, poster and controls; do not make
      them wait on image decode.
- [ ] Preserve the `data-lightbox-video`/`data-lightbox-image` hooks, keyboard
      shortcuts, focus return and URL/counter updates.
- [ ] Do not add a visible fade transition as the fix; a crossfade is optional
      polish, not a substitute for decoded paint.

**Preload policy**

- [ ] Review the existing `PRELOAD_RADIUS` / `PRELOAD_TOTAL_MAX` budgets and the
      idle scheduling. The next item and the first edge item of the next post
      must be in the eager tier; deeper neighbours stay idle.
- [ ] Cache-busting, if added, must not defeat the browser cache. Prefer the
      same URL so the HTTP cache and decoded bitmap are reusable.
- [ ] Log nothing to the console in normal operation. Debug mode may record
      preload/decode timings.

**Tests**

- [ ] Extract the swap decision into a pure helper (e.g. `shouldSwapLayers`,
      `nextPaintPlan`) with `// BEGIN/END` markers and a Node test, matching the
      existing `preload-window` pattern.
- [ ] JS source test: `unloadMedia()`/`replaceChildren()` is not called on the
      visible layer before the incoming image is prepared; the visible image is
      not `decoding="async"`.
- [ ] JS source test: the first forward neighbour is in the eager preload plan
      at overlay open.
- [ ] Node/source test: the decoded set is capped at the active budget (3, or 2
      on low-memory devices) and a preloaded element is promoted rather than
      recreated by `render()`.
- [ ] Failure test: a rejected `decode()` does not leave the stage empty and
      does not permanently block further navigation.
- [ ] `node --check src/monoke/web/static/lightbox.js` and `uv run pytest` pass.
- [ ] Browser acceptance in Chromium and Firefox, desktop at 1440 px and mobile
      emulation at 390 px:
      - open a multi-image post in the merged viewer, go forward through five
        unseen images; no black frame on the first pass;
      - go back through the same five; still clean;
      - cross into the next post forward; clean;
      - throttle to Fast 3G and confirm the current image never disappears
        before the next one is ready;
      - disabled-JS and unavailable-media states still render.

## Acceptance criteria

- [ ] First forward navigation to an image does not show a black frame in the
      merged viewer in Chromium or Firefox.
- [ ] The outgoing image remains visible until the incoming image is decoded
      and ready to paint.
- [ ] Preloading/decode budgets remain bounded; save-data and slow connections
      are respected.
- [ ] Videos, bookmarks, post crossing, fullscreen and hide controls are
      unchanged.
- [ ] A failed image shows the unavailable state instead of a stuck black stage.

## Out of scope

- Swipe/gesture transitions and stacked media layers (old T8.11–T8.19 work).
- Filter-aware or manifest-based preloading.
- Persistent media storage by Monoke: service worker/Cache API, IndexedDB
  blobs, or writing media files to disk. The browser's own HTTP cache and
  in-memory decoded bitmaps are not that: they are expected and in scope.
- Changing the viewer's fullscreen/controls layout (T11.1/T11.2).

## Notes

- The bug is a paint-order problem, not just a network problem: the second visit
  is fast because the bitmap is already decoded, which is exactly what the
  forward path must guarantee before the swap.
- Keep the outgoing `<img>`/`<video>` alive during the incoming decode. A
  hidden preload `Image` alone does not guarantee the DOM element can paint.
- Measure with a screen recording or DevTools performance capture, not just
  "it feels faster". The acceptance criterion is no black frame.
- "First forward neighbour" means `media[currentIndex + 1]` in the current
  post. Crossing into the next post still relies on T8.8's neighbour seeds and
  payload cache; it must not regress, but it is not this seed.
- The fix works on a cold cache too: the outgoing image stays visible while the
  incoming one downloads. Caching makes the swap instantaneous; it is not what
  removes the black frame.
