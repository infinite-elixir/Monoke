# T12.11 — Pawchive acceptance run and epic close-out

## Goal

Prove the feature on a real archive and close the epic with measured results,
not just green unit tests.

## Preconditions

- [ ] T12.1–T12.10 are done.
- [ ] A fresh data directory (`MONOKE_DATA_DIR=/tmp/monoke-acceptance`).
- [ ] Pick a pawchive creator with roughly 20–100 posts for the first run;
      avoid the 173-attachment stress post until the basic flow passes.

## Acceptance steps

1. [ ] `uv run monoke serve`; paste the pawchive creator URL.
2. [ ] First sync:
       - [ ] creator appears with `source='pawchive'`;
       - [ ] post count matches the number of distinct IDs from a manual list
             walk;
       - [ ] no unhandled 403; if blocked, the run is marked blocked and the
             app stays usable.
3. [ ] Browse:
       - [ ] creator page, post page, gallery, viewer, links and bookmarks all
             render;
       - [ ] the original post link goes to pawchive.pw;
       - [ ] caption links are extracted and classified;
       - [ ] preview-only attachments are labelled and never produce a broken
             "Load original".
4. [ ] Second sync:
       - [ ] completes in seconds and only touches new/edited posts;
       - [ ] no duplicate posts/files/links;
       - [ ] `upstream_edited_at` is populated for new posts.
5. [ ] Modify test:
       - [ ] pick one post and simulate an edit in a fixture/respx test (do not
             edit upstream); assert only that post is refetched in a local test.
6. [ ] Full/deep sync:
       - [ ] `--full` refetches all details and remains idempotent.
7. [ ] Cancellation:
       - [ ] cancel mid-sync; run row is cancelled, no half-written post bundle.
8. [ ] Missing upstream:
       - [ ] a post removed from the list walk is flagged, not deleted.
9. [ ] Same service/id on both sources:
       - [ ] archive a cum.st and a pawchive creator with the same numeric id;
             both coexist and link to the right origin.
10. [ ] Regressions:
        - [ ] existing cum.st acceptance (README definition of done) still
              passes;
        - [ ] `uv run pytest` and the opt-in live suite are green.

## Record in the close-out comment

- [ ] Creator URL/id, post count, attachment count, preview-only share.
- [ ] First-sync duration and request count; second-sync duration.
- [ ] Any 403/429 events and the pacing used.
- [ ] Known limitations confirmed in practice.
- [ ] Follow-up tickets for anything deferred (e.g. ZIP support, dimensions).

## Acceptance criteria

- [ ] A user can archive, re-sync and browse a pawchive creator without touching
      the CLI beyond `monoke serve` / `monoke sync`.
- [ ] `docs/SOURCES.md` limitations match observed behaviour.
- [ ] The board marks the epic done and the project definition of done gains the
      pawchive case.
- [ ] No cum.st behaviour regressed.

## Out of scope

- Media mirroring, ZIP unpacking, comments, DMs, importer flows.
- Hosting or authentication work from `tickets/todo.md`.
