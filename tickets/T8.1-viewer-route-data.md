# T8.1 — Fullscreen viewer route, entry point and data contract

## Goal

Add a dedicated viewer surface for one creator, starting at the newest media in
the archive, with a small server contract that can answer "give me this post's
media and its two neighbouring media posts" without loading the whole archive.

This ticket is server-side only. The fullscreen shell is T8.2, navigation is
T8.3, the first-run hint and lifecycle are T8.4.

## Decisions from the user

- Entry: a new route linked from the creator page; it opens the **latest**
  media (first media of the newest post that has media).
- Media scope: **images, real GIFs and videos**. MP4-backed `gif` rows are
  videos after T7.1.
- "Previous post" means **newer**; "next post" means **older**. The list order is
  `published DESC`, so up moves toward the newest post and down toward the
  oldest.

## Data contract

`GET /c/{creator_id}/viewer/data?post=<service_post_id>` returns:

```json
{
  "creator": {"id": 2, "name": "Belledelphine", "service": "onlyfans"},
  "post": {
    "service_id": "2183930591",
    "title": null,
    "published": 1784196537,
    "post_url": "/c/2/p/2183930591",
    "media_count": 5
  },
  "media": [
    {
      "index": 0,
      "sha256": "81e1…",
      "kind": "video",
      "mime_type": "video/mp4",
      "width": 1080,
      "height": 1920,
      "duration_ms": 10000,
      "bytes": 8166926,
      "url": "https://e3.cum.st/media/81e1…/original.mp4",
      "thumb_url": "https://img.cum.st/thumbnail/81e1…/preview.webp",
      "variants": [{"name": "original.mp4", "url": "…", "bytes": 8166926}],
      "post_service_id": "2183930591",
      "post_position": 0
    }
  ],
  "previous_post": "2239074677",
  "next_post": null
}
```

- `media` is ordered by `files.position ASC, files.id ASC`.
- `previous_post` = closest post with media that is **newer** (higher
  `published`, then higher post id).
- `next_post` = closest post with media that is **older** (lower `published`,
  then lower post id).
- Adjacent-post lookups must skip posts with no eligible media; text-only posts
  must never become a destination.
- No global `sha256` dedupe here. The same image attached to two posts appears
  in both, because navigation is post-scoped. Within a post, `files` already has
  `UNIQUE(post_id, sha256)`.

## Scope

**Repository (`db.py`)**

- [ ] Add `VIEWER_KINDS = ('image', 'gif', 'video')` next to
      `GALLERY_KINDS`; use one source of truth.
- [ ] `latest_viewer_post(conn, creator_id) -> dict | None`: newest post with at
      least one eligible file (`ORDER BY published DESC, id DESC LIMIT 1`).
- [ ] `viewer_media(conn, creator_id, post_service_id) -> list[dict]`: files for
      one post, joined to its post row, eligible kinds only, ordered by
      `position, id`. Return `variants` parsed from `variants_json` so the
      template/JSON does not re-parse it.
- [ ] `viewer_neighbour(conn, creator_id, post, direction) -> str | None`:
      `direction` is `newer` or `older`; return the neighbouring
      `posts.service_id` that has eligible media.
- [ ] `viewer_state(conn, creator_id, post_service_id=None) -> dict | None`:
      assembles the payload above. Without a post id it uses the latest post.
      Returns `None` for an unknown post or a post with no eligible media.
- [ ] Use `EXISTS (SELECT 1 FROM files f WHERE f.post_id = p.id AND f.kind IN …)`
      and the existing `files_kind (kind, post_id)` index. Confirm with
      `EXPLAIN QUERY PLAN` that neighbour lookups do not scan all `files`.

**Routes (`web/routes.py`)**

- [ ] `GET /c/{creator_id}/viewer` — render `viewer.html` with the initial
      state embedded as JSON. Default = latest media. Accept `?post=<service_id>`
      and `?i=<index>` so a refresh or bookmark restores the exact item; clamp
      an out-of-range index to the post's first/last item.
- [ ] `GET /c/{creator_id}/viewer/data` — same state as JSON for client-side
      post jumps. Unknown creator → 404; unknown post or post without media →
      404 with a JSON error (the JS shows a flash and stays put).
- [ ] Never send all 19k files in one response. The initial response carries
      only the current post's media (typically 1–40 items).
- [ ] Mark the viewer page `active_page="creators"`, include creator name and a
      return URL (`/c/{id}` by default, `?from=gallery` → `/c/{id}/gallery`).

**Entry points**

- [ ] Creator header: add a `View latest` button next to `Gallery` and `Sync`.
- [ ] Gallery header: add an `Open viewer` button pointing at the creator's
      latest media. Existing tile lightbox stays unchanged.
- [ ] The button must be a plain `<a href>`; no JavaScript required to enter.

**Tests**

- [ ] Default route on a seeded creator opens the newest post's first media.
- [ ] `?post=` opens that post; `?i=` selects the right item; a too-large `i`
      clamps; a post with no media 404s.
- [ ] Neighbour lookup skips text-only posts in both directions.
- [ ] Newer/older mapping matches `published DESC` with id tie-breaking.
- [ ] The JSON payload has all fields above and parses `variants`.
- [ ] Dedupe is not applied across posts; the same sha in two posts appears in
      both.
- [ ] Unknown creator 404s on both routes.
- [ ] Existing creator/gallery tests stay green.

## Acceptance criteria

- [ ] `/c/2/viewer` starts on the newest media post for creator 2 (at the time
      of writing, post `2243257662`, first image).
- [ ] `previous_post` at the newest media post is `null`; `next_post` is the
      next older media post. At the oldest, the reverse.
- [ ] On creator 2, `?post=` requests return only that post's media and never
      more than that post's file count.
- [ ] A creator with zero eligible media gets a clear empty state on `/viewer`,
      not a 500.
- [ ] The initial viewer HTML contains exactly one post's media, not the whole
      archive.
- [ ] No media bytes are downloaded by the route; only URLs are built.

## Out of scope

- The fullscreen shell, media element rendering and Fullscreen API (T8.2).
- Click zones, keyboard, wheel and swipe navigation (T8.3).
- The first-run hint, focus trap and close lifecycle (T8.4).
- Caption images and cross-creator viewers.

## Notes

- `files.url` is already the deterministic `original.<ext>` edge URL; do not
  rebuild it in the viewer. T7.1 guarantees video-backed gifs have
  `kind='video'`.
- `published` can be null in theory. Sort with `COALESCE(p.published, 0)` to
  match the rest of `db.py`.
- The viewer is read-only and never writes to `files`, `posts` or `runs`.

## Resolution

Shipped server-side first, exactly as specified: `VIEWER_KINDS` is now the single
source of truth (`GALLERY_KINDS` aliases it), and the four repository functions
return post-scoped dicts with parsed variants.

**Code**

| File | Change |
|---|---|
| `src/monoke/db.py` | `VIEWER_KINDS`, `latest_viewer_post`, `viewer_media`, `viewer_neighbour`, `viewer_state` |
| `src/monoke/web/routes.py` | `GET /c/{id}/viewer` (HTML + embedded state, `?post`, `?i`, `?from`) and `GET /c/{id}/viewer/data` (JSON, JSON 404s) |
| `src/monoke/web/templates/viewer.html` | viewer shell, initial media, four direction zones, JSON state block |
| `src/monoke/web/templates/creator.html`, `gallery.html` | `View latest` / `Open viewer` plain links |
| `tests/test_viewer.py` | default entry, `?post`/`?i` clamping, empty/404 states, payload contract, variants, neighbour chain and tie-breaking, cross-post no-dedupe, ordering |

`EXPLAIN QUERY PLAN` for the neighbour lookup uses the covering
`files_kind (kind, post_id)` index rather than scanning `files`:

```text
SEARCH f EXISTS USING COVERING INDEX files_kind (kind=? AND post_id=?)
```

A creator with no eligible media renders `No media in this archive`; an explicit
`?post=` that is unknown or has no media returns 404. Media bytes are never
fetched by either route.
