# T7.0 — Audit: onlyfans/39058172 has files but no visible videos

## Goal

Explain why the synced archive for `https://cum.st/creators/onlyfans/39058172`
(creator row `id=2`) contains 756 videos but the profile-level UI never shows
them, and identify every place where attachment types are wrong or invisible.

This ticket records evidence only. Fixes are T7.1–T7.5.

## Evidence (collected 2026-10-21 against `data/monoke.db`)

### The crawl is complete and the videos are in SQLite

```text
posts (creator 2):            1033
files (creator 2):         19139
  image / image/jpeg      18380
  video / video/mp4         756
  gif   / image/gif           3
posts with an image:        918
posts with a video:         264
```

Upstream agrees: the live list endpoint returns `total: 1033`; post details
carry `kind: "video"` with `mimeType: "video/mp4"`. Example post
`2183930591` has five videos, and its Monoke page renders five
`data-kind="video"` attachment rows. **The crawler did not lose anything.**

### Why the profile "shows no videos"

1. `/c/2` is a post list only. A card shows `N links` and `N files`; it never
   says whether those files are images, videos or audio.
2. The only visual browser, `/c/2/gallery`, hard-codes
   `f.kind IN ('image', 'gif')` in `db._gallery_where`. Videos are excluded by
   design (T4.7 listed "video tiles" as out of scope).
3. There is no `/c/2/videos`, no media-kind filter, and no link from the creator
   header to a video view.
4. The gallery header reports `18275 images · 3 gifs · across 918 posts` and
   silently omits 756 videos.
5. The creator stat strip shows `Files 19139` and `Direct media 0`. "Direct
   media" counts *caption links* with `category='direct_media'`, not attachments,
   so a creator with 756 video files looks like it has no video at all.

### Tagging / type bugs found

1. **`kind='gif'` does not guarantee a GIF.** Three onlyfans rows are tagged
   `gif` with `mimeType='image/gif'`, but every variant is `original.mp4`,
   `durationMs` is 9–12 s, and the filename ends in `.mp4`:

   | post | kind | mime | variant | duration |
   |---|---|---|---|---|
   | 85478926 | gif | image/gif | `original.mp4` | 12000 |
   | 74724441 | gif | image/gif | `original.mp4` | 9000 |
   | 65498265 | gif | image/gif | `original.mp4` | 9000 |

   The gallery treats them as still images; the post page emits
   `data-kind="gif"` and no `data-variants`, and `loadAttachment()` inserts the
   `.mp4` URL into an `<img>` (`app.js:172`). The result is a broken image, not
   a playing video. Patreon has real GIFs (`original.gif`) with the same kind,
   so `kind` alone cannot decide.
2. `routes._decorate_files` decides `is_video` / `is_image` from `kind` only.
   Any future upstream mismatch (or an `audio`/`file` kind with a video mime)
   falls through to "open in a new tab".
3. Post cards expose no file-kind counts (`db.post_cards` only returns link
   categories, tags and a thumbnail), so a video post and an image post look
   identical apart from the raw file count.
4. `db.GALLERY_KINDS` exists but is unused; every gallery query repeats the
   literal `('image', 'gif')`.

### "Incorrect tags" is not an ingestion bug for this creator

The profile payload says `"hasTags": false`, and every stored onlyfans post
has `"tags": []` in `raw_json`. The `tags` table has 0 rows for creator 2.
So the empty tag UI is faithful to upstream. There is no hidden tag field to
read; any useful tags would have to be derived from captions (only 5 posts
contain `#`, all of them `#FINISHED`). The remaining problem is presentation:
an empty tag dropdown gives no explanation.

Caption links are also almost absent for this creator (4 rows, all `other`), so
Drive/MEGA/Direct-media facets being 0 is correct. Fixing the media UI must not
change link classification.

## Out of scope

- Changing the crawler's network behaviour; the data is already correct.
- Deriving hashtag tags; not justified by this archive.
- Reworking link classification.

## Resolution

Root cause: **the archive is complete, but the product has no video surface.**
The gallery is image-only by explicit design, the creator page only reports a
generic file count, and file types are trusted from a single upstream `kind`
field that is wrong for three MP4-backed "gif" attachments.

Ticket split:

| Ticket | Fix |
|---|---|
| T7.1 | Normalize attachment kinds (`gif`/MP4, mime/filename/duration) and backfill existing rows |
| T7.2 | Make the gallery media-aware: videos included, kind filter, video lightbox |
| T7.3 | Show image/video counts and badges on the creator page, add a media-kind filter |
| T7.4 | Post page playback for normalized video-backed attachments |
| T7.5 | Clarify/hide empty tag UI when upstream has no tags |
