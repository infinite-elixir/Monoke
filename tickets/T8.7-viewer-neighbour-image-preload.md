# T8.7 — Preload neighbouring images in the fullscreen viewer

## Goal

Remove the per-image stall in the fullscreen viewer. When the user is on a
still image, warm the browser cache for the **3 images before and 3 after** it
(radius 3, six extra images), so pressing next/previous almost always shows an
already-decoded image instead of a blank frame and a network wait.

Preloading is invisible, bounded and skippable: it must never delay the current
image, grow memory without limit, or preload videos/GIFs.

## Current behaviour

- `viewer.js` `render(index)` creates exactly one `<img>`/`<video>` for the
  current item and attaches `src`; nothing else is fetched until the next
  navigation.
- `state.media` is already the full post-scoped list with `url`, `kind` and
  `thumb_url`, so the neighbours are known without a request.
- `viewer_neighbour`/`viewer_state` give `previous_post` and `next_post`; T8.6
  crosses into them at the horizontal edges.
- T8.3 explicitly deferred preloading ("Do not preload the next/previous media
  in this ticket"). This ticket implements that follow-up.
- T6.5 fixed a memory-growth issue; any preload cache must have a hard bound.

## Scope

**Preload window**

- [ ] Add constants near the top of `viewer.js`:
      `PRELOAD_RADIUS = 3`, `PRELOAD_MAX = PRELOAD_RADIUS * 2`.
      Keep them easy to raise to 4 after the memory check passes.
- [ ] On every rendered item, compute the window
      `[index - PRELOAD_RADIUS, index + PRELOAD_RADIUS]`, clamped to the post,
      excluding the current index.
- [ ] Only preload items whose `kind === "image"`. Do **not** preload:
      - `video` (large MP4s, range requests, native buffering),
      - `gif` (animated files can be many MB; the current GIF still loads on
        demand),
      - `audio` (never in the viewer).
- [ ] Skip items with no `url` or a `data:` URL.
- [ ] Never preload the same URL twice for the same post; a `Map` keyed by the
      media URL is the source of truth.

**Timing and priority**

- [ ] Do not start preloading until the current media has fired `load` (or
      `error`), so the visible image always wins the connection.
- [ ] Then schedule with `requestIdleCallback` (fallback `setTimeout(…, 200)`)
      and a `timeout` so a busy main thread cannot starve the warm-up.
- [ ] Cancel a pending idle callback when the user navigates again; recompute
      the window from the new index.
- [ ] Do not block input: navigation must render/swap the current item
      immediately, with preloading continuing afterwards.
- [ ] Respect data saving: skip preloading when
      `navigator.connection.saveData === true` or
      `navigator.connection.effectiveType` is `slow-2g`/`2g`, and when
      `window.matchMedia("(prefers-reduced-data: reduce)")` matches (guard the
      API in try/catch).
- [ ] Do not preload while `document.visibilityState !== "visible"`; a
      `visibilitychange` back to visible may schedule the window once.

**Memory and lifecycle**

- [ ] Keep references to the preloading `Image` objects in the Map; otherwise
      the garbage collector may drop them before the request finishes.
- [ ] When the window moves, delete entries outside the new window from the Map
      (do not touch `img.src`; dropping the reference is enough and avoids
      aborting in-flight loads).
- [ ] Clear the Map when the post changes (`jump()`), so the cache is
      post-scoped and cannot grow across a long session.
- [ ] Hard cap: never more than `PRELOAD_MAX` entries in the Map at any time.
- [ ] On `error`, delete that entry and add the URL to a small failed set so the
      same broken image is not retried on every move. Reset the failed set on a
      post jump.
- [ ] Cancel/invalidate on `unloadMedia()` / viewer close; no listeners or
      timers survive cleanup.

**Correctness**

- [ ] Preloading never mutates the DOM, the current `<img>`/`<video>`, the
      counter, the hint or the zone buttons.
- [ ] A preloaded image is used from the browser cache when it later becomes
      current: no second `Image` object is created for a URL already in the Map.
- [ ] The T8.6 boundary crossing keeps working: after a post jump, the new
      post's window warms (the old post's Map is dropped).
- [ ] If the browser refuses cache reuse, the viewer still works exactly as
      before; preloading is an optimisation, never a dependency.

**Optional, only if free**

- [ ] When preloading, set `image.fetchPriority = "low"` where supported.
- [ ] Use the item's `thumb_url` as a low-quality placeholder while the
      full-size current image loads. Do not add round corners, filters or a
      spinner; the viewer's chrome-free rule (T8.5) still applies.

## Tests

- [ ] `node --check src/monoke/web/static/viewer.js` passes.
- [ ] Static check/unit-style test: for a 10-image post and index 5, the window
      helper returns indices 2-4 and 6-8; at index 0 it returns 1-3 only; at
      index 9 it returns 6-8 only; videos/GIFs are filtered out.
- [ ] Browser acceptance in Chromium and Firefox (Network panel or
      `performance.getEntriesByType("resource")`):
      - landing on a middle image requests the six neighbouring **image** URLs
        during idle;
      - pressing next/previous to an already-warmed image does not issue a new
        request for that URL (cache hit/304) and paints without a blank frame;
      - a video and a GIF in the same post are never preloaded;
      - moving rapidly through 20 images never leaves more than
        `PRELOAD_MAX` entries or more than the window's worth of live `Image`
        objects;
      - leaving the post drops the old entries (heap does not grow across
        repeated post jumps);
      - with data saving / 2G emulation, no neighbour requests are made;
      - a broken neighbour URL does not block navigation or retry endlessly.
- [ ] Existing viewer tests (T8.1-T8.6) stay green.

## Acceptance criteria

- [ ] On a still image, the viewer warms up to 3 images before and 3 after,
      without waiting for the user to navigate.
- [ ] Navigating to a warmed image shows it immediately, with no visible blank
      frame or extra network round-trip in the common case.
- [ ] Videos and GIFs are never preloaded.
- [ ] Memory is bounded: at most `PRELOAD_MAX` entries, cleared per post.
- [ ] Data-saver/2G users and hidden tabs do not trigger background downloads.
- [ ] The viewer still shows only media, the counter and the first-run hint; no
      loading chrome is added.
- [ ] The current image's initial load is not delayed by preloading.

## Out of scope

- Prefetching the neighbouring post's JSON or its first image before a T8.6
  boundary crossing (a separate ticket if the edge still feels slow).
- Video buffering/preloading, `preload="auto"`, or downloading media to disk.
- Thumbnail lazy-loading in the gallery or post page (already handled there).
- Service workers, offline mode, HTTP cache headers for `cum.st` media.
- Preloading the whole post or archive.
- Decoding/`createImageBitmap` workers or zoom/pan.

## Notes

- `new Image()` with `src` set and a retained reference is the simplest way to
  warm the HTTP cache; no CORS header is needed because the image is not read
  back into a canvas.
- The six-image window matches the request: three to four each side. Start at
  three to keep mobile memory low; raising `PRELOAD_RADIUS` to 4 is a one-line
  change after the browser memory check.
- This ticket supersedes T8.3's "no preloading" note and its out-of-scope line.

## Resolution

`viewer.js` now has `PRELOAD_RADIUS = 3` / `PRELOAD_MAX = 6` and a pure
`preloadWindowIndices()` helper (delimited by `BEGIN/END preload-window`
markers so the Node unit test can evaluate it without a DOM). It returns the
in-window indices that are `kind === "image"`, have a real URL and have not
already failed; videos, GIFs, audio and `data:` URLs are skipped.

Warming starts only after the current element fires `load`/`error` (or is
already complete on first paint) and is scheduled through
`requestIdleCallback` with a 1.5 s timeout, falling back to a 200 ms timer. A
per-render cancel plus an epoch guard makes a pending callback a no-op after
navigation. `navigator.connection.saveData`, `slow-2g`/`2g`,
`prefers-reduced-data` and a hidden `document.visibilityState` all suppress
preloading; returning to a visible tab may schedule once.

The cache is a `Map` of URL → retained `Image` (hard-capped at
`PRELOAD_MAX`), pruned to the new window on every move and cleared in
`jump()` and `cleanup()`, together with the failed-URL set. Preloads are never
appended to the DOM and never delay or replace the current element; an error
drops the entry and records the URL so it is not retried until the next post.

`test_preload_window_covers_radius_and_filters_unsafe_items` evaluates the
extracted helper under Node for the 10-image cases, kind/`data:` filtering and
the failed-URL set; `node --check` covers syntax. The Network-panel matrix in
this ticket remains a manual browser pass (no browser automation in the repo).
