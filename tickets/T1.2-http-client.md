# T1.2 — HTTP client: cache, retry, backoff

## Goal
One place that knows how to talk to cum.st politely, correctly, and cache-first.

## Scope

- [x] `httpx.AsyncClient` with:
      - `User-Agent: Monoke/0.1 (local private archive)`
      - `Accept: application/json`
      - `timeout=20s`, `follow_redirects=False`
      - base URL `https://cum.st/api/v1`
- [x] `get_json(path, params=None, *, fresh=False)`:
      - cache lookup in `api_cache` unless `fresh`; return `(data, fetched_at, from_cache)`
      - JSON parse; on non-JSON raise `ApiError` with a body snippet
- [x] Error taxonomy: `ApiNotFound` (404), `ApiServerError` (5xx), `ApiTimeout`, `ApiDecode`,
      `ApiBlocked` (HTML/JS challenge instead of JSON).
- [x] Retry: 3 attempts, `0.5s → 1.5s → 4.5s` ±20 % jitter, on 429/5xx/timeout only.
      Never retry 404.
- [x] Global `asyncio.Semaphore(concurrency)` (default 4) and 100–300 ms jitter before each
      outbound request.
- [x] On a response whose `Content-Type` is `text/html`, raise `ApiBlocked` with a 200-character
      snippet (this is how DDOS-Guard challenges would appear).
- [x] Structured log line per request: path, status, ms, cache hit/miss.

## Acceptance criteria

- [x] respx tests: 500 then 200 retries twice and succeeds; 404 raises immediately.
- [x] An HTML body with status 200 raises `ApiBlocked`, not a JSON decode error.
- [x] Second identical call is served from cache; `fresh=True` bypasses it.
- [x] Concurrency never exceeds the semaphore (instrumented counter in tests).
- [x] Cache entries expose `fetched_at` for the UI.

## Notes
- No special headers are required by cum.st. If you find yourself copying an `Accept: text/css`
  workaround, stop — that was kemono.
- The API sends `cache-control: public, max-age=60, stale-while-revalidate=300`; our own cache
  is independent and only bypassed when `fresh=True`.
