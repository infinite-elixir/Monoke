# T7.7 — Gallery should expose image/video/gif filters, not a creator-page Videos button

## Problem

On a creator page the media entry points are inconsistent:

- **Gallery** opens the gallery with all media, where the only way to choose a
  type is a small `Kind` dropdown buried among search, sort, tag, orientation,
  size and date filters.
- A separate **Videos** button appears in the creator header and deep-links
  straight to `?kind=video`.

Users read this as "Videos is a different destination", while Gallery looks
unfiltered. Both should be the same destination, and the type choice should be
visible as soon as the gallery opens. GIFs currently have no equivalent header
shortcut at all.

## Goal

Make media kind a first-class **tab strip** at the top of the gallery
(**All media · Images · Videos · GIFs**), and remove the separate **Videos**
button from the creator homepage. `?kind=image|video|gif` remains the single
source of truth, so old links keep working.

## Current behaviour

- `creator.html` renders:
  `<a class="button" href="/c/{{ creator.id }}/gallery">Gallery</a>` and,
  when videos exist, `<a class="button" href="/c/{{ creator.id }}/gallery?kind=video">Videos</a>`.
  The stat strip below also links Images/Videos/GIFs to the creator's post
  list (`?media=`), not the gallery.
- `gallery.html` renders a `Kind` `<select>` from `GALLERY_KIND_LABELS`
  (`All media`, `Images`, `Videos`, `GIFs`) alongside eight other controls.
- `GalleryFilters` already parses and preserves `kind`; `gallery_stats()`
  already returns distinct image/video/gif counts used in the header.
- T4.11 groups gallery results by post and `_gallery_sorts()` removes duration
  sorts for the Images tab.

## Scope

**Creator page**

- [x] Remove the conditional **Videos** header button. Gallery is the only
      media-grid action next to View latest, Sync and Delete.
- [x] Keep the stat-strip counts and their existing `?media=` post-list links
      unchanged; this ticket is only about the header action that bypasses the
      gallery.
- [x] Update any test that asserts the Videos header button exists; add one
      asserting it is gone while Gallery remains.

**Gallery media-kind tabs**

- [x] Add a prominent tab strip above the filter form, in this order:
      **All media**, **Images**, **Videos**, **GIFs**.
- [x] Link each tab to `/c/<creator>/gallery` with `kind` omitted for All media
      and `kind=image|video|gif` for the rest. Preserve `q`, `tag`,
      `orientation`, `min_bytes`, `from`, `to` and a valid `sort`; reset `page`
      to 1.
- [x] Show the distinct-media count from `gallery_stats()` in each tab
      (`images`, `videos`, `gifs`; All = their sum). Zero-count tabs stay
      visible and are still clickable so users can confirm an empty type.
- [x] Mark the active tab with `aria-current="page"` and a `is-current` style;
      the strip is a `<nav aria-label="Media type">` of links, keyboard
      reachable, and horizontally scrollable on narrow screens.
- [x] Remove the now-duplicate `Kind` `<select>` from the filter form. When a
      kind is active, submit it as a hidden `kind` input so **Apply**, sort,
      search and the other filters keep the current tab. **Clear** continues to
      reset every filter, including kind.
- [x] Preserve `?kind=` deep links (including the old Videos button URLs and
      bookmarks). Unknown values continue to fall back to All media.
- [x] Header stat links inside the gallery (if any) should either use the tabs
      or stay as text; do not introduce a second kind control.
- [x] Empty tab state: when a valid kind has no matching media, explain
      "No videos match these filters" and offer **All media** plus **Clear**.
      Keep the existing per-tab empty state distinct from the creator-has-no-
      media state.
- [x] Tabs must not break T4.11 post grouping, T7.6 duration sorting, the
      lightbox tile hooks or the gallery bookmark action menu.

**Tests**

- [x] Creator page no longer renders the Videos header button; Gallery still
      renders and points at `/c/<id>/gallery`.
- [x] Gallery renders four tabs in order with the expected counts from a seeded
      creator.
- [x] The active tab is All media with no `kind`, and the matching tab is
      current for each of image/video/gif.
- [x] Tab URLs preserve search, tag, orientation, size, date range and sort,
      and reset `page` to 1.
- [x] Submitting the filter form with a kind active keeps `kind` (hidden input)
      and the selected tab after the redirect/GET.
- [x] Image tab removes duration sorts; All media and Videos keep them.
- [x] Unknown `kind` falls back to All media.
- [x] A kind with zero results shows the tab-specific empty state and a working
      All media link.
- [x] Existing gallery, creator and viewer tests stay green.

## Acceptance criteria

- [x] Opening Gallery immediately shows **All media / Images / Videos / GIFs**
      with counts, without opening a dropdown.
- [x] Choosing Images or Videos changes the grid and keeps every other active
      filter, including sort, search and page reset.
- [x] There is no separate Videos button on the creator homepage.
- [x] Old `?kind=video` links, including the removed button's URL, still work.
- [x] Mobile layout keeps the tab strip usable without page-width overflow.
- [x] The change is keyboard operable and works without JavaScript.

## Out of scope

- Changing gallery pagination or post grouping (T4.11).
- Adding new kinds (audio remains excluded from the gallery), new filters, or
  changing what `gallery_stats()` counts.
- Changing the creator stat-strip links to `?media=`.
- Changing the viewer or the bookmark library.

## Notes

- Reuse `GALLERY_KIND_LABELS` for labels, but drive counts from
  `gallery_stats()` rather than four extra count queries.
- Tab counts are distinct media counts, while the gallery pager counts posts.
  Keep the labels adjacent to the existing "N images · M videos · …" meta so
  the difference is understandable; do not label the tabs "N posts".
- The tab strip should sit visually above the filter form (and outside it,
  because each tab is a link, not a form control). The form needs the hidden
  `kind` input described above to avoid silently dropping the tab on Apply.
