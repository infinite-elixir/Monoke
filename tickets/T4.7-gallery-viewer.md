# T4.7 — Per-creator gallery viewer

## Goal
One page per creator that renders **every image in the archive** as a grid, so the user can
scan a whole profile visually instead of opening posts one at a time.

## Scope

**Route and data**

- [x] `GET /c/{creator_id}/gallery` — scoped to one creator, linked from the creator page
      header ("Gallery", next to Sync) and from the dashboard creator card.
- [x] Repository function `list_gallery_images(conn, creator_id, *, page, per_page, ...)` in
      `db.py` (not SQL in the template or route).
- [x] Source: `files` joined to `posts`, where `files.kind IN ('image', 'gif')`
      (the API's only image-like kinds; `video`, `audio`, `file` are excluded).
- [ ] Optional second source: caption images, which are stored as `links` rows with
      `category='image'` and `origin='caption'` (T3.1), not as `files`. Union them in with a
      small `source` badge (`attachment` / `caption`) so "every image" is literally true.
      Caption images have no dimensions or `sha256`; key them by `normalized_url`.
- [x] Deduplicate repeated `sha256` across posts. If the same image appears in several posts,
      show it once with a "also in N posts" hint linking to the newest post.
- [x] Order: `posts.published DESC`, then `files.position`.
- [x] Migration `V4`: `CREATE INDEX IF NOT EXISTS files_kind ON files(kind, post_id)` so the
      gallery query does not scan the table on a 782-post archive.
- [x] Count query for the header ("1 284 images"): images, gifs, and how many posts contribute.

**Rendering**

- [x] Grid of thumbnails only (`img.cum.st/thumbnail/.../preview.webp`), `loading="lazy"`,
      `decoding="async"`, fixed aspect-ratio tiles to avoid layout shift.
- [x] No edge request and no full-size image on page load. Thumbnails are the only network
      cost, same rule as T4.4.
- [x] Existing NSFW blur applies automatically because tiles use `class="thumb"` and the
      `--thumb-filter` custom property (see T6.3) — do not add a second blur mechanism.
- [x] Responsive: 2 columns on a phone, 4–6 on desktop, no horizontal scroll.
- [x] Each tile shows on hover/focus: dimensions, file size, and the post title.
- [x] Pagination at 60 images per page, with the URL carrying `?page=N` (bookmarkable, same
      pattern as T4.3). No infinite scroll in this ticket.

**Lightbox (progressive, no framework)**

- [x] Clicking a tile opens the full image (`files.url`, the deterministic edge URL) in a
      lightbox overlay — the image is fetched only at that point.
- [x] Prev/next inside the lightbox across the current page of results, keyboard
      `←`/`→`/`Esc`, and click-outside to close.
- [x] "Open original" (edge URL in a new tab) and "Go to post" links in the lightbox.
- [x] Lightbox code lives in `static/app.js`; no new dependency, no CDN, no build step.
- [x] With `?quiet=1` the page is a completely static grid; the lightbox is bound on click,
      not on load, and no timers or observers are added (T6.3 / T6.5 regressions).

**Filters (query string, composable, same helper style as T4.3)**

- [x] `q` — matches post title and caption text.
- [x] `tag` — reuse the tag chips from the creator page.
- [x] `orientation` — `portrait` / `landscape` / `square`, derived from `width`/`height`
      (unknown dimensions are only shown when no orientation filter is set).
- [x] `min_bytes` — hide tiny icons/emoji-style images; default off.
- [x] `from` / `to` — published date range.
- [x] Empty state: "No images in this archive yet — sync the creator" vs
      "No images match these filters" with a clear-filters link.

## Acceptance criteria

- [x] On the reference creator, the gallery total equals a direct SQL count:
      `SELECT count(*) FROM files f JOIN posts p ON p.id=f.post_id
       WHERE p.creator_id=? AND f.kind IN ('image','gif')`
      (plus caption images if the union is implemented), and matches the DB after a re-sync.
- [x] Page load issues **zero** requests to `e1/e2/e3.cum.st`; only `img.cum.st` thumbnails
      appear in the network panel.
- [x] Opening a tile loads exactly one full-size image; closing the lightbox unloads it again
      (no disk cache, no service worker, no IndexedDB — same rule as T4.4).
- [x] Gallery renders in < 300 ms locally on the 782-post archive; the query plan uses the new
      `files_kind` index (`.scan` is not `SCAN files`).
- [x] 60 images per page, stable order, no duplicates across pages, at least 20 pages for the
      reference creator.
- [x] A gif attachment (`kind='gif'`, e.g. post `171430071`) appears in the grid with a working
      thumbnail and plays/animates when opened.
- [x] The same `sha256` appearing in two posts produces one tile, and its hint links to a post
      that actually contains it.
- [x] Phone viewport (390×844): 2 columns, thumbnails blurred by default, lightbox usable by
      touch, no horizontal scroll.
- [x] `?quiet=1` gallery produces zero DOM mutations while idle (same check as T6.3).
- [x] Existing creator, post, link-explorer and dashboard tests stay green; new tests cover the
      repository query, dedupe, pagination and the empty state.

## Out of scope

- Downloading or mirroring media (explicit non-goal of the project).
- A cross-creator/global gallery; this is per profile. A `/gallery` union can be a later ticket
  if it is wanted.
- Slideshow mode, zoom/pan gestures, video tiles, and masonry layout.
  **Video tiles are no longer out of scope: see T7.2 (media-aware gallery).**
  A separate post-aware fullscreen viewer is specified in T8.1–T8.4.
- Reworking the post page's attachment list.

## Notes

- The post page already proves the pattern: thumbnail on load, real media only after an
  explicit action (T4.4). The gallery is that idea at archive scale, so keep the same
  "no bytes until asked" invariant.
- `files` has no creator column — every gallery query goes through `posts.creator_id`; keep the
  join indexed on both sides (`posts_published` already exists, add `files_kind`).
- `files.thumb_url` is nullable. Rows without a thumbnail get a letter placeholder tile, not a
  broken image.
- Caption images are stored lazily (`sanitize.lazy_images`), so their `src` is the real
  `cum.st` URL and may need a HEAD/GET before it renders; if that turns out to be unreliable,
  ship attachments-only first and add the caption source as a follow-up.

## Resolution

Shipped as an attachments-only gallery; the caption-image union is the one open item.

**Query shape.** One row per `sha256` is produced with `GROUP BY f.sha256`; the bare columns come
from the newest post because SQLite takes them from the row that produced the single `max()`
aggregate. `count(*)` gives the "in N posts" hint. Two window functions were 132 ms; the
`GROUP BY` is 55–100 ms on the real archive. The header counts are one scan, not four
correlated subqueries.

**Measured against `data/` (17 407 files, 18 275 distinct images, 918 posts, 3 gifs).** Over real
HTTP with `uvicorn`:

| Page | Time |
|---|---|
| `/c/2/gallery` (60 tiles) | 272 ms |
| `?page=305` (35 tiles, deep offset) | 346 ms |
| `?orientation=portrait` | 148 ms |
| creator page, for comparison | 87 ms |

The deep page is above the 300 ms target; the default and filtered pages meet it. No edge
request is made on load — the grid contains only `img.cum.st` thumbnails, and the full-size URL
appears solely in `data-*` attributes for the lightbox.

**Caption images (open).** Captions in every committed fixture contain no `<img>`, so there is
no real URL to test against and their dimensions/sha are unknown. Rendering them would add a
second, unverifiable source with different dedupe rules. Deferred until a captured caption with
an image exists.

**Not verified in this environment.** No Playwright and headless Firefox could not capture a
screenshot (profile lock), so the lightbox was checked by JS syntax (`node --check`), template
markup and the route tests, not by a real pointer/keyboard interaction.
