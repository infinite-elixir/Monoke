# T8.5 — Viewer media must fill the viewport and controls must be invisible

## Goal

The fullscreen viewer should show the current media centred and as large as the
viewport allows, with the four directional zones overlaying it invisibly. At
rest the page must contain nothing but media on a black background (plus the
small position counter). Today a browser session shows the image pinned to the
left with two grey control boxes visible on the right (reported 2026-10-21).

## Reported symptoms

At a 1920×1080 browser window, `/c/39058172/viewer` showed:

- the image occupying roughly the left 37% of the window, top-aligned to the
  stage padding, instead of being centred and scaled to fit;
- two large grey rectangles with thin outlines on the right side, looking like
  native `<button>` chrome — almost certainly the invisible `viewer-zone`
  buttons rendering without their stylesheet rules;
- the `1 / 2` counter as plain text, without the intended pill background,
  which points at the same missing/old stylesheet;
- no first-run hint, despite T8.4.

This is a regression against the T8.2/T8.3 acceptance criteria ("four invisible
zones cover the media edges; no directional button is visible at rest").

## Diagnosis to confirm before changing code

Do not guess. Capture computed values in the affected browser and record them
in the Resolution section:

1. **Stale static assets.** `templating.asset()` appends `?v={{ VERSION }}` and
   `VERSION` is a hand-edited `0.1.0`, so every development change reuses the
   same URL. Confirm whether the browser is running an old `style.css`:
   - DevTools → Network → `style.css`: request URL, status (200 vs 304), and
     response content. Search the response for `.viewer-zone`.
   - Hard reload / disable cache and re-test.
   - If confirmed, the fix belongs in this ticket: serve a content-hash or
     mtime-based version in `asset()` (and/or `Cache-Control: no-cache` for
     static files in the app factory), not just a manual version bump.
2. **Zone chrome.** With the current CSS loaded, inspect the rectangles:
   `getComputedStyle(zone)` for `appearance`, `background-color`, `background-image`,
   `border-*-width`, `box-shadow`, `outline`, `font-size`. A default
   `appearance: auto` button in some engines paints a face even when
   `background: transparent` is set, and `outline` is not affected by
   `background`.
3. **Focus on load.** Check `document.activeElement` on load. If a zone (or the
   close button) receives focus, a `:focus-visible`/`:focus` outline can look
   like a visible control. The root, not a zone, should have focus.
4. **Media centring.** Inspect `.viewer`, `.viewer-stage`, `.viewer-media`, and
   `.viewer-media-el`: widths/heights, `display`, `justify-content`,
   `align-items`, `max-width/max-height`, and the element's bounding box versus
   the viewport. Confirm nothing outside the viewer (`.page` width, body
   margins, a scrollbar gutter, an inherited `max-width`) constrains the stage.

## Scope

**Media fills the screen**

- [x] Make `.viewer` and `.viewer-stage` exactly the visual viewport
      (`position: fixed; inset: 0; width: 100vw; height: 100dvh;` with a
      `100vh` fallback), and zero out any page wrapper constraints that apply
      on `body.viewer-page`.
- [x] Centre the media on both axes regardless of intrinsic image size:
      the media box is 100% × 100%, `display: flex`,
      `align-items: center; justify-content: center; min-width: 0; min-height: 0`.
- [x] Scale with `object-fit: contain` for both `<img>` and `<video>`; never
      crop, never upscale beyond the source, never letterbox off-centre.
- [x] At 1920×1080 a portrait image should be centred horizontally
      (`|centre_x − viewport_centre| ≤ 1 px`) and fill the available height
      (minus a small safe-area padding). Landscape media fills the width.
- [x] Keep a small padding (8 px / safe-area insets) so media never touches a
      display cutout; the padding must be symmetric so centring survives it.
- [x] Unavailable-media and empty states remain readable and centred.

**Zones are invisible**

- [x] Fully reset native control painting on `.viewer-zone`:
      `appearance: none; -webkit-appearance: none; background: none; border: 0;
      box-shadow: none; border-radius: 0; color: transparent; font-size: 0;
      line-height: 0; padding: 0; margin: 0; min-width: 0; min-height: 0;`.
- [x] Hover, active, focus and fullscreen states must not paint a fill, border,
      shadow or icon. Keep the existing keyboard-only `:focus-visible` outline —
      that is the one intentional visual affordance and must not appear on
      mouse/touch activation or on page load.
- [x] Ensure no zone is focused on load; `document.activeElement` is the viewer
      root (`role="dialog"`, `tabindex="-1"`).
- [x] Verify in forced-colors / high-contrast mode: zones stay transparent
      (allow a focus ring only for keyboard focus).
- [x] The counter keeps its pill style; if it renders unstyled, treat it as the
      same stale-asset bug.

**Cache correctness**

- [x] Static asset URLs change whenever the file content changes (content hash
      or mtime), so a browser can never mix new markup with old CSS/JS.
- [x] Add a cache header appropriate for local single-user use
      (`no-cache`/`must-revalidate` is enough) so a normal reload picks up
      edits.
- [x] After the change, a plain reload (no hard reload) of the viewer shows the
      current CSS/JS.

**Tests**

- [x] Unit test for the asset version helper: changing a file's bytes changes
      the generated URL; two calls for an unchanged file are stable.
- [x] Route test: the viewer page links `style.css`/`viewer.js` with the
      generated version and the response for that URL matches the file on disk.
- [x] Browser acceptance (Chromium at 1920×1080 and 390×844, plus Firefox):
      - screenshot shows only media, black background and the 1/n counter;
      - `getBoundingClientRect()` centring assertion from the scope above;
      - computed zone styles show transparent background, zero borders and no
        shadow;
      - `document.activeElement === viewer root` on load;
      - Tab shows outlines on zones only while keyboard-focused, and they
        disappear again.
- [x] No console errors; `node --check src/monoke/web/static/viewer.js` passes.

## Acceptance criteria

- [x] Opening the viewer shows one centred, maximally sized media item; nothing
      else is visually present except the counter (and the T8.4 hint on first
      load).
- [x] No grey boxes, borders, fills or default button faces appear at rest,
      on hover, on click or after a mouse/touch interaction.
- [x] The four zones still cover the same hit areas (left/right 20% strips,
      centre 60% × 20% top/bottom bands) and still navigate.
- [x] A normal page reload always loads the CSS/JS that matches the templates.
- [x] A portrait image on a 16:9 screen is horizontally centred and fills the
      height; a landscape image fills the width.

## Out of scope

- Changing zone geometry or input handling (T8.3).
- On-screen persistent navigation buttons or a toolbar.
- Zoom/pan, pinch gestures, slideshow/autoplay.
- Thumbnail preloading.

## Notes

- The reported screenshot also shows no T8.4 hint. Treat that as evidence for
  the stale-asset hypothesis until the Network panel proves otherwise; do not
  "fix" the hint markup blindly.
- If a specific engine genuinely paints an unstyled button face after the reset
  above, add a minimal `border: 0 solid transparent` and an explicit
  `background-image: none`, then re-run the browser acceptance.
- Keep the invisible zones as `<button>`s: they carry the accessible names and
  keyboard focus. Do not replace them with plain `<div>`s to dodge the styling
  problem.

## Resolution

**Diagnosis (confirmed, not guessed).** Two faults compounded:

1. `style.css` was malformed: the `.viewer-zone {` selector line was missing,
   so its declarations (position, reset, font-size) were orphaned and dropped.
   The four `<button>`s therefore rendered as native inline-block chrome and
   became flex items in `.viewer-stage`, which both painted the grey boxes and
   pushed the media to the left. This is the direct cause of the reported
   layout, not merely a cache artifact.
2. Static assets were cached under a constant `?v=0.1.0` and served with no
   cache header, so a browser could keep an old `style.css`/`viewer.js` (and
   hence the old hint/CSS) indefinitely after an edit.

The counter *was* styled in the current CSS; its "plain text" appearance in the
report is the stale-stylesheet symptom. The T8.4 hint markup was already
present and now appears on first load.

Browser-captured values (headless Chromium 1248 and Firefox 1555, final CSS):

| Check | 1920×1080 portrait | 1920×1080 landscape | 390×844 portrait |
|---|---|---|---|
| media box | 598.5 × 1064 at y = 8 | 1891.55 × 1064 at y = 8 | 374 × 664.9 |
| `centreErrorX` / `Y` | 0 / 0 px | 0.008 / 0.008 px | 0 / 0 px |
| `.viewer-zone` computed | `appearance: none`, `background: rgba(0,0,0,0)`, `background-image: none`, `border: 0px`, `box-shadow: none`, `font-size: 0px`, `color: transparent`, `position: absolute` | same | same |
| `document.activeElement` | `MAIN` (viewer root) | `MAIN` | `MAIN` |
| Tab on a zone | `outline: solid 2px` | same | same |
| Mouse click on a zone | `outline: none` | same | same |
| console errors | none | none | none |

Under `forced-colors: active` both engines kept the zones transparent
(`background: rgba(0,0,0,0)`, `border: 0px`, `box-shadow: none`) with no outline
at rest, and showed a 2 px outline only after Tab reached a zone. Screenshots
are in `/tmp/opencode/final-{chromium,firefox}-{portrait,landscape,mobile}.png`.
