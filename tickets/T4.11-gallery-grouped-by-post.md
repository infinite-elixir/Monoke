# T4.11 — Group the gallery by post and paginate by posts

## Goal

Turn the gallery from one flat, archive-wide media grid into **post groups**:
each post gets a dated/titled section containing its images, GIFs and videos,
in the same order the viewer uses. Pagination counts posts, not media, so a
post is never split across two pages.

This is the user-facing model: the gallery is a visual index of posts, not a
deduplicated media bucket.

## Current behaviour

- `db.list_gallery_images()` groups by `files.sha256` across the whole
  creator, returns one row per distinct file with a representative
  `post_id`, `copies` and `max(published)`.
- `_gallery_context()` calls it with `GALLERY_PER_PAGE = 60` and paginates
  by media items. `_gallery_pager()` reports the noun `media`.
- `gallery.html` renders one flat `.gallery-grid` of `<figure>` tiles. A tile
  shows the post title in its caption and "in N posts" when deduped.
- `files` has `UNIQUE(post_id, sha256)`, so a post cannot contain the same
  sha twice. The same sha can legitimately appear on two different posts.
- T4.10 makes each tile link to the viewer at its exact media item and
  computes `viewer_index` among `VIEWER_KINDS` ordered by
  `COALESCE(position, 0), id`.
- `GalleryFilters` owns `q`, `tag`, `kind`, `orientation`, `min_bytes`,
  `from`, `to`, `sort` and `page`; `GALLERY_PER_PAGE` is also used by the
  bookmarks media grid, so it must not be changed globally.
- `gallery_stats()` already reports distinct media and the number of posts
  contributing media.

## Scope

**Decisions this ticket implements**

- [ ] Group by post, with a visible section per post.
- [ ] Paginate by post: `GALLERY_POSTS_PER_PAGE = 20` posts per page.
- [ ] Show a post's matching media together on one page; never split a post
      across pages, even when it has more media than usual.
- [ ] Cross-post duplicates are intentional: the same image on two posts
      appears once in each post's section. Remove the global sha dedupe from
      the gallery page and the "in N posts" hint.
- [ ] A post appears only if it has at least one media item matching the
      active filters. Non-matching media inside an otherwise matching
      section are hidden.

**Repository**

- [ ] Add `GALLERY_POSTS_PER_PAGE = 20` (in `web/filters.py` or a gallery
      module). Do not change `GALLERY_PER_PAGE`, which the bookmarks library
      still uses.
- [ ] Replace the gallery-page query with a grouped API, for example
      `list_gallery_posts(conn, creator_id, ..., limit, offset)` returning:
      `(groups, total_posts)`, where each group has the post's `id`,
      `service_id`, `title`, `published`, `post_url`, optional thumb, and an
      ordered `media` list.
- [ ] `total_posts` is `count(DISTINCT p.id)` over posts with at least one
      matching eligible file. It is the pager total, not the media count.
- [ ] Media inside a group are ordered by `COALESCE(f.position, 0), f.id`
      for every sort mode, matching the viewer's in-post order.
- [ ] `viewer_index` for every tile remains the index among **all**
      `VIEWER_KINDS` rows of that post, not the filtered subset. Compute it
      once per page with a window function/CTE or a batched query. Filtering
      by `kind`, `orientation` or `min_bytes` must not change a tile's index.
- [ ] Use one page query for the post groups plus one batched media query for
      those posts (or a single CTE). No query per post and no query per tile.
- [ ] Keep the existing `q`, `tag`, `kind`, `orientation`, `min_bytes`,
      `from`/`to` semantics. `q` and `tag` select posts; the rest select
      media.
- [ ] Keep the `gallery_stats()` header counts unchanged (images, videos,
      gifs, audio, posts) so the header still reports archive totals.
- [ ] Retire `list_gallery_images()` or keep it only as a compatibility
      helper if another page/tests still use it. Do not leave two competing
      gallery models.

**Sort semantics (post groups)**

- [ ] `newest`: posts by `COALESCE(p.published, 0) DESC, p.id DESC`.
- [ ] `oldest`: posts by `COALESCE(p.published, 0) ASC, p.id ASC`.
- [ ] `duration_desc`: posts that have at least one timed video first,
      ranked by their longest matching video duration descending, then
      `published DESC, p.id DESC`.
- [ ] `duration_asc`: posts with timed video first, ranked by their shortest
      matching video duration ascending, then `published DESC, p.id DESC`.
- [ ] Posts with no timed video sort after timed posts for both duration
      modes. Within every post, media stay in viewer/position order.
- [ ] The selected sort is preserved in the pager, filters and viewer return
      URLs.
- [ ] Keep the existing keyword whitelist. User input never reaches the SQL
      `ORDER BY` string.

**Query shape and performance**

- [ ] Prefer one grouped query for the page of posts and one batched query
      for their media, or one CTE that returns both. The 60-tile page budget
      from T4.7 still applies; this page may show more tiles when a post has
      many media, but the common 20-post page should stay under ~300 ms on
      the reference archive.
- [ ] Verify the query plan uses `files_kind`, `files_post` and
      `posts_published` where appropriate. If a new composite index is
      needed for `(post_id, kind, position)`, add a migration and test it.
- [ ] Page through deep offsets by post ID without the old media-offset
      scan regressing.
- [ ] Add a query-count or SQL-trace test proving the route does not issue a
      query per section.

**Markup**

- [ ] Replace the flat `.gallery-grid` with a list of post sections:
      `<section class="gallery-post" aria-labelledby="gallery-post-{id}">`
      containing a header and one `.gallery-grid` for that post's media.
- [ ] Section header:
      - `<h2 id="gallery-post-{id}">` with a link to the post page;
      - publication date (`<time>`) and the count of matching media in this
        section ("4 media", "1 image", etc.);
      - an "Open post in viewer" link to
        `/c/{creator_id}/viewer?post={service_id}&i=0&from=gallery&next=…`
        with `data-viewer-open` and a unique `data-viewer-focus` for the
        header link.
- [ ] Tiles inside the section:
      - use the T4.10 viewer link (`?post=&i=`) with the tile's true
        `viewer_index`, plus `data-viewer-focus="#gallery-{sha256}"`;
      - keep the T4.9 icon-only bookmark control as a sibling of the
        thumbnail anchor;
      - show filename, dimensions and size in the caption instead of
        repeating the post title;
      - keep the play glyph and duration/kind badges for video/GIF tiles.
- [ ] Give section headers enough space and a clear rule/background to scan
      quickly. The grid remains responsive (2 columns on a phone, 4–6 on
      desktop) and keeps the NSFW blur from `.thumb`.
- [ ] Each section must be a landmark-friendly heading level under the page
      `h1`; do not skip from `h1` to `h3`.
- [ ] Empty state stays the same: no media at all vs no media matching
      filters, with the existing clear-filters link.
- [ ] The header copy says the gallery is grouped by post (e.g. "1 284 images
      across 782 posts") and the pager noun becomes `posts`.

**Pager and URL**

- [ ] `_gallery_pager()` receives the post total and renders
      "N posts" rather than "N media".
- [ ] `?page=N` selects a page of **posts**. Page 1 contains the newest 20
      posts (for `newest`) and every media item of those posts that matches
      the filters.
- [ ] Clamp `page` to the post page count as today.
- [ ] Keep filters, sort and page in `filters.url_for()` so bookmark `next`
      URLs, viewer return URLs and pager links all round-trip.
- [ ] Old bookmarked `?page=N` URLs are allowed to point at different content
      after this change; no compatibility shim is required. Say so in the
      ticket resolution when implemented.

**Tests**

- [ ] Render: 3 posts with multiple media produce 3 `<section
      class="gallery-post">` elements with the correct headings, dates,
      counts and media in `position, id` order.
- [ ] Cross-post duplicate: the same `sha256` on two posts appears once in
      each section; no global dedupe and no "in N posts" text.
- [ ] Pagination: 21 posts with media yield 20 sections on page 1 and 1 on
      page 2; `total` is 21 posts; no post is split across pages. A single
      post with 10 media stays whole on one page.
- [ ] Filters: a post with one matching video and one non-matching image
      renders one video tile and the correct count; a post with no matching
      media is omitted entirely.
- [ ] Viewer index: a post containing image, audio, GIF and video, filtered to
      videos only, still links the video tile to the index the viewer renders
      for that post.
- [ ] Sort: `newest`/`oldest` order sections by post date; duration sorts put
      timed posts first in the documented order and keep in-post media order.
- [ ] Stats: header media counts remain unchanged after grouping; the page
      reports the correct number of post groups.
- [ ] Empty states and unknown creator 404 stay green.
- [ ] Query-count/SQL-trace test: one page does not issue per-post or per-tile
      queries.
- [ ] Update the T4.7, T7.2 and T7.6 tests that assume a flat 60-media grid
      or global dedupe. Keep the bookmarks library tests unchanged.
- [ ] Browser acceptance in Chromium and Firefox at 390 px and desktop:
      sections scan clearly, no horizontal scroll, filters/sort/page round-trip,
      a tile opens the exact viewer item, and closing returns to the same
      section/page.

## Acceptance criteria

- [ ] The gallery is visually grouped by post, with one heading per post and
      that post's media together.
- [ ] Pagination is by post, 20 posts per page; no post is split across a
      page boundary.
- [ ] The same image on two posts appears in both sections; there is no
      archive-wide sha dedupe on this page.
- [ ] Filters still select posts/media correctly, and a post with no matching
      media disappears.
- [ ] Every tile still opens the viewer at the exact media item, including
      when filters hide earlier media in the same post.
- [ ] Header media totals remain accurate, and the pager reports posts.
- [ ] No N+1 gallery queries; the common page stays within the T4.7
      performance budget.
- [ ] Existing bookmark, viewer, post, creator and bookmarks-library behavior
      remains green.

## Out of scope

- Global dedupe, "also in N posts" links, or a cross-post duplicate badge.
- Collapsible sections, masonry, infinite scroll or per-post lazy loading.
- Threading/replies, post text/captions, or a post-detail card inside the
  gallery.
- Changing the bookmarks library grid or the post page.
- A cross-creator gallery.
- Reordering media inside a post independently of the viewer.

## Notes

- The old query's `GROUP BY f.sha256` is the reason the page cannot group by
  post. Remove that grouping from the gallery page path rather than trying to
  regroup its output.
- `files` has `UNIQUE(post_id, sha256)`, so a post cannot duplicate a file.
  Cross-post duplicates are the intended repeated case.
- `viewer_index` must be computed before the media filters are applied.
  Otherwise a `kind=video` page would link a tile to index 0 even when the
  viewer shows it after earlier images.
- Duration sorts now order posts, not individual thumbnails. This is the
  only sane interpretation once sections are the unit; document it in the
  UI/README if the label "Longest first" becomes ambiguous.
- The gallery header's "Open viewer" link still opens the post's first item;
  per-post headers add a second entry point at item 0, while tiles target the
  exact item.
- T4.10's shared viewer-index helper should be reused here; do not duplicate
  the position/kind logic in the template or route.
