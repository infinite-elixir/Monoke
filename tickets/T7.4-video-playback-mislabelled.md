# T7.4 — Post page playback for normalized video-backed attachments

## Goal

Use the normalized media kind from T7.1 everywhere the post page decides how to
play an attachment. An MP4-backed `gif` must render and play as a video, not as
a broken `<img>`.

## Why

`loadAttachment()` (`static/app.js:144–182`) branches on `data-kind`:

- `video` → `<video>`
- `image` / `gif` → `<img>`

The reference post `85478926` emits `data-kind="gif"` with
`data-full-src=".../original.mp4"` and no `data-variants`. Clicking **Load**
sets an MP4 URL as an `<img src>`, so nothing plays. The server only emits the
video branch and `data-variants` when `file.is_video`, which is
`kind == "video"` (`routes._decorate_files`). This is a direct consequence of
the mislabelled kinds fixed in T7.1, and the UI must consume the fixed value.

## Scope

**Server (`routes._decorate_files`, `post.html`)**

- [ ] Decide `is_video` / `is_image` / `is_audio` from the normalized
      `files.kind` and, defensively, from `mime_type` + variant extensions. A
      row with a video mime or an `.mp4` variant is a video even if `kind` is
      something else.
- [ ] Emit `data-kind` from the same decision used to render the media element,
      so the two can never disagree.
- [ ] Emit `data-variants` for every video-backed file with variants, not only
      `kind='video'`. MP4-backed gifs should get the variant selector.
- [ ] Render `<video>` for MP4-backed gifs; keep `<img>` for real `.gif` files
      (animated GIFs still animate in an `<img>`).
- [ ] Keep `file.url` as the original variant URL and the selector's first
      option matching it.
- [ ] Add a visible type label that matches reality (`video`, not `gif`), or
      keep the badge but show `gif (mp4)`; do not label a playable MP4 "gif"
      without qualification.

**Client (`static/app.js`)**

- [ ] If `kind` is video but the row contains no `<video>`, fall back to the
      media element that exists instead of silently doing nothing.
- [ ] Changing the variant selector while a video is already loaded must switch
      `src` and reload, not only before the first Load.
- [ ] Leave the existing "Load only on click" invariant intact: no media `src`
      until the user presses Load.

**Tests**

- [ ] Template/route test: a file with `kind='video'` emits `data-kind="video"`
      and a `<video>` element.
- [ ] Template/route test: a real gif (`original.gif`) emits `data-kind="gif"`
      and an `<img>`.
- [ ] Template/route test: an MP4-backed file (`kind='gif'`, `original.mp4`,
      duration set) emits `data-kind="video"`, a `<video>`, and
      `data-variants`.
- [ ] A synthetic `kind='image'` + `video/mp4` row is treated as video.
- [ ] Existing post-page tests still pass.

## Acceptance criteria

- [ ] Post `85478926` shows a video element and plays `original.mp4` after
      pressing Load.
- [ ] Post `171430071` (creator 1, real `.gif`) still renders an `<img>` and
      animates.
- [ ] No attachment labelled `video` by the server can be routed into the
      `<img>` branch by the client.
- [ ] Variant switching works before and after the first load.
- [ ] No full-size media request is made before Load.
- [ ] All post-page tests pass.

## Out of scope

- Normalizing the database (T7.1).
- Gallery rendering (T7.2).
- A general-purpose media player, transcoding, or download support.

## Notes

- This ticket is intentionally small: once T7.1 lands, most rows are already
  correct; the remaining work is making the UI derive its behaviour from the
  normalized value rather than re-implementing `kind == "video"` checks.
- Check `style.css` for `.media-slot` sizing so swapping `<img>` for `<video>`
  does not shift the layout.
