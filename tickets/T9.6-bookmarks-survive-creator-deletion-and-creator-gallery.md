# T9.6 — Bookmarks survive creator deletion, and a creator-scoped bookmark gallery

## Goal

Two related changes:

1. **Deleting a creator must not delete the user's bookmarks.** The archive
   (posts, files, links, tags, runs) is deleted as it is today, but every local
   post and media bookmark that pointed into that archive stays in
   `/bookmarks`, with enough snapshot data to keep rendering after the joins
   disappear.
2. **A creator-scoped bookmark gallery.** A **Bookmarks** button next to
   **Gallery** opens this creator's bookmarks in a creator-framed page, with the
   same All / Posts / Media tabs, instead of dumping the user into the global
   library.

## Current behaviour (verified)

- `delete_creator()` is a single `DELETE FROM creators WHERE id = ?`
  (`src/monoke/db.py:434`). The UI reaches it from the creator header form
  (`src/monoke/web/templates/creator.html:38`) via `_delete_creator()`
  (`src/monoke/web/routes.py:1150`).
- `posts.creator_id` is `REFERENCES creators(id) ON DELETE CASCADE`, so deleting
  a creator deletes all posts, and `files`, `links`, `tags`, `runs` cascade
  behind posts.
- Both bookmark tables also cascade from the creator:
  - `post_bookmarks.creator_id` and `post_bookmarks.post_id` are
    `ON DELETE CASCADE` (`_V6`, `src/monoke/db.py:178`);
  - `media_bookmarks.creator_id` is `ON DELETE CASCADE`.
- `tests/test_db.py:84`, `tests/test_ui.py:391` and
  `tests/test_bookmarks.py:113` currently **assert** that deletion removes
  bookmarks. Those assertions become wrong and must be rewritten, not deleted.
- `list_post_bookmarks()` and `list_media_bookmarks()` join `creators`, `posts`
  and (for media) `files`. Once those rows are gone the bookmark cannot render:
  the post title, thumbnail, service id, media URL and kind all disappear.
- `_bookmarks_context()` already supports `?creator=<id>`, but a deleted
  creator is indistinguishable from a live one and every card links to a
  now-404 post page.
- `bookmarks.html` already has post cards, media tiles, tabs, pagers and removal
  forms. There is no creator-scoped bookmark route and no button for it on
  `creator.html` or `gallery.html`.

## The core design decision (read this first)

Keeping a bookmark after deleting its creator means deciding **what survives**:

| Option | What it means | Cost |
|---|---|---|
| **A. Tombstone creator + snapshots** (recommended) | Keep the `creators` row with `deleted_at` set. Delete posts/files/links/tags/runs. Bookmark rows keep `creator_id`, plus a snapshot of post/media fields so they render without joins. | One migration, query changes, "deleted" badges. |
| B. Fully denormalised bookmarks | Delete the creator row; bookmark rows carry `service`, `service_id`, name and all media/post snapshots; `creator_id` becomes nullable. | Harder uniqueness, no clean re-add, more migration code. |
| C. Soft delete everything | Keep creator, posts, files and bookmarks; just hide the creator from lists. | Nothing is actually deleted; "Delete" stops meaning delete. |

**This ticket assumes A.** It is the smallest change that satisfies "delete the
archive, keep the bookmarks", keeps `(creator_id, sha256)` and
`UNIQUE(post_id)` meaningful, and gives re-adding the same creator a clean
identity to reattach to. If you want B or C, stop and answer the questions at
the end before implementing.

Even under A, `post_bookmarks` cannot keep `post_id ... ON DELETE CASCADE`:
the post row really is deleted. It must become `ON DELETE SET NULL`, with the
post identity snapshotted at bookmark time.

## Scope

### 1. Schema v7 (`db.py`)

- [ ] Bump `SCHEMA_VERSION` to `7`; append `_V7` to `MIGRATIONS`; do not edit
      `_V1`–`_V6`.
- [ ] `ALTER TABLE creators ADD COLUMN deleted_at TEXT` (NULL = live).
- [ ] Add a partial index for the live list:
      `CREATE INDEX creators_live ON creators(deleted_at, last_synced_at DESC)`
      (or the equivalent query plan for `list_creators`).
- [ ] Rebuild `post_bookmarks` (SQLite cannot drop a foreign key in place) with:
      - `id INTEGER PRIMARY KEY`
      - `creator_id INTEGER REFERENCES creators(id) ON DELETE SET NULL`
      - `post_id INTEGER REFERENCES posts(id) ON DELETE SET NULL`
      - snapshot columns: `service TEXT`, `post_service_id TEXT`,
        `title TEXT`, `published INTEGER`, `thumb_url TEXT`,
        `snapshot_at TEXT`
      - `created_at TEXT NOT NULL`
      - `UNIQUE(creator_id, post_service_id)`
      - the existing `(creator_id, created_at DESC, id DESC)` index
- [ ] Backfill the snapshot in the same migration from the live join:
      `posts.service_id`, `posts.service`, `posts.title`, `posts.published`,
      and the first `files.thumb_url` by `COALESCE(position,0), id` — the same
      thumbnail rule `post_cards()` uses. Do not lose existing bookmarks.
- [ ] Add snapshot columns to `media_bookmarks` with `ALTER TABLE`:
      `service TEXT`, `post_service_id TEXT`, `post_title TEXT`, `kind TEXT`,
      `mime_type TEXT`, `url TEXT`, `thumb_url TEXT`, `width INTEGER`,
      `height INTEGER`, `duration_ms INTEGER`, `original_filename TEXT`,
      `bytes INTEGER`, `snapshot_at TEXT`.
- [ ] Backfill media snapshots from the deterministic attachment the current
      list query already picks (`lowest files.id` for that creator+sha).
- [ ] Keep `UNIQUE(creator_id, sha256)`.
- [ ] Migration must be idempotent in the project's existing style (the runner
      applies each version once) and must not touch `api_cache` or
      `link_resolutions`.

### 2. Snapshot lifecycle

- [ ] `toggle_post_bookmark()` writes the snapshot on insert, not only at
      deletion time. A bookmark created while the archive exists is already
      self-contained.
- [ ] `toggle_media_bookmark()` writes the media/post snapshot on insert.
- [ ] Add `refresh_bookmark_snapshots(conn, creator_id)` (or equivalent) called
      at the end of a successful sync, so a re-sync updates titles, URLs and
      thumbnails while the archive is still present. Failure to refresh must
      never delete a bookmark.
- [ ] Never blank a snapshot with a NULL from upstream: use `COALESCE`.
- [ ] `snapshot_at` records when the snapshot was last confirmed, for the
      "snapshot from <relative time>" label on orphaned cards.

### 3. Deletion flow

- [ ] Change `delete_creator()` to, in one transaction:
      1. `UPDATE creators SET deleted_at = now_iso() WHERE id = ? AND deleted_at IS NULL`;
      2. delete the creator's posts (rows; `files`, `links`, `tags` cascade);
      3. delete the creator's runs;
      4. **leave `post_bookmarks` and `media_bookmarks` alone**.
      Return `False` when the creator does not exist or is already deleted.
- [ ] `get_creator()` continues to return tombstones so bookmark queries keep
      their name; add `get_live_creator()` (or an `include_deleted=False`
      argument) for archive routes.
- [ ] `_creator_or_404()` uses the live lookup: `/c/{id}`, `/c/{id}/rows`,
      `/c/{id}/gallery`, `/c/{id}/links`, `/c/{id}/sync`, `/c/{id}/delete`,
      `/c/{id}/bookmarks` and the bookmark toggle routes 404 for a deleted
      creator's archive. `/bookmarks?creator={id}` stays valid.
- [ ] `list_creators()` excludes tombstones. Link creator facets, the dashboard
      count and any "creators" picker exclude tombstones.
- [ ] `bookmark_creator_facets()` and `bookmark_overview()` still include
      tombstones, with a `creator_deleted` flag.
- [ ] Update the delete confirmation copy in `creator.html`:
      "Delete {name} and every post, link and file in this archive? Your
      bookmarks for this creator are kept."
- [ ] Re-adding the same `(service, service_id)` finds the tombstone,
      clears `deleted_at`, reuses the same `creator_id`, and relinks orphaned
      post bookmarks whose `post_service_id` reappears. Add
      `relink_post_bookmarks(conn, creator_id)` and call it after a successful
      sync (and in `save_post_bundle`, or once at sync end).
- [ ] The media bookmarks reattach automatically because they key on
      `(creator_id, sha256)`; the next sync recreates the files.

### 4. Repository and query changes

- [ ] `list_post_bookmarks()` becomes a `LEFT JOIN posts` (and still
      `JOIN creators`). Select
      `COALESCE(p.service_id, pb.post_service_id)` etc. Add `orphaned = 1`
      when `pb.post_id IS NULL` (or the post row no longer exists), and
      `creator_deleted` from `c.deleted_at`.
- [ ] `list_media_bookmarks()` becomes `LEFT JOIN files` and selects
      `COALESCE(f.kind, mb.kind)`, `COALESCE(f.url, mb.url)`, … . The current
      `missing = 1 if not url` rule stays for "file vanished upstream", but an
      orphaned media bookmark with a snapshot URL is **not** missing: it renders
      the last known thumbnail/url and gets an "archive deleted" badge.
- [ ] Decide and document the difference between `missing` (the file is no
      longer attached) and `orphaned` (the creator archive was deleted). Do not
      conflate them in the template.
- [ ] `bookmark_overview()` and `bookmark_creator_facets()` use the same
      `COALESCE` fields and expose `creator_deleted`.
- [ ] `bookmarked_post_ids()` / `bookmarked_media_shas()` keep working for live
      creators; no behaviour change.
- [ ] `_CREATOR_NAME_SQL` stays the name source (tombstone row has it); do not
      append "(deleted)" in SQL — expose a flag and let the template render the
      badge.
- [ ] All list queries keep the current bounded-query guarantee: no query per
      creator, no query per bookmark.

### 5. Orphan removal

- [ ] A bookmark whose creator archive is gone must still be removable.
      `toggle_post_bookmark(conn, creator_id, post_service_id)` cannot work for
      an orphan because there is no post row; removal needs a bookmark-id path.
- [ ] Add `remove_bookmark(conn, kind, bookmark_id)` for `bookmarks.html` (or a
      scoped `POST /bookmarks/remove` endpoint) that deletes by primary key and
      is limited to the current local library. The form must carry the same
      `next` URL so removal returns to the same tab/filter/page.
- [ ] Removal of a media bookmark by `(creator_id, sha256)` keeps working for
      tombstones; removal of a post bookmark by id is the new path.
- [ ] Live items may keep using the existing toggle endpoints; the library may
      use the by-id removal for both kinds for consistency.

### 6. `/bookmarks` presentation

- [ ] Orphaned post cards do not link to a deleted post page. Render the
      snapshot thumbnail and title, the creator name, an "archive deleted"
      badge, and the "Bookmarked …" line. No broken `<a href="/c/.../p/...">`.
- [ ] Orphaned media tiles open the viewer using the snapshot URL/thumbnail
      (if present) and show the "archive deleted" badge. The post-title link is
      omitted or plain text when `post_service_id` no longer has a live post.
- [ ] If a snapshot has no URL at all, fall back to the existing
      "No longer attached" placeholder; it must remain removable.
- [ ] The creator filter lists tombstones too, labelled
      `Name (deleted)`, so a user can find exactly the bookmarks that survived.
- [ ] Creator section headers link to `/c/{id}` only when the creator is live;
      otherwise render a plain name plus the badge.
- [ ] The bookmarks viewer playlist (`/bookmarks/viewer/data`, T11.10) includes
      orphaned media using snapshot fields and tolerates `post_url = null`; no
      JS exception when the creator is gone.

### 7. Creator-scoped bookmark gallery

- [ ] Add `GET /c/{creator_id}/bookmarks` with `view=all|posts|media` and

- [ ] No global creator `<select>` on this page.
- [ ] Empty state names the creator and explains how to bookmark, with a link

- [ ] Extract the shared library markup into a partial (e.g.

- [ ] Add a **Bookmarks** button **next to Gallery** in `creator.html`'s

- [ ] Add the same button to `gallery.html`'s `.creator-actions` next to Posts

- [ ] Decide whether a zero-bookmark creator still shows the button (see

## Acceptance criteria

- [ ] Deleting a creator removes their posts, files, links, tags and runs, and
      **no bookmark**.
- [ ] Every preserved bookmark is still visible in `/bookmarks`, grouped under
      the creator's name, marked as belonging to a deleted archive, and
      removable.
- [ ] No preserved card or tile links to a 404.
- [ ] Re-adding the same creator brings the old bookmarks back against the new
      archive where the posts/media still exist.
- [ ] A **Bookmarks** button next to **Gallery** opens
      `/c/{id}/bookmarks`, showing that creator's bookmarks in the creator
      frame with working tabs, paging and removal.
- [ ] All of the above works with JavaScript disabled.
- [ ] `uv run pytest` is green.

## Out of scope

- Bookmark search, folders, tags, notes, bulk removal, export/import.
- Preserving the full textual archive (captions, links, tags) after deletion —
  only the bookmark snapshot survives.
- Undo/restore for deletion beyond re-adding the creator.
- Changing `cum.st`'s upstream `bookmarked` flags; these are provenance only.
- A generic "deleted creators" admin page or garbage collection of tombstones.

## Notes / implementation traps

- SQLite requires a table rebuild to change `post_bookmarks.post_id` from
  CASCADE to SET NULL. Do the rebuild with an explicit new table, copy, drop,
  rename, recreate indexes, all inside the migration transaction.
- `UNIQUE(post_id)` must become `UNIQUE(creator_id, post_service_id)`: with
  `post_id` nullable, SQLite treats NULLs as distinct and a stale unique index
  would silently allow duplicates.
- Do not snapshot `thumb_url` only; snapshot `url` too, or an orphaned media
  bookmark cannot open the viewer.
- Keep `missing` and `orphaned` distinct. A live creator whose file vanished
  upstream is `missing`; a deleted creator is `orphaned` even if the snapshot
  URL still resolves.
- `_creator_or_404()` is used by the toggle routes. If it starts rejecting
  tombstones, orphan removal via the new by-id endpoint must not route through
  it.
- The gallery page's action row is inside `gallery.html`, not the shared
  `creator.html` header; both need the button if "near the gallery" means the
  gallery screen too.
- Existing `post_bookmarks` rows have `post_id`; backfill before the FK is
  relaxed so the snapshot is complete.

## Grill: answer these before starting

These are the guesses baked into the scope above. Each one changes the schema
or the UI, so answer them first.

1. **What does "delete" mean?** Hard-delete the archive and keep a tombstone
   creator row (recommended), fully denormalise and delete the creator row, or
   soft-delete everything and keep the posts? If you expect disk space to be
   freed, only A/B qualify.
2. **Are post bookmarks also preserved, or only media bookmarks?** A post
   bookmark without its post can only be a dead snapshot card: title, date,
   thumbnail, creator name, "archive deleted". Is that still useful, or should
   post bookmarks be dropped and only media kept?
3. **How much snapshot data do you want?** Minimum identity (creator/service/
   post id) versus a full render snapshot (title, thumbnail, media URL, kind,
   dimensions, duration, filename). Without a full snapshot the surviving
   bookmarks look like grey "no longer attached" boxes.
4. **Do snapshot URLs stay usable after deletion?** They are the original
   remote edge URLs; they may expire, 403 or be taken down. Is showing a
   possibly-dead remote image acceptable, or should orphaned media always show
   a placeholder?
5. **Re-adding the same creator: auto-revive and relink, or leave the old
   bookmarks orphaned forever?** Auto-revive needs `(service, service_id)` as
   the stable identity and a relink step after sync.
6. **Where exactly is the button, and what does "creator page itself" mean?**
   - (a) button in the creator header next to Gallery → navigates to a new
     `/c/{id}/bookmarks` page (my read of your request);
   - (b) button → `/bookmarks?creator={id}` (reuses the global page, leaves the
     creator frame);
   - (c) an in-page tab on `/c/{id}` that swaps Posts for Bookmarks without a
     navigation (htmx);
   - (d) only in the gallery page's action row, showing media bookmarks only.
   Also: should it show both posts and media, or media only because it sits
   next to a media gallery?
7. **Delete button semantics.** Should the existing Delete button become
   "Delete archive (keep bookmarks)" and stay one click, or gain a second
   confirmation that explains what survives? Should a creator with zero
   bookmarks still get a tombstone row?
8. **Removing an orphaned bookmark.** Is a new local `/bookmarks/remove`
   endpoint acceptable, or do you want to keep every removal on the
   `/c/{id}/p/.../bookmark` URL shape even when the creator is gone?
9. **Are tombstones visible in the creators list?** Recommendation: no, but
   they remain selectable in the bookmarks creator filter as `Name (deleted)`.
   Do you want a separate "deleted creators" list to restore/manage them?
10. **Scope check.** Is this one ticket (schema + deletion + library + new
    creator page), or should it split into T9.6a (data preservation) and T9.6b
    (creator-scoped gallery button)? The two touch the same templates but can
    ship independently.
