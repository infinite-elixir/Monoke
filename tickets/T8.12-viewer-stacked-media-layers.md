# T8.12 — Stack the viewer media layers and unstick the swipe

## Goal

T8.11 rebuilt the swipe geometry on the measured media box, but the manual
browser pass shows the gesture is still unusable: the media does not follow
the finger smoothly, a large black band appears between the outgoing and the
incoming image, and a vertical swipe moves the current image **sideways** and
leaves the other post in the wrong corner.

The blocker is not the gesture maths (that part is now correct) — it is the
**layout of the media host**. The host is a flex row, so the moment the drag
adds the second layer, the browser re-lays the two media **side by side**
instead of stacking them. Every symptom the user sees follows from that one
fact.

This ticket fixes the stacking first, then removes the remaining stiffness
(dead zone, decode delay, commit snap) and adds the browser-level checks that
would have caught this.

## Decisions (agreed with the user, 2026-10-21)

1. **No black band between images.** The incoming media is placed flush
   against the current media's edge. The stage is already black, so a flush
   join reads as one continuous surface.
2. **The vertical axis follows the finger.**
   - Swipe **up** → the **older** post comes from **below**.
   - Swipe **down** → the **newer** post comes from **above**.
   This is direct manipulation, and it matches the archive list order (the
   newest post is at the top of the creator page). The keyboard, the wheel
   and the first-run hint flip with it, so there is **one** vertical meaning
   everywhere:
   - `ArrowUp` = older post, `ArrowDown` = newer post
   - wheel up = older post, wheel down = newer post
   - hint: `↑ Older post`, `↓ Newer post`
   The T8.9 transition plan already matches this model (`next-post` = older
   enters from below, `prev-post` = newer enters from above) and stays as it
   is; what flips is which action the **drag**, the **keys** and the **wheel**
   trigger.
3. **Vertical reveal is one axis only**, and the drag never produces
   horizontal movement.
4. Browser coverage for the manual pass: **Firefox desktop** and **Android
   Chrome (touch)** (the two the user tested with).

## Reported symptoms (manual pass, 2026-10-21)

- Swiping left "gets stuck sometimes with a big black space in between". The
  black band is **consistent** in size, which points at layout, not at a
  threshold.
- Swiping **down**: the current image moves **left** and is only half visible
  with black space on the right; the other post's image sits in the **top
  right** with half black space on the left.
- The whole gesture feels "stiff" rather than finger-following.

## Root cause (verified in a real browser, not guessed)

`src/monoke/web/static/style.css`:

```css
.viewer-media {
  display: flex;
  align-items: center;
  justify-content: center;
  width: 100%;
  height: 100%;
}
.viewer-media-el {
  width: auto;
  height: auto;
  max-width: 100%;
  max-height: 100%;
  object-fit: contain;
}
```

`.viewer-media` is a **flex row**. With one child (the current media) the row
is harmless: the image is centred and sized to its own box. With two children
(current media + drag preview) the flex algorithm:

1. lays the two images **next to each other** (row direction), not on top of
   each other;
2. shrinks both of them, because their combined base size exceeds the
   container (`flex-shrink: 1` is the default);
3. therefore **re-renders both images at roughly half their width**, and
   `object-fit: contain` letterboxes them inside their new, smaller boxes →
   the "half visible with black space" appearance.

Because the media are re-laid out at the moment the preview is inserted, three
things break at once:

- the box measured at `pointerdown` (single media, full size) is **stale**
  the moment the preview appears, so the flush-join step is wrong and a black
  band opens up between the two images;
- the current media **jumps left** into the first flex column — exactly the
  "the current image goes left" report;
- the preview lands in the second flex column, i.e. the **top right** corner
  of the stage, exactly as reported.

The same bug is in the T8.9 transition: during a keyboard/wheel navigation
the outgoing and incoming media also sit side by side and shrink, so the
"fluid transition" has been quietly broken too.

Reproduction (Firefox 158, 1000×800 stage, one 1600×900 and one 900×1600
image, the current CSS): the two images are rendered as two columns, each
about half the stage wide. The same markup with the grid overlay described
below renders both images at their correct size, overlapping in one cell.

## Evidence

- `/tmp/opencode/layout-flex.html` → screenshot `layout-flex.png`: the flex
  row puts the landscape image in the left column and the portrait image in
  the right column, both squeezed.
- `/tmp/opencode/layout-grid.html` → screenshot `layout-grid.png`: with

## Research before coding

A short pass over how the reference experiences and the platform do this, and
what to copy:

- **The pager model.** Instagram's carousel and X's media viewer are a
  *viewport plus a track*: the viewport clips, the track holds page-sized
  children, and the children are laid out **along one axis and clipped**, not
  stacked as independent centred layers. The current and the next item are
  neighbours *in the same track*, which is what makes them look glued
  together. Copy the model, not the pixels.
- **Overlapping siblings in CSS.** The idiomatic way to make several children
  share one centred box is CSS Grid: `display: grid` with a single cell and
  `grid-area: 1 / 1` on every child, plus `place-items: center` to centre
  them. CSS-Tricks ("Positioning Overlay Content with CSS Grid") documents
  exactly this carousel/overlay pattern, and notes that `overflow: hidden` on
  the container is what keeps the sliding content clipped to the viewport.
  Absolute positioning (`position: absolute; inset: 0`) is the alternative,
  but it forces the centring to move into the `transform`, which would fight
  the drag transform this viewer already uses.
- **A viewport that clips.** Real pagers clip the track: the outgoing media
  must leave the frame, the incoming one must not paint over the viewer
  chrome (close/fullscreen buttons). `overflow: hidden` on the host gives
  that for free.
- **Reserve the space before the bytes arrive.** An `<img>` without dimensions
  has no box until it decodes, so a freshly inserted preview is invisible (and
  unmeasurable) for a frame or two. The `width`/`height` attributes (or
  `aspect-ratio`) reserve the box up front — the standard "sizing hints" fix
  for layout shift.
- **Direct manipulation beats list semantics.** The vertical axis here follows
  the finger (drag up → what is below, drag down → what is above) instead of
  the keyboard's list semantics. That is the same choice Instagram Reels
  makes (drag up → the next reel, which comes from below) and it keeps the
  drag and the transition consistent.
- **Velocity and snapping** stay as in T8.10/T8.11: sample the last ~100 ms,
  commit on distance or velocity, otherwise spring back.

## Scope

**A. Stack the media layers (the blocker)**

- [ ] Turn `.viewer-media` into a **grid viewport**: one row, one column,
      `place-items: center`, and `overflow: hidden` so the sliding media are
      clipped to the stage.
- [ ] Put every media layer in the **same grid cell** (`grid-area: 1 / 1`),
      including the `.viewer-unavailable` fallback box, so a second layer can
      never re-lay the first one.
- [ ] The layers must keep their own rendered size: no flex shrink, no
      letterbox inside a shrunk box. A wide landscape image and a tall
      portrait image must each render at their natural fitted size.
- [ ] The stage must not scroll, bounce or grow: the host is a fixed
      viewport, the media are the only things that move.
- [ ] Update the stylesheet test that asserts the media host's layout.

**B. Re-measure after the layout is fixed**

- [ ] The drag geometry must use the **real rendered box** of each layer,
      measured after the layer is in the DOM. The metadata fit is only a
      fallback for media without `width`/`height`.
- [ ] The preview must be positioned **before it is painted** (same task as
      the axis lock) and must not change the layout of the current media when
      it appears.
- [ ] A late decode that reports a different size corrects the shared step
      once, with no timer and no visible jump.

**C. Make the drag feel continuous**

- [ ] The current media follows the finger 1:1 from the first frame of the
      drag; no easing, no reflow, no jump when the neighbour appears.
- [ ] The incoming media is visible **as soon as the drag starts**. If it is
      not decoded yet, its box must still be reserved (`width`/`height`
      attributes from the payload) so the reveal is geometrically correct
      from the first frame instead of showing a black hole that later fills.
- [ ] Decide whether to **pre-stage the neighbour layer** (mounted, hidden and
      decoded while the current media is on screen) so the reveal is instant.
      If yes: at most two media elements at any time, the hidden layer is
      removed/refreshed when the current item changes, and nothing is fetched
      merely to preview.
- [ ] The commit animation must continue the drag: the incoming layer starts
      the T8.9 transition **from its current drag offset** and the outgoing
      layer leaves along the same axis. No "jump to centre and restart".
- [ ] The spring-back and the rubber band must keep the existing short
      duration, and reduced motion must still snap instantly.

**D. Dead zone and axis lock**

- [ ] Measure the dead zone: the media must not stay still for longer than
      necessary before it starts following the finger. If the dominance rule
      (1.2) makes short gestures feel unresponsive, revisit the numbers and
      document the change — do not change them silently.
- [ ] The axis must still lock once and never flip, and a vertical gesture
      must never produce horizontal movement.

**E. Flip the vertical axis (one meaning everywhere)**

- [ ] `swipeActionFor("y", delta)`: dragging **up** (`delta < 0`) → the
      **older** post (`next-post`), dragging **down** (`delta > 0`) → the
      **newer** post (`prev-post`).
- [ ] The preview side follows the finger, which the existing
      `swipeOffsets()` already does: a drag up opens the band **below** the
      current media, a drag down opens the band **above** it.
- [ ] `onKeydown`: `ArrowUp` → `next-post` (older), `ArrowDown` →
      `prev-post` (newer).
- [ ] `onWheel`: wheel up → older post, wheel down → newer post.
- [ ] The first-run hint in `viewer.html` flips to `↑ Older post` and
      `↓ Newer post` (and the bookmark variant stays post-free).
- [ ] `transitionPlan` keeps its current signs: `next-post` (older) enters
      from **below**, `prev-post` (newer) enters from **above**. Add a test
      that pins both, so the drag reveal and the key transition can never
      drift apart again.
- [ ] Update the direction contract in T8.3 and the user documentation
      (`docs/INSTALL_AND_USAGE.md`) to the new vertical meaning.

**F. Post-boundary preview**

- [ ] When the neighbouring post's payload is not cached, the vertical drag
      currently previews nothing and shows the black stage. Either accept it
      and document it, or preview the neighbouring post's **edge image**
      (`neighbour_images` from the T8.8 payload) as a stand-in, with the
      caveat that the post's first media may not be an image.
- [ ] The gesture must still not fetch merely to preview.

**G. Browser-level checks (the gap that let this through)**

- [ ] Add a **real-browser** check to the acceptance flow: render the viewer
      with two layers and assert that the two media boxes **overlap** (their
      boxes are not side by side) and that the current media's box does not
      change when the preview is inserted.
- [ ] The fake-DOM harness (`tests/fixtures/viewer_drag_harness.js`) cannot
      catch layout bugs — it has no layout engine. Keep it for the gesture
      logic, but do not treat it as layout coverage.

## Tests

- [ ] Stylesheet test: the media host is a grid viewport with a single cell,
      the layers share that cell, and the host clips its overflow.
- [ ] Layout test (real browser or a headless screenshot comparison): with two
      layers present, the current media's rendered box is **unchanged** and the
      two boxes are not side by side.
- [ ] Node tests for the gesture geometry stay green: axis lock, flush edges,
      letterbox fit, rubber band.
- [ ] Direction tests: swipe up → older post, swipe down → newer post;
      `ArrowUp` → older post, `ArrowDown` → newer post; wheel up → older,
      wheel down → newer; `next-post` enters from below, `prev-post` from
      above. One test pins the whole contract so a refactor cannot invert one
      input method only.
- [ ] Fake-DOM harness stays green (its vertical expectations must be
      updated to the new mapping).
- [ ] A regression test that the current media's measured box is not affected
      by the presence of a second layer (the exact bug of this ticket).
- [ ] Server tests for the viewer route/markup stay green; the payload and URL
      contract must not change. The hint markup changes, so the hint test
      changes with it.

## Acceptance criteria

- [ ] A horizontal drag shows the neighbour flush against the current image's
      edge, with **no black band between them** and no first-frame jump.
- [ ] A vertical drag **up** moves the current image up and shows the older
      post in the band **below** it; a vertical drag **down** moves the current
      image down and shows the newer post in the band **above** it. Neither
      ever moves horizontally.
- [ ] `ArrowUp`, the wheel and the swipe all mean "older post"; `ArrowDown`,
      the wheel and the swipe all mean "newer post". The hint says so.
- [ ] The current image never changes size or position when the neighbour
      appears.
- [ ] The drag follows the finger 1:1 from the first frame; the commit
      continues the drag instead of restarting it.
- [ ] A wide letterboxed image and a tall portrait image both drag without a
      gap, in both axes.
- [ ] At most two media elements exist at any time, and none are left behind.
- [ ] Reduced motion still tracks the finger and snaps on release.
- [ ] No new dependency, no idle loops/timers, no route or payload changes.
- [ ] The manual browser pass is green in **Firefox desktop** and **Android
      Chrome (touch)**.

## Out of scope

- Pinch zoom, pan, rotate, double-tap zoom.
- Inertial continuation through multiple items.
- Swipe-down-to-dismiss (still conflicts with the vertical axis).
- A visible filmstrip, page dots or drag handle.
- Rebuilding the gallery lightbox.
- Changing the keyboard or wheel thresholds (only their vertical *meaning*
  changes, per decision 2).
- Re-designing the transition timings beyond making them continuous with the
  drag.

## Notes

- The T8.11 manual pass failed because the automated coverage had **no
  layout engine**: the fake-DOM harness proves the *transform maths* but
  cannot see that the two media were laid out in two columns. Any future
  layout change in the viewer needs a real-browser check.
- T8.11's "flush" rule assumed the two media boxes can be placed edge to
  edge. That is only true if both are centred in the same box — hence the
  stacking fix is a prerequisite, not a nice-to-have.
- The media-step (the neighbour is flush with the current media) is kept
  rather than Instagram's page-step (the neighbour is centred in the next
  page, with the page's letterbox visible between them), per decision 1.
- If the neighbour media have different rendered sizes, the join is still
  flush: the centre-to-centre step is the half-sum of the two visible boxes,
  nothing is stretched, and the stage background stays continuous.
- The vertical mapping in T8.11 ("down = older post, up = newer post") is
  **superseded by this ticket**: the vertical axis now follows the finger
  ("up = older post, down = newer post"). The action *names* (`next-post` =
  the older post, `prev-post` = the newer post) keep their meaning, so the
  database/payload code does not change — only the bindings.
- The internal action names now read oddly against the user-facing direction
  (`next-post` = older = "up"). Renaming them (`older-post` / `newer-post`)
  is **not** required by this ticket, but it would remove a permanent source
  of confusion. If it is done, it must touch the payload contract names too
  (`previous_post` / `next_post`), which is a wider change.

## Implementation status

- The media host is now a clipped CSS Grid viewport. Every media layer and the
  unavailable fallback share grid cell `1 / 1`, so inserting a preview cannot
  turn the host into a flex row or resize the current layer.
- Image `width`/`height` attributes reserve the preview box before decode.
  Gesture geometry continues to use the measured current and incoming boxes,
  with one late-load correction for metadata that differs from the rendered
  size.
- The vertical contract is now consistent across swipe, keyboard, wheel and
  hint: up means the older post and down means the newer post. Transition
  signs remain unchanged (`next-post` enters from below and `prev-post` from
  above).
- An uncached neighbouring post intentionally has no drag preview; the gesture
  never fetches solely to paint one. Release still uses the existing post
  navigation/fetch path.
- Automated coverage includes the grid stylesheet contract, reserved image
  dimensions, direction invariant, measured-box geometry and the fake-DOM
  gesture regression harness. Full test suite: 415 passed, 1 skipped.
