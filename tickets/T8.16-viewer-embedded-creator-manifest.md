# T8.16 — Embed the creator viewer manifest and media links

## Goal

Make the creator viewer load with the navigation data it needs, like the
bookmark-only image viewer. The current creator viewer embeds one post and
small neighbour hints, then discovers the next post's JSON through a fetch
while the user is navigating. That request and JSON parse can make a fast
post-boundary move feel slower than moving through the flat bookmark playlist.

The creator viewer should receive a server-rendered manifest of the creator's
eligible media-post navigation and the links needed to resolve each post,
while retaining post-scoped rendering and post paging rather than flattening
the entire archive into one giant media playlist.

## Current behavior

- `/c/{creator_id}/viewer` embeds the current `viewer_state` in
  `#viewer-initial`.
- The state contains the current post's complete eligible media list,
  `previous_post`/`next_post` IDs, and bounded neighbour edge-image hints.
- Crossing a post boundary may fetch `/c/{creator_id}/viewer/data?post=...`
  after the gesture has already started.
- `/bookmarks/viewer` embeds its complete flat media playlist in the initial
  state, so normal next/previous navigation does not need post discovery.

## Scope

### A. Server-rendered creator manifest

- [ ] Add a creator-viewer manifest to the initial payload containing the
      ordered eligible media-post sequence or an equivalent compact navigation
      index.
- [ ] Include each eligible post's service ID, viewer-data URL, position/rank
      metadata, and enough media-link metadata to identify its first/last
      eligible image without a boundary request.
- [ ] Preserve the current post's full media payload, dimensions, ordering,
      bookmark fields, and post metadata exactly as today.
- [ ] Keep the manifest creator-scoped, archive-boundary-aware, and filtered
      to posts with viewer-eligible media; skip text-only posts.
- [ ] Generate URLs through the application's existing route helpers rather
      than concatenating unvalidated user input.

### B. Post paging remains post-scoped

- [ ] Keep the current `state.media` model and post-by-post rendering.
- [ ] A boundary move may apply a manifest entry synchronously when its
      post/media payload is embedded; otherwise it uses the existing
      `/viewer/data` endpoint with the manifest's known URL.
- [ ] Preserve `previous_post`/`next_post` semantics and horizontal/vertical
      direction behavior.
- [ ] Keep `AbortController`, stale-response guards, error flashes, and safe
      fallback behavior for missing or failed post data.
- [ ] Do not flatten every creator media item into one bookmark-style playlist
      in the DOM or viewer layer.

### C. Payload size and loading policy

- [ ] Define and test a bounded manifest/media strategy for large creators;
      do not duplicate the full current-post media list for every manifest
      entry.
- [ ] Reuse the existing payload cache and preload map when promoting an
      embedded post entry.
- [ ] Avoid duplicate JSON/image requests when a manifest entry already
      contains the required data.
- [ ] Preserve bookmark mode's smaller, independent flat-playlist contract.
- [ ] Preserve data-saving, hidden-tab, reduced-data, and archive-boundary
      protections.

### D. Compatibility and observability

- [ ] Keep `/c/{creator_id}/viewer/data` functional for direct paging,
      fallback, and clients with an older or reduced initial payload.
- [ ] Version or feature-detect the manifest shape if necessary; malformed
      manifest data must fall back to the existing post fetch path.
- [ ] Keep URL restoration (`post` + `i`), bookmark toggles, accessibility
      announcements, and return paths unchanged.
- [ ] Add enough debug/test visibility to distinguish manifest hits from
      boundary JSON fetches during browser acceptance.

## Tests

- [ ] Initial creator viewer HTML contains the manifest and all required
      navigation/data URLs for a multi-post fixture.
- [ ] Manifest ordering matches the viewer's archive ordering, including
      text-only post skipping and newest/oldest boundaries.
- [ ] The current post retains its complete media list and exact requested
      index.
- [ ] A boundary move using an embedded manifest entry does not call
      `/viewer/data`; a non-embedded or malformed entry uses the existing
      endpoint.
- [ ] Repeated forward/backward post paging does not duplicate payload or
      image requests.
- [ ] Large-creator payload sizing stays within the chosen manifest bound and
      does not create extra viewer layers.
- [ ] Bookmark viewer payload and behavior remain unchanged.
- [ ] Existing preload, tap-zone, swipe, route, bookmark, and full offline
      test suites remain green.
- [ ] Browser acceptance verifies that a fast boundary move has no
      post-discovery stall and that the network waterfall shows no redundant
      destination request for embedded entries.

## Acceptance criteria

- [ ] On initial creator-viewer load, the browser has the post navigation data
      and required destination links without discovering them only after a
      swipe/tap starts.
- [ ] A boundary move to an embedded post is applied from initial data or an
      already-warmed entry, without waiting for a new post-discovery request.
- [ ] Post paging remains post-scoped, preserves direction semantics, and does
      not turn the creator archive into a single unbounded playlist.
- [ ] Large creators remain responsive and do not receive duplicated full media
      payloads.
- [ ] Missing, stale, malformed, or failed manifest entries degrade to the
      current safe `/viewer/data` path.
- [ ] Bookmark viewer performance and payload contracts are unchanged.

## Out of scope

- Preloading videos, GIFs, audio, or the entire archive's binary bytes.
- Service workers, persistent offline storage, or custom HTTP cache policy.
- Changing creator archive ordering or post-boundary direction semantics.
- Replacing the bookmark viewer's flat playlist model.
- Removing the existing `/viewer/data` endpoint.

## Notes

- The bookmark viewer's advantage is not only image preloading: it embeds the
  complete logical playlist, so navigation does not first discover the next
  item through a post request.
- The implementation should measure manifest size against creator size and
  choose compact post entries over repeating all media metadata everywhere.
- The manifest must own navigation knowledge; the preload map should own
  request/decode readiness. These are related but should not become duplicate
  caches.
