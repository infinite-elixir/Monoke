# T8.19 — Make the viewer filter-, sort- and gallery-context-aware

## Goal

The fullscreen viewer must stay inside the gallery set it was opened from. If
the gallery is showing `Images`, the viewer must contain only images: no videos,
no GIFs, no video posts on the next/previous boundary, and no video preloads.
The same rule applies to every other gallery filter and to the active sort.

The viewer must also know and communicate where it is: which filtered set,
which post, which item, and what the next/previous item will be. The filter must
survive swipes, post crossings, URL rewrites, refreshes and closing back to the
gallery.

## Reported behaviour

- With the gallery's **Images** filter active, opening the viewer still shows
  videos (or starts on one).
- Swiping across a post boundary leaves the filtered set and enters posts that
  do not match the current filter.
- The viewer's counter and post position describe the unfiltered archive, not
  the gallery the user is actually browsing.
- The gallery correctly returns to the filtered page on close, so the filter is
  known at the edges but is lost inside the viewer.

## Current implementation and gaps

- `_gallery_viewer_url()` passes only `post`, `i`, `from=gallery` and `next`.
  `creator_viewer()` reads only `post`, `i`, `from`, `hint` and `quiet`.
  `GalleryFilters` never reaches the viewer.
- The gallery's top-level **Open viewer** link passes `from=gallery` and `next`
  but no starting post or media. The viewer therefore starts at
  `latest_viewer_post()`, which is the newest post with *any* viewer media, not
  the first item on the filtered gallery page.
- `viewer_state()` calls `viewer_media()` with all `VIEWER_KINDS`, and
  `viewer_neighbour()` / `viewer_post_rank()` / `latest_viewer_post()` use the
  unfiltered media set. `kind`, `q`, `tag`, orientation, size and date filters
  are all ignored inside the viewer.
- `_gallery_context()` computes `viewer_index` among *all* viewer media of a
  post before applying the gallery media filter. Under `kind=image`, that index
  includes videos and can point at the wrong item.
- `neighbour_preload_images()` hard-codes `kind = 'image'`, which is right for
  T8.18's still-image window but wrong for a `Videos` or `All media` context
  (video posters need warming) and wrong for filtered media edge selection.
- `viewer/data` has no filter context, so `jump()` and payload prefetch cannot
  preserve it across post boundaries.
- `manifestDataUrl()` builds only `?post=`; `payloadPlan()` only knows post
  ids. Neither carries filter state.
- `replaceUrl()` preserves unrelated query parameters but only rewrites
  `post`/`i` (or `b` in bookmark mode). It does not write or validate a filter
  token.
- `_viewer_return_url()` already preserves the filtered gallery URL from
  `next`; that part works and must remain.
- The counter in `updateCounter()` says "N of M in this post" and "N of M
  media posts" using unfiltered totals.

## Scope

### A. Define an explicit viewer context contract

- [ ] Add a single, server-validated viewer context parameter (recommended:
      a canonical gallery-filter query string, e.g. `gf=kind%3Dimage%26sort%3Dnewest`)
      to the viewer URL and to every `/viewer/data` request.
- [ ] Build the token from `GalleryFilters.pairs()` without `page`, so the
      context stays stable while paging. Keep `next` for the return location.
- [ ] Parse the token with the existing `GalleryFilters.from_query()`
      validation. Unknown or malformed values must be ignored or rejected, not
      reflected into SQL or navigation.
- [ ] Keep `from=gallery` and `next=` validation unchanged.
- [ ] Support the context in both the HTML route and the JSON data route.
- [ ] Keep direct viewer URLs with no context exactly as they are today:
      unfiltered, all viewer kinds.
- [ ] Do not use cookies, sessions or global state; the URL is the source of
      truth.

### B. Scope media, neighbours and rank to the context

- [ ] Add filter-aware variants (or parameters) for:
      `viewer_media`, `viewer_neighbour`, `latest_viewer_post`,
      `viewer_post_rank`, `_neighbour_preload_images` and any manifest helper
      that enumerates media posts.
- [ ] Reuse the gallery predicates for post-level filters (`q`, `tag`,
      date range) and media-level filters (`kind`, `orientation`, `min_bytes`)
      so the gallery and viewer cannot drift.
- [ ] Media in the current post: only items matching the context, in normal
      viewer order (`COALESCE(position, 0), id`).
- [ ] Previous/next post: the nearest post that still has at least one matching
      media item under the context.
- [ ] Post rank and total: position among matching posts, not all media posts.
- [ ] Latest/starting post for a context: the first post in the current
      filtered gallery order, not the newest unfiltered media post.
- [ ] Honour the active sort when crossing post boundaries:
      `newest`, `oldest`, `duration_desc`, `duration_asc`.
- [ ] For duration sorts, compute the sort key from matching media only.
      Images have no duration, so the gallery's existing sort restrictions
      continue to apply.
- [ ] If an explicit `post` has no matching media under the context, choose and
      document one behaviour: fall back to the nearest matching post in the
      filtered order, or show a clear "no media matches this filter" state with
      a return link. Do not silently show unfiltered media.
- [ ] If no post matches at all, return the existing empty/404 behaviour
      without a broken viewer shell.

### C. Fix starting item identity

- [ ] Stop treating the gallery's unfiltered `viewer_index` as the filtered
      index.
- [ ] Prefer a stable media identity in the viewer URL (for example `sha256`,
      with the post id as scope) and resolve the starting index against the
      filtered media list server-side.
- [ ] Keep `i` as a backwards-compatible fallback when no stable id is present,
      but clamp it against the filtered list.
- [ ] Update gallery tile, post-header "Open post in viewer" and top-level
      "Open viewer" links to pass the context and the exact item/post.
- [ ] The top-level "Open viewer" link must open the first matching item on the
      current filtered page, not the newest item in the archive.
- [ ] Refresh and deep links must land on the same filtered item.

### D. Propagate context through navigation and preload

- [ ] Include the context token in the initial JSON payload so `viewer.js` does
      not have to re-parse the page URL.
- [ ] Include it in `manifestDataUrl()` so `jump()` and boundary prefetch keep
      the filter.
- [ ] Include it in `payloadPlan()` and all preload requests.
- [ ] `preloadWindowIndices()` must only warm items that are in the filtered
      media list; filtered-out kinds must never enter the window.
- [ ] Neighbour edge warming must use the context. For an image-only context,
      warm images only. For a video context, warm video posters rather than
      video bytes (coordinate with T8.18).
- [ ] `jump()` to an adjacent post must land on the first/last **matching**
      media item, not the first/last media item overall.
- [ ] Destination checks for gestures (`destinationFor`) must use the filtered
      payload and context-scoped neighbours.

### E. URL, return and UI context

- [ ] `replaceUrl()` must preserve the context token when rewriting `post`
      and the item identity. It must not drop `next`, `from` or `gf`.
- [ ] Closing the viewer returns to the exact filtered gallery page and
      fragment already supplied by `next`.
- [ ] Counter: "Image 3 of 12 in this post" for a kind-filtered context.
- [ ] Announcer: include the filtered post rank ("post 4 of 12 image posts")
      and the current filter/kind in accessible text.
- [ ] Do not add a permanent toolbar; the viewer stays chrome-free. Context may
      be exposed through the existing counter/announcer and page title.
- [ ] If the context token is invalid or the post no longer matches, the return
      link must still work.

### F. Performance and correctness

- [ ] Keep the gallery viewer query count bounded. Do not introduce per-media
      N+1 queries when filtering a post.
- [ ] Add indexes if the filter-aware neighbour/rank queries need them; explain
      each new index.
- [ ] Keep bookmark mode (`state.mode == "bookmarks"`) unchanged and unfiltered.
- [ ] Keep data-saver, reduced-data, hidden-tab and preload bounds intact.
- [ ] Keep the manifest bounded; do not embed the whole filtered archive.

## Acceptance criteria

- [ ] Opening the viewer from any filtered gallery never shows media excluded
      by that filter, including across post boundaries and in preloads.
- [ ] The starting item is the exact tile/post the user activated, resolved
      against the filtered media list.
- [ ] Previous/next navigation follows the filtered gallery order and sort.
- [ ] The filter and item survive swipes, post crossings, URL rewrites and
      refresh; closing returns to the same filtered gallery page.
- [ ] Direct, unfiltered viewer URLs keep their current behaviour.
- [ ] Bookmark mode is unchanged.
- [ ] The viewer remains chrome-free; context is available to assistive tech and
      the existing counter.
- [ ] No new dependency, no session state, no unbounded payload.

## Out of scope

- Redesigning the gallery filter UI or adding new filter types.
- Persisting a "last used filter" across unrelated creator pages.
- Filtering the bookmarks viewer by gallery kind (separate mode).
- Preloading the entire filtered archive as one playlist.
- Replacing the T8.12 gesture model or the T8.18 preload pipeline, beyond the
  context propagation described here.

## Notes

- `next` already encodes the filtered gallery URL. It is a return target, not a
  reliable navigation context for `viewer/data`; use the explicit token.
- `from` is already used for the gallery origin, and gallery date filters also
  use `from`. Do not overload it; the context token avoids that collision.
- Kind filters are media-level, while search/tag/date are post-level. A post
  can match the post filters yet contribute zero media under the kind filter;
  such a post must not become a boundary destination.
- The viewer index is positional. A stable media id is the only safe way to
  survive a filter change or a re-sync between opening the gallery and opening
  the viewer.
