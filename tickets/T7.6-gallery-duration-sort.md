# T7.6 — Sort video sections by duration (longest / shortest first)

## Goal

Every list that shows videos can be ordered by video length. The first and most
important target is the gallery's video view
(`/c/{id}/gallery?kind=video`), which today is fixed to newest-first and cannot
answer "which video is the longest?" or "show me the short clips". The sort must
be URL-encoded, bookmarkable, preserved across pagination, and correct for
attachments whose duration is unknown.

## Current behaviour

- `GalleryFilters` (`src/monoke/web/filters.py`) has no `sort` field; the SQL in
  `db.list_gallery_images()` hard-codes
  `ORDER BY published DESC, COALESCE(f.position, 0), f.id`.
- The gallery template has Kind, Tag, Orientation, Minimum size and date
  filters, but no sort control.
- `files.duration_ms` already holds the duration for videos (and for real GIFs
  when upstream provides it); `human_duration` already renders it on tiles.
- The link explorer and creator-page post list have their own sorts and are not
  the target of this ticket.

## Scope

**Filter model (`GalleryFilters`)**

- [x] Add `sort: str = "newest"` and a `GALLERY_SORTS` table with stable keys,
      at minimum:
      - `newest` — published DESC (current default)
      - `oldest` — published ASC
      - `duration_desc` — longest video first
      - `duration_asc` — shortest video first
- [x] Accept a legacy/plain `?sort=duration` or `?sort=length` only if it maps
      cleanly; otherwise silently fall back to `newest`, matching how
      `PostFilters` handles unknown values.
- [x] Changing `sort` resets `page` to 1, like the other filter dimensions.
- [x] Include a non-default sort in `pairs()`/`url_for()`, so pagination and
      "Clear" preserve it.
- [x] `active` should *not* become true just because a non-default sort is
      selected; "Clear filters" keeps the chosen sort only if that is the
      existing convention for the link explorer (verify first, then be
      consistent).

**Query (`db.list_gallery_images`)**

- [x] Accept `sort` as a keyword argument and map it through a whitelist, never
      by interpolating user input into SQL.
- [x] `duration_desc`: `ORDER BY f.duration_ms IS NULL, f.duration_ms DESC,
      published DESC, f.id DESC`.
- [x] `duration_asc`: `ORDER BY f.duration_ms IS NULL, f.duration_ms ASC,
      published DESC, f.id DESC`.
- [x] Null/zero durations always sort last in both directions; they are not
      treated as "0 seconds" at the top.
- [x] Keep the existing deterministic tie-breaks so paging cannot repeat or
      skip a row (dedup happens on `f.sha256`, so break ties on that or `f.id`).
- [x] The same ordering must apply to the `count(DISTINCT sha256)` total query
      path only where relevant; totals do not change with sort.
- [x] Non-video rows in a mixed grid: define the behaviour explicitly (prefer
      "duration sorts only apply to videos/GIFs; images go last") and cover it
      in a test.

**Template / UI (`gallery.html`)**

- [x] Add a "Sort" `<select name="sort">` bound to the filter form, with a
      proper `<label for="gallery-sort">`.
- [x] Show all four options when `kind` is empty, `video` or `gif`; hide the
      duration options when `kind=image` (they cannot mean anything there) and
      make sure a bookmarked `?kind=image&sort=duration_desc` still renders
      sensibly (fall back or keep the option visible but selected).
- [x] The select submits with the existing "Apply" behaviour; no JavaScript
      needed and no htmx requirement.
- [x] Gallery header/count text stays unchanged.
- [x] Add a "Longest first" / "Shortest first" human label, not raw keys.

**Other video sections**

- [x] Reuse `GALLERY_SORTS`/the same ordering helper if a second video list is
      added later; do not duplicate the SQL. Document the helper in the
      Resolution.
- [x] The viewer's within-post order stays `position`-based (T8.1) and is out of
      scope.
- [x] The post page attachment order stays `position`-based (T4.4) unless a
      separate ticket asks otherwise.

**Tests**

- [x] Filter parsing: `sort=duration_desc` accepted; unknown values fall back to
      `newest`; `sort` survives `pairs()`/`url_for()` round-trips; changing sort
      resets the page.
- [x] DB ordering: seed videos with durations `5_000`, `90_000`, `null` and one
      image. Assert `duration_desc` → 90 s, 5 s, then null/image; `duration_asc`
      → 5 s, 90 s, then null/image. Same result with a `kind=video` filter.
- [x] Paging: with a page size forced small, page 1 + page 2 under
      `duration_desc` contain no duplicate sha and cover the expected set.
- [x] Route/template: the select has the four options with the current value
      `selected`; `?kind=video&sort=duration_desc` appears in the response and
      in the pager links.
- [x] Existing gallery tests (T4.7/T7.2) stay green.

## Acceptance criteria

- [x] `/c/{id}/gallery?kind=video&sort=duration_desc` shows the longest video
      first, and `duration_asc` shows the shortest first.
- [x] Videos without a known duration never appear above videos with a known
      duration, whichever direction is selected.
- [x] Page 2 of a sorted gallery keeps the same sort, and the URL can be
      bookmarked and reloaded to the same order.
- [x] The sort control is keyboard reachable, labelled, and works without
      JavaScript.
- [x] The default gallery view is unchanged (newest first).
- [x] Bulk/mixed media still renders with images where the chosen order
      defines, with a documented rule and no duplicated tiles.

## Out of scope

- Sorting the viewer or the post page attachment list by duration.
- Sorting by resolution, bitrate or file size (a separate ticket if wanted).
- Client-side sorting of an already-rendered grid.
- Upstream backfilling of missing `duration_ms` (T7.1 already normalizes kind;
  missing durations stay missing).
- Natural-language queries such as "show videos over 2 minutes" (that is a
  min/max duration *filter*, not a sort).

## Notes

- Check whether `duration_ms` is populated for MP4-backed GIFs (kind `video`)
  and real GIFs (kind `gif`) in the reference archive before deciding whether
  the sort label should say "Video length" or "Duration"; keep the SQL generic
  either way.
- `human_duration` already formats the tile badge, so the UI needs no new
  formatting helper.
- Follow the `PostFilters.sort` / `SORTS` pattern for naming and validation so
  the two filter models stay consistent.

## Resolution

Shipped as a URL-encoded `sort` dimension on the gallery, with one whitelist for
labels and one for SQL.

**Code**

| File | Change |
|---|---|
| `src/monoke/web/filters.py` | `GALLERY_SORTS` labels, `sort: str = "newest"` on `GalleryFilters`, `_gallery_sort()` (accepts `duration`/`length` aliases), page reset on sort change, non-default sort in `pairs()` |
| `src/monoke/db.py` | `GALLERY_SORTS_DB` whitelist plus `gallery_order_sql()` helper, `sort=` keyword on `list_gallery_images()` |
| `src/monoke/web/routes.py` | `_gallery_sorts()` hides duration keys for `kind=image` (keeps a bookmarked key selected) and passes `sorts` to the template |
| `src/monoke/web/templates/gallery.html` | labelled `<select id="gallery-sort" name="sort">` inside the existing filter form |
| `tests/test_gallery.py` | parsing/aliases/fallback/URL round-trip, duration ordering with null + zero + image, paging without duplicates, template selection and pager links |

**Ordering rule.** `duration_desc` and `duration_asc` only order timed media:
the first key puts `kind='image'` rows last, the second puts unknown (NULL or
zero) durations last, and only then does the duration itself apply. Unknowns of
either spelling tie on `published DESC, max(f.id) DESC`, so explicit paging
cannot skip or repeat a row. `newest`/`oldest` keep the previous published
ordering; the default grid output is unchanged.

**Clear convention.** `active` is unaffected by `sort`, matching `PostFilters`
and `LinkFilters`; "Clear filters" goes to the bare gallery URL and therefore
drops the sort, exactly like the link explorer's `base_url`. The chosen sort is
preserved across pagination and in bookmarks through `pairs()`.

The viewer and post attachment lists stay `position`-ordered (T8.1, T4.4); this
helper is the one to reuse if another archive-wide video list is added.
