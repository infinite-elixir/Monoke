# T12.8 — Crawler and sync loop for multiple sources

## Goal

Run the same crawl orchestration for cum.st and pawchive while respecting their
different pagination, totals and incremental signals.

## Scope

**Source selection**

- [ ] `crawl_full(ref: SourceRef, ...)` resolves the adapter from
      `registry.get(ref.source)` and builds the matching client.
- [ ] The adapter supplies profile/list/detail paths and payload parsing; the
      crawler continues to own persistence, progress and cancellation.
- [ ] `web/tasks.py` and the CLI pass `SourceRef` through unchanged.

**Page walk**

- [ ] Share one loop that:
      - [ ] calls `posts_page(ref, offset)`;
      - [ ] stops on an empty page;
      - [ ] stops when `len(page.posts) < page_size` **only when the adapter
            promises a fixed page size** (cum.st uses `Settings.page_size`,
            default 50; pawchive is fixed at 50);
      - [ ] dedupes IDs and tolerates offset shifts on a live feed;
      - [ ] reconciles against `page.total` **only when it is not `None`**;
      - [ ] for pawchive, records `posts_seen = len(ids)` with no total warning
            and no 10,000-page false alarm beyond the existing guard.
- [ ] Progress events:
      - [ ] `page` events omit `pages_total` when unknown;
      - [ ] `total` may be `None`; the SSE client and `sync_progress.html` must
            not render `NaN` or divide by zero;
      - [ ] after the walk, `posts_seen` becomes the denominator as today.

**Incremental sync**

- [ ] `pending` becomes a list of `(post_id, upstream_edited_at | None)` rather
      than bare IDs.
- [ ] `--full` / `--deep` still refetches everything.
- [ ] Default incremental:
      - [ ] cum.st: unchanged — new IDs plus the newest `refresh_window` IDs.
      - [ ] pawchive: new IDs, plus any existing post whose list `edited`
            differs from `posts.upstream_edited_at`, plus the refresh window.
- [ ] Detail fetches write `upstream_edited_at`; a failed detail retries on the
      next sync because the timestamp is still stale.
- [ ] `_fan_out` still records per-post errors, warnings, link/file counts and
      rate; cancellation still propagates.

**Missing upstream**

- [ ] A stored post absent from a completed list walk is flagged
      `missing_upstream`; never deleted. This works for pawchive too even
      without a total.

**CLI**

- [ ] `monoke sync <cum.st URL>` and `monoke sync <pawchive URL>` autodetect.
- [ ] Update `--help` text and the module description to say "supported
      sources", not cum.st only.
- [ ] Exit codes stay `0/2/3/130/1`; a pawchive 403 maps to `blocked` → `3`.
- [ ] `--json` includes the source.

**Tests**

- [ ] respx crawl test for pawchive: 2 list pages (50 + 3), 53 detail responses,
      empty third page, correct counts and rows.
- [ ] List-only incremental test: change one `edited`, assert only that post's
      detail is refetched.
- [ ] Empty page terminates without a `total`.
- [ ] A 403 aborts as blocked and leaves the run row failed/blocked.
- [ ] Cancellation mid-fan-out marks the run cancelled.
- [ ] Existing cum.st crawl tests pass unchanged.

## Acceptance criteria

- [ ] A pawchive URL can complete a crawl through the same `crawl_full` entry
      point as cum.st.
- [ ] No `if source ==` branch outside the source adapters; differences are
      expressed by adapter capabilities (`has_total`, `page_size`).
- [ ] A second sync of an unchanged pawchive creator fetches only list pages
      (plus the refresh window) and writes no duplicate rows.
- [ ] `uv run pytest` is green offline.

## Out of scope

- UI copy/badges and preview-only presentation (T12.9).
- Downloading media or ZIPs.

## Notes

- Pawchive's list does not include a total; do not invent one from a previous
  run or from `post_count`.
- Pacing is set by T12.4. Do not raise pawchive concurrency to "make the first
  crawl faster" without a measured, documented reason.
