# T9.1 — Local bookmark storage, repository and toggle endpoints

## Goal

Give Monoke its own bookmark state for **posts** and **media**. Bookmarks are a
local, single-user curation tool: they survive a sync, are independent of
cum.st's upstream `bookmarked` flag, and can be toggled from forms without
JavaScript.

This ticket provides the schema, the repository functions, and the HTTP toggle
endpoints. The buttons and the library page are T9.2 and T9.3.

## Current behaviour

- `creators.bookmarked` and `posts.bookmarked` exist in the schema, but they are
  copied from the cum.st API by the crawler (`crawl.py`, `upsert_creator`,
  `upsert_post`) and are overwritten on every sync. They are **not** usable for
  local bookmarks.
- There is no local table, repository, route or UI for bookmarks.
- `files` rows are deleted and re-inserted by `replace_files()` on every sync,
  so `files.id` is not stable. A media bookmark must key on the stable
  `(creator_id, sha256)` pair instead.

## Scope

**Schema (`db.py`)**

- [ ] Bump `SCHEMA_VERSION` and append a `_V6` migration (do not edit `_V1`):
      - `post_bookmarks(id INTEGER PRIMARY KEY, creator_id INTEGER NOT NULL
        REFERENCES creators(id) ON DELETE CASCADE, post_id INTEGER NOT NULL
        REFERENCES posts(id) ON DELETE CASCADE, created_at TEXT NOT NULL,
        UNIQUE(post_id))`
      - index on `(creator_id, created_at DESC, id DESC)`
      - `media_bookmarks(id INTEGER PRIMARY KEY, creator_id INTEGER NOT NULL
        REFERENCES creators(id) ON DELETE CASCADE, sha256 TEXT NOT NULL,
        created_at TEXT NOT NULL, UNIQUE(creator_id, sha256))`
      - index on `(creator_id, created_at DESC, id DESC)`
- [ ] Deleting a creator removes both kinds of bookmark via `ON DELETE CASCADE`;
      deleting/replacing a post's files must not remove a media bookmark.
- [ ] No foreign key from `media_bookmarks` to `files`.

**Repository functions**

- [ ] `toggle_post_bookmark(conn, creator_id, post_service_id) -> bool`
      returns the new state. Look up the post by `(creator_id, service_id)`;
      raise `ValueError`/`KeyError` for an unknown post. Use `now_iso()`.
- [ ] `toggle_media_bookmark(conn, creator_id, sha256) -> bool` validates that
      at least one `files` row with that sha belongs to the creator before
      inserting, so junk shas cannot be bookmarked. Re-bookmarking the same sha
      in another post is one bookmark, not two.
- [ ] `post_is_bookmarked(conn, creator_id, post_id) -> bool` and
      `media_is_bookmarked(conn, creator_id, sha256) -> bool` for single views.
- [ ] Batch helpers for list pages (no N+1):
      `bookmarked_post_ids(conn, creator_id, post_ids) -> set[int]` and
      `bookmarked_media_shas(conn, creator_id, shas) -> set[str]`.
- [ ] `list_post_bookmarks(conn, *, creator_id=None, limit, offset)` returns
      `(rows, total)` newest-bookmarked first, joined to `creators` so the
      library page can show the creator name and a post link. Include the
      current `title`, `published`, `service_id`, `missing_upstream` and a
      thumbnail (first attachment, same rule as `post_cards`).
- [ ] `list_media_bookmarks(conn, *, creator_id=None, limit, offset)` returns
      one row per bookmark with `sha256`, `created_at`, `creator_id`,
      `creator_name`, `post_id`, `post_service_id`, plus the **current**
      attachment metadata (`url`, `thumb_url`, `kind`, `width`, `height`,
      `duration_ms`, `original_filename`) chosen deterministically from any
      current file row with that sha. If the file is no longer attached, return
      the row with `url = NULL` and `missing = 1`; do not drop the bookmark.
- [ ] Both list functions must not interpolate user input into SQL and must
      clamp `limit`/`offset`.

**HTTP endpoints (`routes.py`)**

- [ ] `POST /c/{creator_id}/p/{post_service_id}/bookmark` toggles a post.
- [ ] `POST /c/{creator_id}/media/{sha256}/bookmark` toggles a media item.
- [ ] Unknown creator, post or sha → 404; a sha that exists only under another
      creator → 404, never cross-creator bookmarking.
- [ ] Form response: `303` redirect to the optional `next` field when it is a
      safe local path (`/…` but not `//…`), otherwise to the post or creator
      page. Never redirect to an external URL (open-redirect guard).
- [ ] `Accept: application/json` (or `?format=json`) returns
      `{"bookmarked": true|false, "kind": "post"|"media", "id": …}` with 200 so
      the viewer can toggle without reloading.
- [ ] Toggle is idempotent in effect: two posts in a row return to the original
      state.
- [ ] Do not read, write or mimic the upstream `posts.bookmarked` column.

**Tests**

- [ ] Migration test: a fresh DB reports schema v6; an existing v5 DB migrates
      without losing rows.
- [ ] Post toggle: true → false → true; second creator cannot see the bookmark.
- [ ] Media toggle: survives `replace_files()` with the same sha, disappears
      when the post is deleted, and is deduplicated across two posts.
- [ ] Batch helpers return exactly the bookmarked ids/shas for the given page.
- [ ] `list_post_bookmarks` / `list_media_bookmarks` ordering, creator filter,
      creator-name join, and the `missing = 1` case after a file disappears.
- [ ] Route tests: POST redirect (safe and rejected external `next`), JSON
      response, 404s, unknown sha, cross-creator sha, double toggle.
- [ ] `uv run pytest` stays green.

## Acceptance criteria

- [ ] A post can be bookmarked and un-bookmarked against the local DB, and the
      state survives a full re-sync.
- [ ] An image/video can be bookmarked by its sha; the same file appearing in
      several posts is one bookmark.
- [ ] No bookmark is ever written to the upstream `bookmarked` column.
- [ ] Toggle endpoints are safe for form posts (303 + local-only redirect) and
      return JSON when asked.
- [ ] Unknown or cross-creator targets return 404.
- [ ] Schema migration is additive and old databases upgrade cleanly.

## Out of scope

- Buttons, templates, styles and the viewer shortcut (T9.2).
- The `/bookmarks` library page and nav entry (T9.3).
- Sync-time import/export of cum.st's own bookmarks.
- Tags/collections/folders, notes, ordering by hand, sharing.
- Multi-user accounts or per-user bookmark namespaces.

## Notes

- `posts.bookmarked` is upstream provenance. Reusing it would be overwritten by
  the next sync and would lie about the user's local curation.
- Keying media by sha is deliberate: `replace_files()` recreates rows, and the
  gallery already deduplicates by sha.
- Keep the toggle JSON tiny; T9.2 can optimistically swap the button state and
  fall back to a normal form POST when JavaScript is off.

## Resolution

Schema is v6 (`_V6` appended; `_V1` untouched): `post_bookmarks` and
`media_bookmarks`, both cascading from `creators`, with
`(creator_id, created_at DESC, id DESC)` indexes and `UNIQUE(post_id)` /
`UNIQUE(creator_id, sha256)`. There is deliberately no foreign key from a media
bookmark to `files`, so `replace_files()` cannot erase curation.

`db.py` adds `toggle_post_bookmark`, `toggle_media_bookmark`,
`post_is_bookmarked`, `media_is_bookmarked`, the batch helpers
`bookmarked_post_ids` / `bookmarked_media_shas`, `list_post_bookmarks`,
`list_media_bookmarks` and `bookmark_creator_facets` (used by T9.3). List
functions clamp `limit` to 1..200 and `offset` to >= 0, use bound parameters
only, and order by `created_at DESC, id DESC`. Media rows pick their current
attachment deterministically (`min(files.id)` for the creator + sha) and come
back with `missing = 1`, `url = NULL` when the file is gone.

One intentional reading of the ticket: a media bookmark is **not** removed when
its post or file disappears. Keying by `(creator_id, sha256)` and T9.3's
"missing attachment is still visible and removable" require the bookmark to
survive; removal of a missing bookmark is therefore allowed while insertion
still validates that the sha belongs to the creator. `posts.bookmarked` is never
read or written by any bookmark path.

`routes.py` adds `POST /c/{creator_id}/p/{post_service_id}/bookmark` and
`POST /c/{creator_id}/media/{sha256}/bookmark`. Unknown creator/post/sha and
cross-creator shas are 404. Forms get a 303 to a validated local-only `next`
(rejects `//host`, scheme URLs, backslashes, CR/LF and encoded `/%2f`); JSON
clients (`Accept: application/json`, `X-Requested-With: fetch` or
`?format=json`) get `{"bookmarked", "kind", "id"}` with 200.

Tests in `tests/test_bookmarks.py` cover the v5→v6 upgrade preserving rows,
cascade on creator delete, post/media toggles, sha dedupe across posts, file
replacement, batch helpers, list ordering/filter/name join/missing state,
facets, redirect safety, JSON toggles, double toggles and 404s.
