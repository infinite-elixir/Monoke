# T12.3 — Persist source identity, upstream edit times, and preview-only files

## Goal

Let one database hold a cum.st creator and a pawchive creator that happen to
share the same service and creator id, and carry the extra fields pawchive
needs without lying about cum.st data.

## Why

`creators` is currently `UNIQUE(service, service_id)`. `patreon/30500811` may
exist on both sites; today the second archive would collide with the first.
Pawchive also needs an upstream `edited` timestamp for cheap incremental sync,
and many attachments are preview-only, which the UI must not present as
downloadable originals.

## Scope

**Migration V7 (`SCHEMA_VERSION = 7`)**

- [ ] Rebuild `creators` with the full existing column list plus:

      ```sql
      source TEXT NOT NULL DEFAULT 'cumst',
      ...
      UNIQUE(source, service, service_id)
      ```

      Copy every column (`id, service, service_id, name, display_name,
      avatar_url, header_url, indexed_at, updated_at, content_updated_at,
      bookmarked, post_count, last_synced_at`) and preserve `id` values so every
      child foreign key keeps pointing at the same creator.
- [ ] Existing rows backfill to `source='cumst'`.
- [ ] The rebuild must run with `PRAGMA foreign_keys=OFF` outside the
      transaction, then `PRAGMA foreign_keys=ON` and `PRAGMA foreign_key_check`
      afterwards. Verify `posts`, `runs`, `post_bookmarks` and
      `media_bookmarks` cascade/survive.
- [ ] `ALTER TABLE posts ADD COLUMN upstream_edited_at INTEGER` (epoch seconds,
      nullable). cum.st leaves it `NULL`.
- [ ] `ALTER TABLE files ADD COLUMN preview_only INTEGER NOT NULL DEFAULT 0`.
- [ ] Do not add `source` to `posts`: the creator owns it, and
      `UNIQUE(creator_id, service_id)` already scopes posts correctly.
- [ ] Keep migrations idempotent through the existing migration runner.

**Repositories**

- [ ] `db.upsert_creator(..., source: str = "cumst")` writes and looks up on
      `(source, service, service_id)`; `db.find_creator(conn, source, service,
      service_id)` takes the source.
- [ ] Update every caller: crawler, web add/sync routes, tests.
- [ ] `db.list_creators` / creator rows expose `source` for the dashboard and
      source badges.
- [ ] `db.save_post_bundle(..., upstream_edited_at: int | None = None)`.
- [ ] `db._write_files` persists `preview_only`; `db.list_files` and gallery
      queries return it.
- [ ] Add `db.post_edit_map(conn, creator_id) -> dict[str, int | None]` (or
      equivalent) for incremental pawchive sync.
- [ ] `db.print_stats` reports creators per source.

**Tests**

- [ ] Migrate a v6 database with one creator, post, file, run, bookmark and a
      link resolution; assert all rows survive, `source='cumst'`,
      `preview_only=0`.
- [ ] After migration, insert the same `(service, service_id)` under
      `source='pawchive'`; both creators coexist and list separately.
- [ ] Deleting the pawchive creator cascades only its own posts/files/bookmarks.
- [ ] Inserting a preview-only file round-trips the flag.
- [ ] Re-running migration is a no-op.

## Acceptance criteria

- [ ] A fresh database and a migrated v6 database have the same schema version
      and pass the full existing test suite.
- [ ] `PRAGMA foreign_key_check` returns no rows after migration.
- [ ] `SELECT source, service, service_id FROM creators` is unique per source.
- [ ] Existing cum.st creator IDs, post URLs, bookmarks and media bookmarks are
      unchanged.

## Out of scope

- UI badges for `source` and `preview_only` (T12.9).
- Populating `upstream_edited_at` (T12.6/T12.8).

## Notes

- SQLite cannot drop the old table-level `UNIQUE`; a table rebuild is required.
  Do not fake it with a second unique index—the old constraint would still
  reject the pawchive row.
- `preview_only` is a display/permission hint, not a licence to download
  anything. Monoke still never stores media bytes.
