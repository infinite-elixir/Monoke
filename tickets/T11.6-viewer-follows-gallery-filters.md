# T11.6 — Viewer follows the active gallery filters

## Goal

Opening a tile from a filtered gallery must keep browsing inside that filtered
set. If the **Videos** tab is active, Next from the last video in a post must
land on the next matching video, never on an image or GIF. The same applies to
search, tag, orientation, minimum size, date range and the chosen sort order.

## Problem

The grid is filtered by `db.list_gallery_posts`, but the viewer payload is not
filter-aware:

- `/c/{id}/viewer/data` accepts only `post` and calls `db.viewer_state`.
- `viewer_media` returns every viewer-kind file of the post.
- `viewer_neighbour` skips text-only posts but not posts whose media the current
  filter excludes.
- `neighbour_images` preloads unrelated media.

So on the Videos tab, pressing Next from the last video crosses into the next
post and paints its first image. Up/Down post arrows also ignore the filtered
post order and the gallery sort.

## Locked contract

The viewer request carries the gallery filter context:

```
GET /c/{creator_id}/viewer/data
    ?post={post_service_id}
    &kind=video
    &q=...
    &tag=...
    &orientation=portrait
    &min_bytes=...
    &from=YYYY-MM-DD
    &to=YYYY-MM-DD
    &sort=newest|oldest|duration_desc|duration_asc
```

- Parameter names and validation match `GalleryFilters` exactly.
- `page` is deliberately **not** sent: the viewer crosses page boundaries and
  stops only at the edges of the filtered result set.
- No filter parameters means today's behaviour: every viewer-kind medium, in
  viewer order. Future entry points such as bookmarks keep that default.
- A post with no media matching the filters is never a navigation destination.

## Current behaviour

- `viewer_state()` returns all `image` / `gif` / `video` files for the post.
- `previous_post` / `next_post` use published-descending post order only.
- Tiles carry `data-viewer-index` computed among **all** files of the post
  before filtering.
- `lightbox.js` builds the data URL from `post` alone (`fetchPayload`,
  `jump`, `hydrate`).

## Scope

**Endpoint and data layer**

- [ ] Accept the gallery filter parameters on `/viewer/data` by reusing
      `GalleryFilters.from_query`; ignore `page` for the navigation set.
- [ ] Extend `viewer_state()` to take the filters and filter the current post's
      media with the same conditions as `_gallery_media_where`
      (kind / orientation / min_bytes).
- [ ] Apply the post-level conditions (search / tag / dates) when resolving
      `previous_post` and `next_post`, and skip any post with no matching media.
- [ ] Order neighbours according to `sort` (`newest`, `oldest`, `duration_desc`,
      `duration_asc`) so Up/Down follow what the grid shows.
- [ ] Make `post_rank` / `media_post_count` reflect the filtered set and sort.
- [ ] Return only matching media in `media`; `media_count` and item indexes
      describe that filtered list.
- [ ] Return `neighbour_images` only when the filters can still produce still
      images; on a Videos-only or GIF-only view do not preload image neighbours.
- [ ] Return `404 {"error": "no media match these filters"}` when a post has no
      matching media instead of an empty playlist.
- [ ] Keep the unfiltered payload unchanged when no parameters are present.

**Template and controller**

- [ ] Serialise the active filters once on the gallery page (for example a
      `data-viewer-query` on `[data-gallery]`) with `page` removed.
- [ ] `lightbox.js` appends that whitelisted query to every `/viewer/data`
      request: initial `hydrate`, `jump` and payload prefetch.
- [ ] Entry points without a gallery context (bookmark tiles, future routes)
      request the unfiltered payload.
- [ ] Keep resolving the opening item by `sha256` first; make the
      `data-viewer-index` fallback match the filtered list so it cannot open
      the wrong item.
- [ ] Post arrows disable at the first/last **matching** post.
- [ ] Media arrows at the end of the filtered post cross to the neighbouring
      matching post's first matching medium (and its last medium when going
      backwards), never to an excluded kind.

**Tests**

- [ ] Endpoint: `kind=video` on a mixed post returns only videos and their
      filtered indexes.
- [ ] Endpoint: `previous_post` / `next_post` skip posts without a matching
      video, including posts outside the current gallery page.
- [ ] Endpoint: search, tag, orientation, `min_bytes` and date filters each
      constrain both current media and neighbours.
- [ ] Endpoint: `sort=oldest` reverses Up/Down order; duration sorts order by
      the matching videos.
- [ ] Endpoint: `neighbour_images` is empty when still images are filtered out.
- [ ] No-filter request returns the same payload as before this ticket.
- [ ] JS source/behaviour: every data request includes the serialised filters;
      tile-opened viewers keep contrast between filtered and unfiltered entry.
- [ ] `node --check src/monoke/web/static/lightbox.js` and `uv run pytest` pass.

## Acceptance criteria

- [ ] With **Videos** selected, opening a video and pressing Next moves through
      videos and never paints an image.
- [ ] Search/tag/orientation/size/date filters are honoured inside the viewer,
      including when crossing posts.
- [ ] At the filtered edges the corresponding arrow is disabled.
- [ ] Browsing continues into matching posts on later gallery pages.
- [ ] Opening from an unfiltered surface behaves exactly as in T11.5.

## Out of scope

- Media-level bookmarks and the bookmarks-library viewer (T11.3).
- Changing gallery filter semantics, facet counts or the grid query.
- A persisted "viewer follows grid" preference.
- Matching search text against filenames; search stays post-level.

## Notes

- Reuse `_gallery_media_where`, `_gallery_post_where` and `_gallery_post_order`
  rather than copying their SQL into the viewer.
- The endpoint is internal; changing its signature is fine, but tile bootstrap
  and bookmark entry points must both keep working.
- Keep the filters serialised in one place so the controller cannot drift from
  the grid.
