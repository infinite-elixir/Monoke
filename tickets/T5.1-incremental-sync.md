# T5.1 — Incremental sync

## Goal
Keep the archive fresh in seconds, not minutes.

## Scope

- [ ] `async sync(ref, *, deep=False, refresh_window=100, progress=None)`.
- [ ] Algorithm:
      1. list pages only (`o=0,50,…` until empty) → ordered IDs and `total`.
      2. `new_ids` = IDs not in the DB.
      3. `refresh_ids` = the newest `refresh_window` posts (default 100). The list response has
         no per-post `edited`/`updated` field, so this window is how edits are caught.
      4. fetch details for `new_ids ∪ refresh_ids`; `--deep` → every ID.
      5. IDs present in the DB but absent from the walk → `missing_upstream = 1` (never delete).
      6. update `creators.post_count = total`, `last_synced_at`, write the run.
- [ ] Re-appearance clears `missing_upstream`.
- [ ] `refresh_window=0, deep=False` → list-only mode ("what's new").
- [ ] Re-extraction updates existing rows in place; `posts.id` stays stable.
- [ ] Report `posts_new`, `posts_updated`, `posts_missing`, `links_found`, elapsed.

## Acceptance criteria

- [ ] Second sync on an unchanged creator: 16 list calls + 100 detail calls, 0 new posts,
      finishes in < 30 s locally.
- [ ] A post inserted upstream (fixture: one extra ID at the head, `total` 783) is fetched
      once and appears once.
- [ ] A post removed upstream is flagged `missing_upstream=1`, still viewable, badged.
- [ ] Re-appearing post clears the flag.
- [ ] `--deep` re-fetches all 782 details and reports `posts_updated=782`.
- [ ] No duplicate links or files after re-extraction.

## Notes
- Document the refresh window in the README; users will ask why an old edited post is stale.
- Do not clear `api_cache` on sync.
- `total` is the only source of truth for the post count; there is no `post_count` in the
  profile payload.
