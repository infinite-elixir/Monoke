# T8.6 — Left/right at a post's edge crosses into the neighbouring post

## Goal

Make horizontal navigation continuous across the archive. Today left/right stop
dead at the first and last media of a post, forcing the user to move to the
top/bottom band (or press Up/Down) to reach the next post. Instead:

- **Right on the last media of a post** loads the **first media of the next
  (older) post**, if one exists.
- **Left on the first media of a post** loads the **last media of the previous
  (newer) post**, if one exists.

This matches the mental model of paging through a book: horizontal movement
keeps going in the same direction, and reversing it lands on the item you came
from.

## Current behaviour

- `viewer.js` `go("next-image")` returns early when
  `currentIndex === state.media.length - 1`; `go("prev-image")` returns early
  at `0`. Both edges are no-ops.
- `db.viewer_state()` already returns `previous_post` (newer) and `next_post`
  (older) service ids, and `jump()` in `viewer.js` already fetches
  `/c/{id}/viewer/data?post=…` with an `AbortController` and a token guard.
- `jump()` currently hard-codes the destination index to `0`, so the reverse
  case (previous post, last media) has no path yet.
- T8.3's direction contract explicitly says "No wrapping. Right at the last
  image must not silently jump to another post". This ticket supersedes the
  boundary rows of that contract; its in-post behaviour is unchanged.

## Direction contract (amended)

With the current item at index `i` in a post containing `n` items:

| Direction | Normal action | At the edge |
|---|---|---|
| Right | `i + 1` in the same post | `i = n - 1` → **next post** (older), item `0` |
| Left | `i - 1` in the same post | `i = 0` → **previous post** (newer), item `n - 1` of that post |
| Up | previous/newer post, item `0` | unchanged, no wrap at the newest post |
| Down | next/older post, item `0` | unchanged, no wrap at the oldest post |

- "Next post" and "previous post" are exactly `state.next_post` and
  `state.previous_post` from T8.1, so text-only posts stay skipped.
- No wrap-around at the archive ends: left on the newest post's first media and
  right on the oldest post's last media remain no-ops.
- The target index for a post jump must be explicit; do not add a second copy
  of the fetch/abort logic.

## Scope

**Behaviour**

- [ ] Right at `n - 1` calls the existing post-jump path with
      `next_post` and target index `0` when `next_post` is non-null.
- [ ] Left at `0` calls the same path with `previous_post` and target index
      `media.length - 1` of the target post, when `previous_post` is non-null.
- [ ] The target post's payload is used to clamp the index (the neighbour post
      may have a different media count); never keep the old post's index.
- [ ] At the archive ends nothing happens: no fetch, no flash, no URL change.
- [ ] A jump in either direction updates the URL to
      `?post=<target service id>&i=<target index>` via `history.replaceState`.
- [ ] The counter reads `target index + 1 / target media count` and the
      `aria-live` announcer reports the new post rank, exactly as Up/Down do.

**All input methods**

- [ ] The boundary decision lives in the same `go(action)` dispatcher used by
      the zones, arrow keys, horizontal wheel/trackpad and swipes, so all four
      paths cross posts without separate implementations.
- [ ] Keep the 150 ms navigation throttle; a boundary jump plus a trailing
      gesture must not fire two fetches.
- [ ] A late response from an older boundary jump must not overwrite a newer
      one (`AbortController` + token guard, as today).
- [ ] A failed fetch keeps the current media, clears `aria-busy` and shows the
      existing non-blocking flash.
- [ ] Video playback must not be affected: crossing away pauses/unloads the
      old element via the existing `unloadMedia()` path.

**Hint / discoverability**

- [ ] Do not add visible chrome (T8.5). The existing first-run hint wording may
      stay; optional: mention that left/right continue into the next post.
- [ ] Keyboard focus stays on the viewer root after a boundary jump, as it does
      after Up/Down.

## Tests

- [ ] Server test: for a chain of three media posts, `viewer_state` exposes
      `previous_post`/`next_post` for the middle post and `null` at the
      respective archive ends (extend the existing neighbour tests if needed).
- [ ] Server test: the target post's `/viewer/data` payload has the expected
      first and last `index`/`sha256` values, so the JS has a valid destination
      in both directions.
- [ ] `node --check src/monoke/web/static/viewer.js` passes.
- [ ] Browser acceptance (Chromium and Firefox):
      - a 3-image post in the middle: right on item 3 lands on item 1 of the
        next older post; left on item 1 of that post returns to item 3 of the
        original post;
      - newest post, left on item 1: no navigation and no request;
      - oldest post, right on the last item: no navigation and no request;
      - zone click, `ArrowRight`/`ArrowLeft`, horizontal wheel and swipe all
        cross at the edge and still move one step inside the post;
      - exactly one `/viewer/data` request per boundary crossing;
      - URL, counter and announcer match the destination.

## Acceptance criteria

- [ ] Right on the last media of a post opens the first media of the next post
      (if any); left on the first media opens the last media of the previous
      post (if any).
- [ ] No wrap-around at the newest or oldest media post.
- [ ] Up/Down and all in-post left/right behaviour are unchanged.
- [ ] One gesture = one move, with no duplicate fetches or double navigation.
- [ ] A failed target fetch leaves the current item and controls intact.
- [ ] The viewer still shows only media, the counter and (first run) the hint.

## Out of scope

- Changing Up/Down semantics or the hint's design (T8.4).
- Preloading the neighbouring post's data or its media; T8.7 only warms images
  inside the current post.
- Infinite loop / wrap-around navigation at the archive ends.
- Bookmarking (T9.1-T9.3).
- Cross-creator navigation.

## Notes

- Reuse `jump()`, but give it an optional `index` argument (default `0`) instead
  of setting `state.index = 0` after the fetch. Up/Down must keep landing on
  item `0`.
- The left-at-start direction is intentional: it is the inverse of the move
  that brought the user into the post, so a quick left/right pair round-trips.
- Update T8.3's Notes with a pointer to this ticket so the old "never wrap"
  line is not read as current behaviour.

## Resolution

`go("prev-image")` / `go("next-image")` keep their in-post branch and, at the
edge, call the existing post-jump path instead of returning: right uses
`state.next_post` with target `0`, left uses `state.previous_post` with a `-1`
sentinel that `jump()` resolves to `media.length - 1` **of the fetched target
payload**. `jump(serviceId, index)` defaults `index` to `0`, so Up/Down still
land on item 0, and the target index is clamped by `render()` against the new
post's own count — the old post's index is never reused.

All inputs (zones, arrow keys, horizontal wheel, swipes) already funnel through
`go()`, so they cross posts through one implementation. The 150 ms throttle,
`AbortController` and token guard are untouched; a failed fetch keeps the
current media, clears `aria-busy` and reuses the existing flash. `render()`
owns the URL, counter and announcer update, so a boundary jump matches Up/Down
including the new post rank. At the archive ends both neighbours are `null`,
so the handler returns before any fetch or URL change.

Covered by `test_viewer_state_exposes_neighbour_chain_and_destination_edges`
(three-post chain, archive ends, both destination endpoints) plus
`node --check`. The Chromium/Firefox matrix in this ticket remains a manual
browser pass, since the repo has no browser automation.
