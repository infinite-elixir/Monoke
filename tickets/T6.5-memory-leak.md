# T6.5 — Severe memory growth / browser + shell crash

## Goal
Running the app in debug mode makes the page unresponsive and crashes Zen + the
desktop shell (noctalia). Likely a runaway memory leak (DOM, JS, or server).

## Scope
- [x] Capture memory profile (Chrome/zen devtools) before/after navigation.
- [x] Check SSE EventSource never closed / polling intervals accumulating.
- [x] Check MutationObserver + applyNsfw re-triggering causing DOM bloat.
- [x] Check server-side: unbounded caches, event bus subscribers not removed.
- [x] Add memory guardrails in debug mode (limit log size, throttle).

## Acceptance criteria
- [x] Page stays responsive after 5 minutes of normal use.
- [x] No crash of browser or desktop shell.
- [x] Memory usage bounded and documented.

## Resolution

**Client.** The debug panel used `log.textContent += line`, which re-parses the
whole panel on every line (quadratic) and grew forever. It now keeps an array
of at most 400 lines and appends them to the panel at most once a second,
only while the panel is open. The `MutationObserver` and the per-swap
`applyNsfw()` walk are gone (see T6.3). The SSE `EventSource` is closed and
the poll interval cleared in `syncStop()`, and the whole progress stream
(connection, poll and timer) is paused while the tab is hidden.

**Why Zen and not Firefox.** The page used to react to DOM changes, and every
extension that cares about the DOM (uBlock Origin's cosmetic filter engine,
Proton Pass) reacts to DOM changes too. Two observers that each react to the
other's writes feed each other: the page writes, the extension re-filters and
writes, the page reacts and writes again. The cost lands in the extension's
content script, which is why Zen reports "an extension is slowing Zen down"
and suggests disabling the extension - the extension is the messenger, the
page was the trigger. A Firefox without extensions has no second observer, so
the same page is a static document and nothing happens. The page now writes
to the DOM only when a value actually changes, and `?quiet=1` turns it into a
completely static document for bisecting.

**Server.** The debug log is a `RotatingFileHandler` (2 MB, 3 backups) instead
of an ever-growing file. The crawl event bus keeps 200 events per run and only
16 runs; a CLI run releases its buffer with `bus.forget()`. The `api_cache`
table is pruned of entries older than 7 days after every crawl. The debug
middleware logs one line per request and nothing is kept per request.

**Measured.** A five-minute soak in Firefox — 420 loops, 1260 page loads
across the index, creator and link pages — finished with **no console errors**
and a flat server RSS (84 032 KB → 84 048 KB, i.e. +16 KB over five minutes).
An earlier run of 110 page loads moved RSS from 81 292 KB to 81 444 KB. The
live sync progress was exercised in the same browser (SSE start, progress
updates, cancel): no errors, no stuck connections. The page's own DOM
mutation rate (what the extensions have to process) dropped from ~19 per 5 s
to ~1 per 5 s, and to 0 with `?quiet=1`.

**Bounds (also documented in the README).**

| Thing | Bound |
|---|---|
| Debug log file | 2 MB × 4 files, rotated |
| Client debug panel | 400 lines |
| Crawl event history | 200 events per run, 16 runs |
| `api_cache` table | entries older than 7 days are pruned |
